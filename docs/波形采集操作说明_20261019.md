## 一、这次改了什么

新增一条**只用于采集训练数据**的串口通道，把 `fastcap` 每 10 ms 采到的一帧 200 点原始 ADC 波形，每 100 ms 通过 USART1（PA9）发给电脑。

| 文件 | 改动 | 备份 |
|---|---|---|
| `HARDWARE\wave_dump.h` | **新建**，导出通道接口 + 帧格式定义 | — |
| `HARDWARE\wave_dump.c` | **新建**，USART1 + DMA2 Stream7 实现 | — |
| `HARDWARE\fastcap.c` | 新增 `g_lastBlock[200]` 软件快照 + `save_block()` + `fastcap_get_last_block()` | `fastcap.c.bak_wavedump_20261019_1640` |
| `HARDWARE\fastcap.h` | 新增 `fastcap_get_last_block()` 声明 | `fastcap.h.bak_wavedump_20261019_1640` |
| `USER\main.c` | 加 include、`WaveDump_Init()`、主循环里 `WaveDump_Poll()` | `main.c.bak_wavedump_20261019_1640` |
| `USER\STM32F407_Template.uvprojx` | 登记 `wave_dump.c` | `STM32F407_Template.uvprojx.bak_wavedump_20261019_1640` |
| `output\ai_data_collection\wave_capture.py` | **新建**，上位机采集脚本 | — |

### 为什么需要软件快照

DMA 是循环模式，两个半区轮流被硬件写。主循环异步组装帧的时候，如果直接读 DMA 缓冲，可能读到「半个新帧 + 半个旧帧」。所以每帧处理完立刻复制一份到 `g_lastBlock`，导出通道只读这份副本。200 次 `uint16` 复制在 168 MHz 下约 1 µs，对 10 ms 的帧周期没有影响。

### 编译结果

```
Program Size: Code=21068  RO-data=3928  RW-data=208  ZI-data=17544
"..\OBJ\STM32F407_Template.axf" - 0 Error(s), 0 Warning(s).
```

| | 改前 | 改后 | 增量 |
|---|---|---|---|
| Code | 20304 | 21068 | **+764** |
| RO-data | 3928 | 3928 | 0 |
| RW-data | 192 | 208 | +16 |
| ZI-data | 16728 | 17544 | **+816** |

ZI 增量 816 字节 = `g_frame[418]` + `g_lastBlock[400]`（对齐后）。SRAM 用了约 17.5 KB / 128 KB，余量充足，NanoEdge 的 8 KB 栈不受影响。

板载 CH340C 现在**不是 COM3**。实测系统里有两个 CH340：

```
COM5   USB-SERIAL CH340
COM7   USB-SERIAL CH340
```

一个可能是 D1 mini，一个是 STM32 板载。不用猜，让脚本自己找：

```powershell
cd H:\毕设设计\output\ai_data_collection
C:\Users\Administrator\.workbuddy\binaries\python\envs\default\Scripts\python.exe wave_capture.py --probe
```

先把电机切到 1 档（按 KEY1）让它转起来，再跑上面的命令。脚本会逐个串口试读 2 秒，能解出波形帧的那个会打印 `<- 这个是 STM32`。

## 四、采集流程

### 4.1 采正常数据（normal）

```powershell
cd H:\毕设设计\output\ai_data_collection

C:\Users\Administrator\.workbuddy\binaries\python\envs\default\Scripts\python.exe wave_capture.py ^
    --port COM7 --label normal --seconds 30 ^
    --out-dir H:\毕设设计\output\ai_samples\wave_20261019
```

操作顺序：
1. **先按 KEY1 进 1 档**，让电机稳定转 3~5 秒
2. 再运行命令
3. 采集期间**手不要碰电机和桌子**
4. 30 秒后自动结束

### 4.2 采异常数据（grip）

```powershell
C:\Users\Administrator\.workbuddy\binaries\python\envs\default\Scripts\python.exe wave_capture.py ^
    --port COM7 --label grip --seconds 30 ^
    --out-dir H:\毕设设计\output\ai_samples\wave_20261019
```

1. 电机 1 档稳定转 3~5 秒
2. 运行命令后**立刻用手捏紧电机输出轴**（模拟负载突增 / 卡滞）
3. 保持捏紧直到采集结束

### 4.3 建议的批次规模

对齐之前 19 维分析的规模（6 批正常 + 3 批异常）：

| 标签 | 批数 | 每批时长 | 预计帧数 |
|---|---|---|---|
| `normal` | 6 | 30 s | 每批约 300 帧 |
| `grip` | 3 | 30 s | 每批约 300 帧 |

每批之间**断电重启一次**（重新标定 ADC 相位与电流零点），这样批间差异能反映真实换机/换人的情况。

### 4.4 采集时不要做的事

- **不要同时开别的串口助手**占着同一个 COM 口（会打不开或互相抢数据）
- **不要在 0 档采集**：固件在 `duty == 0` 时不发波形（停转时电流恒为零，没有训练价值）
- **不要按 KEY0 急停**：会让档位归零，导出随之停止

## 五、采完怎么检查

每批会产出 3 个文件：

| 文件 | 内容 |
|---|---|
| `wave_normal_20261019_163000.csv` | 418 字节帧解析后的原始数据，含 seq / 状态 / 直流 / 极值 / 200 点 |
| `nanoedge_1axis200_normal_20261019_163000.csv` | 纯 200 列数值，**无表头、空格分隔**，直接喂 NanoEdge Studio |
| `wave_normal_20261019_163000.summary.json` | 帧数、丢帧、坏帧、直流均值、峰峰值均值 |

**四个关键指标**：

| 指标 | 正常范围 | 异常时的含义 |
|---|---|---|
| `frames` | 30 s 约 290~300 | 明显偏少 = 波特率或周期不对 |
| `bad_frames` | 0 | 不为 0 = 串口误码（线太长/波特率不稳） |
| `lost_frames` | 0 | 不为 0 = 单片机发得比电脑收得快 |
| `status_hist` | 只有 `正常=N` | 出现「贴轨饱和」= ACS712 输出超出范围，检查接线 |

正常运行时 `dc` 应该稳定在 2000 附近（ACS712 零点 2.5 V 对应 ADC 约 3100，实际取决于分压，以实测为准），`peak_to_peak` 反映纹波大小。

## 七、故障排查

| 现象 | 原因 | 处理 |
|---|---|---|
| `一帧都没收到` | 电机 0 档 | 按 KEY1 进 1 档 |
| 同上 | 串口选错 | 用 `--probe` 自动找 |
| 同上 | 固件没烧 | 重新 Download |
| `打不开 COM7` | 被别的软件占用 | 关掉串口助手 / 关掉 D1 的监控程序 |
| `bad_frames` 很高 | 线太长、共地不良 | 换短 USB 线，确认共地 |
| `status` 出现「贴轨饱和」 | ACS712 输出 0 V 或 5 V | 检查 ACS712 供电与信号线 |
| 波形全是同一个值 | ADC 通道没接对 | 确认 PA5 接 ACS712 OUT |

## 八、这份固件对原功能的影响

**零影响**，理由：

1. 电机控制路径完全没动（`pwm.c` / `motor` 一行未改）
2. 板上 AI 路径完全没动（`ai_monitor.c` / `feature19.c` 一行未改）
3. D1 遥测路径完全没动（`telemetry.c` / `m2_protocol.c` 一行未改）
4. 唯一新增的是 `fastcap_poll()` 之后的一次 `WaveDump_Poll()` 调用，且发送走 DMA，**不阻塞主循环**
5. 主循环新增开销：每 100 ms 一次 418 字节组装（含 414 字节 CRC 计算，约 40 µs）
