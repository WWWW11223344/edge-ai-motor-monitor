## 1 设计目标与约束

### 1.1 题目与场景

**基于边缘 AI 的电机智能状态监控系统。** 在一台 3S 锂电供电的 MG310 直流有刷电机上，实时采集运行数据，在 MCU 本地（无云端、无上位机算力）完成异常检测，把结果同时呈现在板载 OLED 和手机浏览器上。

监控对象是**机械负载类异常**：堵转、卡滞、异物缠绕、轴承磨损导致的摩擦上升。这类异常的共同特征是「电机还在转，但转得比该有的慢」。

### 1.2 设计约束

毕设有硬约束，方案的所有取舍都受它们限制：

| 约束 | 内容 | 对方案的影响 |
|---|---|---|
| 零焊接 | 只能使用杜邦线、现成模块、板载接口 | 排除 INA181A2 等需焊接的精密电流方案，最终用 ACS712-05B 模块 |
| 预算紧 | 新增器件合计 ¥244.50（含备件，开发板不计） | 复用电机自带霍尔编码器（不额外买编码器）、复用 D153C 板载分压（不额外买分压板） |
| 必须可答辩 | 每个数值都要说得出依据 | 阈值、窗长、学习次数全部有标定记录，不用「经验值」 |
| 单机算力 | STM32F407 无 NPU，168 MHz Cortex-M4 | 模型必须在 RAM < 1 KB、Flash < 10 KB 量级 |
| 老师意见 | 「19 个特征值太多，要单一变量下的异常检测」 | 整个第 3 代方案由此而生，见第 4 章 |

### 1.3 老师意见的原文与响应

> 「19 个特征值太多，只要区分正常/异常的关键变量，最好是单一变量下的异常检测。」

这条意见有两种可能的响应方式，本项目选了第二种：

| 响应方式 | 做法 | 问题 |
|---|---|---|
| 敷衍式 | 保留 19 维计算，只是缩小窗口 | 没有回答「为什么是 19 个」 |
| **实质式（本项目采用）** | **用数据证明 19 维本身高度冗余，收敛到 1 维** | 需要重新采数据、重新训练、重写固件 |

实质式响应的完整论证链在第 4 章：先量化 19 维的冗余度（20 对变量 |r| > 0.9），再用「批间区间不重叠度」而非「两类均值差」做筛选判据，最后引入电压归一化解决误报。这条链条每一步都有数据支撑，是本文最值得讲的部分。

## 2 系统总体架构

### 2.1 三层架构

系统自下而上分三层，算力下沉，网络只做呈现：

```
┌──────────────────────────────────────────────────────────────┐
│  呈现层  手机浏览器（同一 WiFi 下打开 http://192.168.157.79） │
│          AI 状态卡 / 转速 / 电流 / 母线 / 特征比值 R          │
└────────────────────────▲─────────────────────────────────────┘
                         │  HTTP，JSON（status_json.cpp 组装）
┌────────────────────────┴─────────────────────────────────────┐
│  网关层  Wemos D1 mini（ESP8266）                             │
│          10 Hz 收 M2 二进制帧 → 解析 → 缓存最新值 → 出 HTTP   │
└────────────────────────▲─────────────────────────────────────┘
                         │  UART 57600 8N1，42 字节二进制帧，10 Hz
┌────────────────────────┴─────────────────────────────────────┐
│  感知与推理层  STM32F407ZGT6（168 MHz，裸机，无 RTOS）         │
│          编码器 → 转速 ┐                                      │
│          分压   → 母线 ┴→ R = rpm/V → 32 点窗 → ZSM 模型       │
│          ADC    → 电流（辅助显示，不进模型）                   │
│          → 相似度 → 报警判定 → OLED 显示 + 串口上报            │
└──────────────────────────────────────────────────────────────┘
```

关键设计：**推理全部在 STM32 上完成，D1 mini 不做任何计算，只做协议转换和网页托管。** 这样「边缘 AI」的名实相符——模型跑在电机旁边，断网也能报警（OLED 与报警灯不依赖网络）。

### 2.2 五级数据流水线

| 级 | 名称 | 在哪 | 输入 | 输出 | 节拍 |
|---|---|---|---|---|---|
| ① | 数据采集 | `encoder.c` `vbat.c` `current.c` | 编码器脉冲、ADC 原始码 | rpm、V、mA | 100 ms / 10 ms |
| ② | 特征构造 | `feature_r.c` | rpm、V | R = rpm / V | 100 ms |
| ③ | 窗口化 | `feature_r.c` | 单个 R | 32 点 R 序列（3.2 s） | 100 ms 滑动 |
| ④ | 边缘推理 | `ai_monitor.c` + `libneai.a` | 32 点窗 | 相似度 0~100 | 100 ms |
| ⑤ | 判定与呈现 | `ai_monitor.c` `ui.c` `telemetry.c` | 相似度 | 报警标志、OLED、遥测帧 | 100 ms |

### 2.3 端到端时延预算

这是答辩一定会被问的点：报警要多久。

| 环节 | 时延 | 说明 |
|---|---|---|
| 编码器采样 | ≤ 100 ms | TIM4 四倍频计数，100 ms 窗 |
| 窗口填满（固有滞后） | **3200 ms** | 32 点 × 100 ms，占绝对主导 |
| 模型推理 | < 5 ms | 32 点均值池化 + 一次 Z-score，40 B 模型 |
| 报警去抖 | 200 ms | 连续 2 个窗低于阈值 |
| **合计（最坏）** | **约 3.5 s** | 实测捏轴到报警 3.0 ~ 3.5 s，与预算吻合 |

**3.2 s 的窗长滞后是主动取舍**，不是缺陷：

- 窗越短，报警越快，但窗口均值的方差越大，正常抖动就越容易误报（板上实测 45 点正常数据的相似度标准差已达 9.8 分）；
- 窗越长，相似度越稳，但对突发异常的响应越慢。

在「轴承磨损、异物缠绕」这类**渐变型**异常上，3.5 s 完全可接受；对「敲击」这类毫秒级冲击则必然漏掉（见 9.1 局限）。

### 2.4 双通道输出

| 通道 | 载体 | 内容 | 是否依赖网络 |
|---|---|---|---|
| 本地 | OLED（SSD1315，128×64，I2C） | 转速 / 电流 / R / 相似度 / 状态 | 否 |
| 本地 | 报警灯（PF9，低电平点亮） | 报警时常亮 | 否 |
| 远程 | D1 mini 网页 | 全套数据 + AI 状态卡 | 是（同一 WiFi） |

OLED 也**不画实时曲线**，只显示数值。这是有意为之：128×64 的屏画 3.2 s 波形几乎不可读，且刷新会拖慢主循环；趋势由手机页面承担（页面内存历史点做迷你折线）。

### 3.4 转速测量：为什么是「四倍频 + 100 ms 窗口」

MG310 自带霍尔编码器标称 **13 ppr**（每转 13 个脉冲/相）。TIM4 配成 TI12 编码器模式，A/B 两相的上升沿与下降沿都计数，即**四倍频**；再乘减速比 20：

```
每转计数 = 13 × 4 × 20 = 1040 counts/圈
```

100 ms 窗口内的计数值 ΔCount 换算转速：

```
rpm = ΔCount / 1040 × 600 = ΔCount × 0.576923
```

所以一个计数单位对应 0.577 rpm，140 rpm 时 ΔCount ≈ 243 —— 量化误差约 0.4%，足够。

**为什么不用 M 法（固定时间测脉冲数）以外的方案**：T 法（测脉冲周期）在低速时精度高，但本项目转速稳定在 140 rpm 附近，M 法 100 ms 已足够，且实现简单、无需捕获中断。100 ms 窗口同时决定了特征推送节拍，与模型窗长天然对齐，不用额外做重采样。

### 3.5 母线电压测量

D153C 板上已有 10 k + 1 k 分压（比例 1/11），直接飞线到 PA4，无需自建分压电路——这是「零焊接」约束下的最优解。

```
VM = ADC_raw / 4095 × 3.3 × 11
```

分辨率：3.3 × 11 / 4095 ≈ **8.9 mV/LSB**。母线 10.8 V 时，1 LSB 的相对误差 0.08%，远小于转速的 0.4%，所以 R 的精度由转速侧主导。

### 3.6 电流测量（仅显示，不进模型）

ACS712-05B 是霍尔隔离型，输出零点 2.5 V、灵敏度 185 mV/A：

```
I = (Vout − 2.5) / 0.185    （单位 A）
```

零点漂移是霍尔传感器的通病，处理办法：**上电时电机不转，连采 64 次取平均作为零点基准**；运行中停机时用 α = 0.02 的一阶滤波缓慢跟踪零点，避免温漂累积。

**电流为什么不进模型**——这是第 3 代方案最重要的一次否决，详见 4.4。

### 3.7 供电与电流回路

```
3S 锂电 (11.1 V 标称, 12.6 V 满电)
   ├─ D153C VM  ──┬── H2-5 ──→ STM32 PA4（经板载 1/11 分压）
   │              └─ 板载 5 V ──→ 神舟号 VIN
   │                              ├─ 板载 3.3 V → STM32 / OLED
   │                              └─ 3.3 V → ACS712 VCC
   └─ D153C 输出 ── ACS712 串联 ──→ MG310
```

**电流模块必须串在「驱动输出」与「电机」之间**，不能串在电池总线上——否则测得的是「电机 + 驱动板静态损耗」，空载时会有一个几十 mA 的底数，把真实负载电流淹没掉。

### 3.8 硬件接线自查清单（每次上板前）

| 检查项 | 现象 | 根因 |
|---|---|---|
| STBY（PA8）是否拉高 | 电机一格不转，PWM 有波形 | D153C 未使能 |
| H2-2 → PB6、H2-1 → PB7 | 转速恒 0 | 编码器飞线没接 |
| H2-5 → PA4 | 母线显示 0 或 0.3 V | 分压飞线没接 |
| ACS712 是否在驱动输出侧 | 空载电流 60~80 mA 偏大 | 接到了电池总线 |
| 共地 | 数据乱跳、ADC 满量程 | STM32 / D153C / ACS712 未共地 |

## 4 核心决策：为什么收敛到单变量 R

本章是整个方案的技术核心，也是答辩时最能体现思考深度的部分。逻辑是四步：**先证明 19 维冗余 → 再排名单变量区分力 → 解释为什么排除加速度和电流 → 最后用电压归一化解决误报。**

### 4.1 第一步：19 维里有一大半是同一个东西换算法

对 19 维做相关分析，**|r| > 0.9 的冗余变量对有 20 对**：

| 变量对 | 相关系数 | 说明 |
|---|---|---|
| `current_mean_A` ~ `current_rms_A` | +0.995 | 均值与有效值，交流分量极小时必然重合 |
| `accel_x_mean_g` ~ `accel_x_rms_g` | −1.000 | 完全线性，只差一个符号 |
| `accel_x_mean_g` ~ `accel_z_rms_g` | +0.990 | 都是姿态投影 |
| `accel_x_mean_g` ~ `speed_mean_norm` | +0.952 | 都在反映负载 |
| `accel_x_variance_g2` ~ `accel_x_waveform_factor` | +1.000 | 波形因子 = RMS/均值，方差小时退化为线性 |

**结论：19 维的真实独立信息量远小于 19。** 这不是「砍掉有用特征」，而是「这 19 维本来就在重复表达同一件事」——这是对老师意见最直接的数据支撑。

### 4.2 第二步：单变量区分力排名

判据的选择很关键。不能只看「两类均值差多少」，因为跨批次会失效；要看**正常批与异常批的均值区间是否真的不重叠**，再折算成「相当于几个批内标准差」。

数据：9 批独立采集（6 批正常 + 3 批负载异常，共 3252 窗）+ 1 批低电量对照（182 窗）。

| 排名 | 变量 | 正常 6 批均值范围 | 异常 3 批均值范围 | 区间间隙 | 相当于几个批内 sd | 判定 |
|---|---|---|---|---|---|---|
| 1 | `speed_mean_norm`（转速） | 0.2941 ~ 0.3004 | 0.2391 ~ 0.2449 | +0.0492 | **26.9** | 完全分开 |
| 2 | `accel_z_rms_g`（Z 轴振动） | 0.2557 ~ 0.2739 | 0.1459 ~ 0.1877 | +0.0680 | 18.3 | 完全分开但见 4.3 |
| 3 | `accel_x_mean_g` | −0.9221 ~ −0.9160 | −0.9462 ~ −0.9383 | +0.0162 | 9.3 | 同上 |
| 4 | `accel_x_rms_g` | 0.9161 ~ 0.9223 | 0.9383 ~ 0.9463 | +0.0160 | 8.9 | 同上 |
| 5 | `accel_y_mean_g` | −0.0420 ~ −0.0405 | −0.0494 ~ −0.0489 | +0.0069 | 7.1 | 同上 |
| 6 | `speed_std_norm`（转速波动） | 0.00045 ~ 0.00057 | 0.00139 ~ 0.00212 | +0.00082 | 3.3 | 可用 |
| 7 | `current_mean_A`（电流） | 0.0784 ~ 0.0889 | 0.0975 ~ 0.1104 | +0.0086 | **0.93** | 勉强 |
| 8~19 | 其余 12 维 | — | — | ≤ 0.63 | ≤ 0.63 | 单变量不可用 |

**转速以 26.9 个标准差的分离度排第一，是电流（0.93）的 29 倍。**

### 4.3 为什么不选加速度（哪怕它也是 100% 分开）

`accel_x_mean_g` 能从 −0.921 变到 −0.946，差 0.025 g。**这不是故障特征，这是传感器倾角变了 1.5 度。**

0.025 g / 1 g = 2.5%，对应姿态角约 1.4°。也就是说：只要安装时手抖一下、垫片厚 0.2 mm、桌面不平，这个「特征」就完全变了，而电机其实好好的。

同理 `accel_z_rms_g` 从 0.257 掉到 0.166（−36%），主要也是振动传导路径变了（不同批次摆放位置、垫材不同），不是电机状态。

**这类特征在实验室看着很漂亮（100% 分离），一换安装就是灾难。** 答辩时一定会被问「你换个人装还准吗」，答不上来。

还有一条工程上的硬理由：MPU6050 已于 2026-10-19 摘除（姿态类特征正是第 1、2 代方案失效的主因之一），现在物理上就没有这条路。

### 4.4 为什么不选电流（看着最符合物理，实测最差）

物理上讲得通：负载 ↑ → 电流 ↑。实测也确实升了（0.082 → 0.105 A，+27%）。

但**正常批之间的电流差异（0.0784 ~ 0.0889，跨度 13%）几乎和正常→异常的差（+27% 的一半）一个量级**，区间间隙只有 0.93 个批内标准差。原因：电流对摩擦、装配、温漂、电源纹波都敏感；而转速由电压和负载决定，摩擦已经被包含在负载里，又被减速比和反电动势压住了。

另一条更硬的证据来自 20 kHz 波形分析：`fastcap.c` 采到的电流波形与故障状态的相关性只有 **0.0106**，即波形里学不到信息（详见 5.4）。

**结论：电流适合做辅助显示，不适合做唯一判据。**

### 4.5 关键发现：不做电压归一化，会大面积误报

这是本方案最重要的一条，也是「想过」的证明。

手头有一批 `controlled_vibration_20261008_tabletop02_test` 数据（182 窗），母线只有 **9.85 V**（正常批是 11.1 V），但电机本身工作正常。

用**裸转速**判断：

| 指标 | 正常 6 批 | 该批（低电量，正常） |
|---|---|---|
| 转速均值 | 147.2 rpm | 121.8 rpm |
| 与正常批差异 | — | **−17.2%** |
| 若阈值设在 130 rpm | 0% 误报 | **100% 误报** |

**电压掉了 11%，转速跟着掉 17%，看起来和「负载异常」一模一样。**

归一化之后：

| 数据 | 母线电压 | 转速 | `rpm/V` | 判定 |
|---|---|---|---|---|
| 正常 6 批 | 11.09 V | 147.2 rpm | **13.23 ~ 13.53** | 正常 ✓ |
| 低电量批（工作正常） | 9.85 V | 121.8 rpm | **12.37** | 正常 ✓ |
| 负载异常 3 批 | 11.07 V | 121.0 rpm | **10.79 ~ 11.07** | 异常 ✓ |

三者被干净地分成三段。**除以电压这一步，把「电池没电」和「电机带载异常」彻底分开了。**

于是得到最终特征：

```
        rpm   （转速，编码器 TIM4 四倍频 1040 counts/圈）
R = ─────────
        V     （母线电压，ADC1_IN4，板载 1/11 分压）
```

单位 `rpm/V`，量纲上是「每伏能跑多少转」，物理含义是**单位电压下的机械负载能力**。

> 诚实的说明：当年那批「轻敲能分开」的结论，很可能是被这 11% 的电压差带出来的，不完全是敲击本身的贡献。论文里如果引用那批数据，必须注明电压条件不同。

### 4.6 阈值标定

#### 4.6.1 离线阈值扫描

| 阈值 T（`rpm/V` < T 判异常） | 正常 6 批误报率 | 异常 3 批检出率 | 低电量批误报率 |
|---|---|---|---|
| 12.6 | 0.00% | 100.00% | **100.0%** |
| 12.4 | 0.00% | 100.00% | 89.6% |
| **12.2** | 0.00% | 100.00% | 0.0% |
| **12.0** | **0.00%** | **100.00%** | **0.0%** |
| 11.8 | 0.00% | 100.00% | 0.0% |
| 11.6 | 0.00% | 100.00% | 0.0% |
| 11.4 | 0.00% | 97.84% | 0.0% |
| 11.2 | 0.00% | 90.57% | 0.0% |
| 11.0 | 0.00% | 67.30% | 0.0% |

**可用区间 11.6 ~ 12.2，取中点 12.0。** 裕量核算（阈值 12.0）：

- 距正常批单窗最低值 13.09：**+8.3%**
- 距异常批单窗最高值 11.55：**−3.9%**
- 距低电量批 12.37：**+3.1%**

三边都有余量，不是贴着边界切的。

#### 4.6.2 相对基线写法

绝对值 12.0 是这一台电机、这一套机械结构的数，换电机要重标定。更稳的做法是上电学习基线：

```
学习阶段（约 10 秒，电机在目标工况下运转）
    R0 = 学习窗内 R 的均值
参考阈值
    ALARM_TH = 0.90 × R0        // 允许下降 10%
```

实测 R0 ≈ 13.3 → 阈值 11.97，与绝对阈值 12.0 一致，但具备了自适应性。

#### 4.6.3 板上阈值必须重新标定（重要教训）

离线算出的可用区间 11.6~12.2 只是**参考**。板上实测发现：

| 场景 | 离线结论 | 板上实测 |
|---|---|---|
| 正常时相似度下限 | 60 | **44** |
| 相似度标准差 | — | **9.8** |
| 捏轴时相似度上限 | 20 | 16（过渡点） |

板上抖动比离线大得多（整台机器在振，3.2 s 窗均值的方差被放大）。按离线结论取阈值 48，板上 45 个正常点里就有 1 次跌破并真的触发了报警——**这是误报**。

最终取 **32**（正常下限 44 与异常上限 16 的中点略偏保守侧，两侧余量 12 分与 16 分）。**离线结果只能用来定窗长和学习次数，阈值必须以板上分布为准。** 这句话适合直接写进论文。

## 5 边缘 AI 方案

### 5.1 为什么仍然要用模型，而不是纯阈值

单变量 R 加一个固定阈值（12.0）在离线数据上已经做到 0% 误报 / 100% 检出。那还需要 AI 吗？需要，理由有两条，都不是「为了用 AI 而用 AI」。

**理由一：阈值是静态的，模型能在线自适应。**

实测量化：电机连续跑 5 分钟后，摩擦变小，同占空比下转速从 139.6 升到 142.5（+2%），R 随之升高约 2%，基线是在冷机上学到的，于是相似度从 100 掉到 67~75。

| 阶段 | rpm | 母线 | R | 相似度 |
|---|---|---|---|---|
| 冷机（刚学完） | 139.6 ~ 140.8 | 10.85 V | 12.87 ~ 12.96 | 100 |
| 热机（5 分钟后） | 142.5 ~ 143.1 | 10.85 V | 13.05 ~ 13.24 | 67 ~ 75 |

固定阈值 12.0 当然也能分开正常与异常，但**它无法跟着温升移动**；而模型配合周期重学习（10 分钟一次），会自动把基线刷新到当前工况——实测 32 分钟内自动重学了 3 轮，相似度每次都回到 100，全程零人工干预。

**理由二：相似度是连续量，不是二值。**

阈值只能回答「是/否」，模型还给出「偏离了多少」。这在实测里很有用：捏到 103 rpm 时相似度 53（未报警）、85 rpm 时 24（报警）、78 rpm 时 0（报警）——三次实验的点落在一条单调曲线上，说明判别力充足，只是阈值设得偏保守。如果只有阈值输出，就看不到这条曲线，也就没法回答「还有多少余量」。

**代价是诚实的**：模型比阈值多花 40 B Flash 和 56 B RAM，多 5 ms 推理时间，多一套重学习状态机。这个代价在 F407 上可以忽略，换来的是自适应能力和可解释的连续量，值得。

### 5.3 库内算法链路

ZSM 模型只有 40 B Flash，它做的事非常轻：

```
32 个 R 值
   │
   ├─ ① mean 池化 5%  ──→  32 个点压成 1 个均值（13.33）
   │      池化比例 5%、n_windows = 1，所以输出正好 1 个数
   │      作用：把 3.2 s 内的抖动平均掉，留下这一窗的「水平」
   │
   ├─ ② Z-score 归一化  ──→  z = (x − 13.3305) / 0.10655
   │      用学习阶段统计出来的均值和标准差
   │
   └─ ③ 判定  ──→  |z_mean| > 1.206  →  相似度下降
                   |z_max|  > 3.0    →  相似度归 0
```

模型参数（`artifacts/zsm_model_params.json` 实测导出）：

```json
{
  "signal_len": 32, "dimension": 1, "input_size": 1,
  "sensitivity": 1.0, "threshold_ratio": 1.45,
  "z_mean_factor": 0.07, "z_max_factor": 0.41,
  "minimal_learning_calls": 2, "learning_call_cnt": 500,
  "mean": [13.330528259277344],
  "std":  [0.10655135661363602],
  "z_mean_threshold": 1.2061256170272827,
  "z_max_threshold": 3.0,
  "m_cv": 498
}
```

**`mean` 和 `std` 是长度为 1 的数组**——这是「单一变量」最硬的证据：模型按变量存归一化参数，有几个变量就有几个数。

所以模型实际「看」的是一个标量：这一窗的 R 均值离基线多少个 σ。正常 R 在 13.33 上下、σ 只有 0.107；捏轴掉到 10.93，是 **−22 σ**，不可能漏。

> **对答辩的意义**：被问「你的 AI 到底学到了什么」时，可以如实回答「学到了正常工况下 R 的均值与标准差，判定的是这一窗偏离基线多少个 σ」。这比说「AI 学到了特征分布」要实在得多，也不怕追问。

### 5.4 为什么选 44 号 ZSM 而不选 43 号 MML

这是模型选型的核心取舍，实测对比：

| 指标 | 43 号（MML） | **44 号（ZSM，采用）** |
|---|---|---|
| RAM 占用 | 1564 B | **56 B** |
| Flash 占用 | 约 8 KB | **40 B** |
| 达到精度所需学习窗数 | **130 窗** | **16 窗（工程用 64）** |
| 上电到进入检测 | **约 7 分钟** | **约 9.6 秒** |
| 推理耗时 | 数十 ms | < 5 ms |

**决定性因素是学习耗时。** MML 要 130 个窗才能收敛，按 100 ms 一窗算就是 13 s 数据，但它的学习是「每窗多次迭代」，实测总耗时约 7 分钟——对毕设演示是灾难（每次上电都要等 7 分钟才看到 DET）。ZSM 学习 64 窗只要 6.4 s，上电 10 秒内进入检测，观众能当场看到全过程。

**MML 的优势（本项目用不上）**：在多变量、非线性、有形状信息的信号上判别力更强。而本方案的信号是单变量标量，形状自相关实测 ≈ 0（见下表），MML 的建模能力无处发挥。

**为什么单变量下「形状」不可学**——这在做方案选择时必须先确认，否则会误以为可以照搬时序模型的套路：

| 信号 | 窗口 | 正常批形状自相关 | 异常批形状自相关 |
|---|---|---|---|
| `rpm/V`（100 ms/点） | 16 点 = 1.6 s | −0.005 ~ +0.002 | −0.006 ~ −0.005 |
| `accel_z_mg` | 64 点 = 1.28 s | −0.005 ~ +0.008 | −0.002 ~ 0.000 |
| `current_mA` | 64 点 = 1.28 s | −0.002 ~ +0.002 | −0.002 ~ +0.004 |

全部 ≈ 0，说明每窗形状互不相关，就是随机噪声，AI 学不到形状信息。原因有两个：**欠采样**（电机振动主频几十到几百 Hz，100 ms 采样必然混叠）和**已被平滑**（rpm 本身就是 100 ms 计数值）。

**这条结论直接排除了「1 轴 × 200 点 20 kHz 电流波形」那条路线**（原方案里的路线 C）：`fastcap.c` 的 20 kHz 电流波形理论上形状里有信息，但实测电流与故障的相关性只有 0.0106，波形里没有可用判别信息，接了模型也学不出东西。所以最终放弃，`fastcap.c` 保留在工程里但未接入主循环。

### 5.5 数据集构造

三份 CSV 在 `output\单变量分析_20261019\nanoedge_r32\`：

| 文件 | 用途 | 样本数（行） | 每行列数 | 数值范围 | 均值 |
|---|---|---|---|---|---|
| `R32_regular_normal.csv` | 正常，训练用 | 1000 | **32** | 13.029 ~ 13.839 | 13.336 |
| `R32_abnormal_grip.csv` | 捏轴异常，训练用 | 500 | **32** | 10.225 ~ 11.669 | 10.927 |
| `R32_test_normal_batch06.csv` | 正常第 6 批，独立测试 | 569 | **32** | 13.078 ~ 13.521 | 13.287 |

「每行列数」是逐行统计的：**2000 多行全部是 32 个浮点数，无表头、无标签列，一个例外都没有。**

**异常类是怎么做出来的**：只改一个条件——用手捏住电机输出轴，人为加载。采样通道、量程、窗长（32 点 × 100 ms = 3.2 s）、stride（1 点）全部不变。

| 项目 | 正常类 | 异常类 |
|---|---|---|
| 物理动作 | 空载运转 | 捏轴加载 |
| 采样信号 | R = rpm/V | R = rpm/V（同一个） |
| 窗长 | 32 点 | 32 点 |
| 特征维度 | 1 | 1 |

这是单变量异常检测的标准做法：**变量不变、工况变**。如果两个类连变量都不一样，那就不是异常检测而是分类任务了。

数据导出脚本：`output\单变量分析_20261019\export_r32_for_studio.py`（从原始遥测 CSV 按 32 点滑窗导出，stride = 1）。

### 5.6 模型部署流程

从 PC 到 MCU 共五步，每步都有产物可核对：

```
① 采数据       wave_dump 固件 + 串口脚本 → 原始 CSV（每批 30 s）
                    ↓
② 造样本       export_r32_for_studio.py → R32_*.csv（每行 32 个 R）
                    ↓
③ 训模型       NanoEdge Studio（关 Detrend）→ result_id 44 / ZSM
                    ↓
④ 导库包       libneai.a + NanoEdgeAI.h + artifacts/*.json
                    ↓

```

### 6.3 `feature_r.c`：只做三件事

这个模块是整个数据通路的第一环，逻辑非常短（217 行，含注释），核心只有一个除法和一个滑窗。

**参数（改了就得重新导训练数据并重刷模型）**：

```c
#define FEATURE_R_WINDOW        32U     /* 窗口点数 = 模型输入长度 */
#define FEATURE_R_PUSH_MS       100U    /* 推点周期，与编码器采样周期一致 */
#define FEATURE_R_RPM_MIN       20.0f   /* 低于此转速视为停转 */
#define FEATURE_R_VBAT_MIN      1.0f    /* 低于此电压视为分压通路失效 */
```

窗长 32 × 100 ms = **3.2 s**，与模型 `signal_len = 32` 严格一致。

**处理流程（`feature_r_tick`，每 10 ms 调一次）**：

```
① 判有效运行状态
     电压无效 / 电压 < 1.0 V / 转速 < 20 rpm  →  丢窗（不是只不推点）+ 清屏显有效位
     为什么丢窗：重新转起来时窗口里混着停机前的数据，相似度就是错的
② 算 R = rpm / vbat_v，更新屏显瞬时值
③ 按 100 ms 节拍推点
     窗口未满：追加到末尾
     窗口已满：整体左移一位，丢掉最旧点（新点落末尾）
```

**两个容易被忽略的细节**：

1. **节拍对齐用 `s_lastPushMs = now_ms` 而不是累加**。累加会在主循环偶尔延时后补推一串点，把窗口挤爆；对齐到当前时刻则「丢点不补」，窗口时间跨度始终是 3.2 s。
2. **时间差用无符号减法** `(uint32_t)(now_ms - s_lastPushMs)`，天然抗 32 位回绕（约 49.7 天一次），不需要额外的回绕判断。

**为什么不在滑窗里做重采样**：推点节拍（100 ms）与编码器采样周期完全同源，天然对齐，不需要插值或抽取。这是设计上刻意省掉的一层复杂度。

### 6.4 `ai_monitor.c`：状态机与常量依据

#### 6.4.1 四个阶段

```c
typedef enum {
    AI_MONITOR_OFF       = 0,  /* 未启用（采集模式） */
    AI_MONITOR_LEARNING  = 1,  /* 现场学习 */
    AI_MONITOR_DETECTING = 2,  /* 持续检测 */
    AI_MONITOR_ERROR     = 3   /* 初始化失败或调用报错 */
} AiMonitorPhase;
```

枚举值必须与 M2 协议里的 `M2_AI_*` 一一对应，不能随意改数字——D1 页面按这个字节显示状态。

#### 6.4.2 检测分支流程

```
窗未满 32 点  →  清结果、清报警、返回（绝不拿半窗判异常）
学习未满 64 窗 →  neai_learn(窗)；计数 +1；不做检测
学习已满      →  neai_detect(窗, &similarity)
                 ↓
         sim < 32  →  lowRun++ / highRun=0；lowRun ≥ 2 → alarm = 1
         sim ≥ 32  →  highRun++ / lowRun=0；highRun ≥ 2 → alarm = 0
                 ↓
         sim ≥ 20  →  detectCount++；≥ 6000 → 重学（g_learned = 0）
```

**注意「窗未满就清报警」这一条**：看起来反直觉（正在报警怎么反而清掉），但它是必要的——窗口被清空说明电机停过或电压失效，此时的数据不足以支撑任何结论，报一个「不知道」比报「正常」或「报警」都安全。实际使用中，报警状态下停机属于人为干预，清报警是符合预期的。

#### 6.4.3 常量表与取值依据

这是全套参数，**每一个都标了依据，答辩可直接引用**：

| 常量 | 值 | 依据 |
|---|---|---|
| `AI_MONITOR_THRESHOLD` | **32** | 板上：正常下限 44 / 异常上限 16，取中点略偏保守侧，两侧余量 12 与 16 分 |
| `AI_MONITOR_LEARN_WINDOWS` | **64** | 同一批数据只改学习窗数：16 窗正常最低 54、64 窗 60 且独立批 91；64 窗两方向余量最均衡 |
| `AI_MONITOR_ALARM_WINDOWS` | **2** | 抗单点抖动，200 ms 内触发 |
| `AI_MONITOR_CLEAR_WINDOWS` | **2** | 松开后 0.4 s 内自动解除 |
| `AI_MONITOR_RELEARN_DETECTS` | **6000** | 100 ms 一次检测，约 10 分钟，用于跟随温升漂移 |
| `AI_MONITOR_RELEARN_MIN_SIM` | **20** | 真故障实测 ≤ 16、正常 ≥ 44，20 卡在中间：挡得住真故障，不挡工况漂移 |
| `AI_MONITOR_STOP_TICKS` | **50** | 0.5 s 停机即重学基线；比重新攒窗的 3.2 s 短得多，又足以避开转速瞬时跌破 20 rpm |

**为什么学习窗数取 64 而不是库声明的 16**：16 是模型达到标称精度所需的最少次数，但实测它正好落在精度拐点上——正常侧最低分只有 54，离阈值只剩 6 分余量，工况略漂就误报。同一批数据、同一份库，只改学习窗数的对比：

| 学习窗数 | 正常最低分 | 捏轴最高分 | 独立批最低分 |
|---|---|---|---|
| 12 | 19（未学稳，不可用） | — | — |
| 16 | 54 | 1 | 64 |
| 32 | 64 | 37 | 91 |
| **64（采用）** | **60** | **20** | **91** |
| 96 | 58 | 9 | — |

64 窗在两个方向上余量最均衡，且**没参与训练的独立批最低分从 16 窗的 64 提到 91**，跨工况泛化明显更好。耗时 3.2 + 6.4 = 9.6 s，上电约 10 秒进入检测。

#### 6.4.4 周期重学习的死锁修复（重要教训）

初版把累计条件写成 `if (g_alarm == 0U)`，本意是「报警时别把异常学成正常」。实际后果是死锁：

```
工况整体漂移 → 相似度长期偏低 → 报警不解除 → 重学习永不触发
             → 基线永不更新 → 再也回不来
```

实测证据：`g_detectCount` 冻结在 2428、`g_learned` 一直是 64，跑多久都不重学。

改成用相似度本身来挡：

```c
/* 原来：报警就完全不累计，会死锁 */
if (g_alarm == 0U)

/* 现在：只有落在硬故障区间才拒绝重学 */
if (g_similarity >= AI_MONITOR_RELEARN_MIN_SIM)   /* 20 */
```

`RELEARN_MIN_SIM` 取 20 的依据：捏轴实测相似度全程 0（只在过渡点出现 16），正常侧最低 44。20 正好卡在两者之间——**挡得住真故障，又不挡工况漂移**。报警去抖仍由 `ALARM_WINDOWS` 负责，两者各管一件事。

#### 6.4.5 停机重学：写在主循环里，不能写进 tick

新增 `ai_monitor_notify_stopped()`，由 `main.c` 的 10 ms 块在 `d.speed_rpm < 20.0f` 时调用，连续 50 拍就 `g_learned = 0`、`g_phase = LEARNING`。换负载、换工况、换电池后不用断电，停一下再起转就按新工况重学。

**踩过的坑**：第一版把它写进 `ai_monitor_tick()` 的「窗未满」分支，实测完全无效（停机 1.5 s 后 `g_learned` 仍是 64）。原因：`main.c` 只在 `feature_r_tick()` 返回 1 时才调 `ai_monitor_tick()`，而 `feature_r_tick()` 在 `rpm < 20` 时直接 `return 0U`——**停机时那个函数根本不会被调用**。

**教训：判断「停机」不能写在只有运行中才被调用的函数里，必须由主循环主动通知。** 这条适合写进论文的「工程实践」小节。

### 6.5 `main.c`：三个节拍

系统没有 RTOS，靠一个节拍器分三档：

| 节拍 | 周期 | 内容 |
|---|---|---|
| 1 ms | 中断（SysTick + TIM7） | 时基递增、按键扫描消抖 |
| 10 ms | 主循环判时 | 读转速 / 母线 / 电流 → `feature_r_tick()`；`rpm < 20` 时调 `ai_monitor_notify_stopped()` |
| 100 ms | 由 `feature_r_tick()` 返回 1 触发 | `ai_monitor_tick()` → 更新 `UI_Data` → `Telemetry_Tick()` |

关键连接（三行，是整个 AI 通路的枢纽）：

```c
if (feature_r_tick(d.speed_rpm, vbat, vbat_valid, now_ms) != 0U)
{
    ai_monitor_tick();          /* 只有真的推了新点才检测，天然限频到 10 Hz */
}
```

这个写法有两个好处：AI 检测频率自动绑定 100 ms 节拍，不用单独定时；窗未满时 `ai_monitor_tick()` 内部的闸门会拦住，不会空转浪费算力。

**初始化顺序不可乱**：`Key_Init()` 必须排在 `Tim7_Init()` 之前，否则按键中断触发时 GPIO 还没配好，会造成档位卡死（历史故障，已修复）。

### 6.6 `ui.c`：四行布局

```
页 0~1   Spd  xxxxx  rpm        <- 转速（大字号 F8x16）
页 2~3   Cur  x.xx   A          <- 电流（大字号）
页 4~5   （保留区）              <- 原振动行，留给后续使用
页 6     Bat 10.8V S: 100 ALARM  <- 母线电压 + 相似度 + 状态（F6x8 小字号）
页 7     DET L1:58%  T 1234s |  <- 阶段 + 档位 + 运行秒数 + 心跳
```

状态行是信息密度最高的一行，列坐标经过逐像素核对：

| 词 | 列范围 |
|---|---|
| `Bat` | 0 ~ 17 |
| `10.8` | 24 ~ 47 |
| `V` | 48 ~ 53 |
| `S:` | 60 ~ 71 |
| `100` | 72 ~ 89 |
| `ALARM`（5 字定宽） | 92 ~ 121 |

最后一个像素落在第 121 列，屏宽 128，**余量 6 列**，不出屏；54~59 这 6 列墨点数为 0，确认是真空格（`10.8V` 和 `S:` 不会粘成一体）。

核对方法不是靠肉眼估，而是把 `font.h` 里的 `F6x8` 表解析出来，按 `OLED_ShowString` 的规则（字符宽 6 px、bit0 为最上一行）逐像素重排，脚本在 `output\上板实测_20261019\render_oled_row.py`。**以后挪坐标前先跑这个脚本验证。**

### 6.7 `telemetry.c` + M2 协议

USART3，57600 8N1，10 Hz，42 字节定长二进制帧：

```
[0]=0xA5 [1]=0x5A  帧头
[2]=0x01           协议版本
[3]=36             载荷长度
[4..7]   seq       帧序号
[8..11]  uptimeMs  开机毫秒
[12]     level     档位 0/1
[13]     duty      占空比百分数
[14]     validMask 有效位
[15]     aiState   bit0~1 阶段，bit2 报警
[16..39] value[6]  6 个 int32（小端）：电流mA / 加速度X,Y,Z mg / 转速×10 / 母线mV
[40..41] CRC       CCITT-FALSE，覆盖 [2] 起 38 字节
```

**有效位 `validMask` 的现状（必须以代码为准）**：

| 位 | 含义 | 现状 |
|---|---|---|
| bit0 | 电流 | 有效（需主电源接通） |
| bit1~3 | 加速度 X/Y/Z | **恒为 0**（MPU6050 已摘除） |
| bit4 | 转速 | 有效 |
| bit5 | 母线电压 | 有效 |

实际满值 = `0x31` = 49，不是宏里的 `M2_VALID_ALL = 0x3F`。**`M2_VALID_ALL` 是历史定义（6 路全有效），现固件永远不会达到该值**——这个认知错误曾在 D1 页面上造成「部分测量无效」永久误报，详见 6.8。

帧结构保持不变（仍是 42 字节、6 个槽位），只为兼容旧接收端；加速度三槽不再写入。

**CRC 为何不覆盖帧头**：帧头用于重新同步，一旦与 CRC 绑定，接收端在错位状态下无法用帧头定位，重同步会变慢。这是流式协议的常规做法。

### 6.8 `firmware_d1mini`：网关与手机页面

| 文件 | 职责 | 体积 |
|---|---|---|
| `d1mini_telemetry.ino` | 主程序：串口收帧、WiFi、HTTP 服务 | 58 KB（含注释） |

**页面为什么嵌在固件里**：ESP8266 没有文件系统可依赖（SPIFFS 会磨损且首次需烧录两遍），把 12.5 KB 的 HTML 放在 PROGMEM 里由 `server.send_P()` 直出，最省事也最稳。代价是改页面必须重烧固件，但页面本来就很少改。

**页面内容（第 3 代重写）**：

- **删掉** X/Y/Z 三轴加速度格子（物理上永远无数据）
- **新增** 「特征比值 R」格子（`R = rpm × 100 / battery_mV`）
- **AI 主卡六态**：`ok`（绿）/ `learn`（琥珀）/ `alarm`（红 + 呼吸动画）/ `idle` / `off` / `err`
- **暗色/亮色自动适配**：CSS 变量 + `prefers-color-scheme`

**「部分测量无效」误报的根因与修复（值得记录的排查过程）**：

页面底部原来有一条橙色提示，一直在显示。旧代码的判断是：

```js
if (d.feature_valid_mask !== 63) { showWarning('部分测量无效'); }
```

`63 = 0x3F` 是「6 路全有效」，但 STM32 实际只置 bit0/4/5 = `0x31` = 49，因此**条件恒成立，提示永久显示，与硬件健康无关**。这是结构性误报。

改成按通道分别判断：

```js
var miss=[], mask=d.feature_valid_mask;
if((mask&CH_CURRENT)===0){miss.push('电流');}
if((mask&CH_SPEED)===0){miss.push('转速');}
if((mask&CH_BUS)===0){miss.push('母线电压');}
if(miss.length>0){el('cond').textContent='未采到：'+miss.join(' / ')+'（检查对应接线）';}
```

修复后提示会精确到通道。实测宝子当时板子只接了逻辑电源，`valid_mask` 为 16（只有转速位），页面正确显示「未采到：电流 / 母线电压（检查对应接线）」——**这是真实缺路，不是误报**，接上主电源与分压飞线后会自动消失。

**这个对比很适合写进论文**：同一个界面提示，改前是「永远亮、无信息量」，改后是「只在真缺路时亮、且指出缺哪一路」。前者是 bug，后者是诊断。

### 7.2 学习阶段（冷机启动）

| t=22.14 | 76.7 | 7.12 | 10.78 | 20 | **1** | 3 | **报警触发**，距跌破阈值约 0.2 s |
| t=22.89~23.84 | 76~82 | 7.1~7.8 | 10.74 | **0** | 1 | 11~20 | 相似度打满 0 分，连续 6 个采样点 |

1. **报警路径完全正常**。相似度从 100 单调降到 0，跌破 32 后 2 个窗（`ALARM_WINDOWS = 2`）触发 ALARM，无需外部干预。

3. **阈值折合的转速门槛约为基准的 59%**。
4. **R 的归一化设计得到验证**。三次捏轴过程中母线电压始终在 10.74~10.86 V 之间（波动 1.1%），而 R 从 13.8 掉到 6.2 —— **R 的下降 100% 来自转速，电压没有参与**。这正是 `R = rpm / V` 相对「直接看转速」的核心价值：换一块电量不同的电池，转速会整体平移但 R 保持稳定。

### 7.5 判据边界：负载掉多少才报警

三次捏轴，力度依次加重，把边界量了出来：

| 捏到转速 | 相对基准 | 最低 R | 最低相似度 | 是否报警 |
|---|---|---|---|---|
| 103 rpm | −28% | 9.59 | **53** | 否 |
| 85 rpm | −41% | 8.14 | **24** | **是** |
| 78 rpm | −46% | 7.28 | **0** | **是** |

三个点的相似度随 R 单调下降（R 9.59→sim 53、R 8.14→sim 24、R 7.28→sim 0），说明**判别力充足，只是阈值设得偏保守**：负载下降 30% 以内不会报警。对「避免误报」是好事，对「及早发现卡滞」偏迟钝，属可调参数。

如果现场应用要求更早发现，把 `AI_MONITOR_THRESHOLD` 从 32 调到 45 左右即可（正常下限 44 之上会误报，所以 44 是上限），代价是误报率上升。**这个权衡关系应写进论文的讨论部分**，比单纯说「准确率 100%」更有说服力。

### 7.6 冷机 → 热机的基线漂移

连续跑 5 分钟后，工况稳定但相似度落在 **67 ~ 75**，不再回到 100：

| 阶段 | rpm | 母线 | R | 相似度 |
|---|---|---|---|---|
| 冷机（刚学完） | 139.6 ~ 140.8 | 10.85 V | 12.87 ~ 12.96 | 100 |
| 热机（跑 5 分钟后） | 142.5 ~ 143.1 | 10.85 V | 13.05 ~ 13.24 | 67 ~ 75 |

**原因**：电机跑热后摩擦变小，同占空比下转速从 139.6 升到 142.5（+2%），R 随之升高约 2%。基线是在冷机上学到的，所以热机后偏离了约 2 个标准差。**母线电压没变（10.85 V 稳定），漂移来自转速侧，不是电量侧。**

**这不是漂移失控**：50 秒连续采样显示相似度在 67~75 之间来回摆，没有继续下滑。热机状态相似度 67~75、阈值 32，余量 35 分以上；捏轴时 0~16，余量 16 分以上，两侧都比较宽，**阈值 32 不需要改**。

**应对机制**：`RELEARN_DETECTS = 6000`（约 10 分钟）会触发周期重学习，把基线重新对齐到当前热机工况，相似度回到 100。

### 7.10 遗留的物理问题（必须写进论文）

模型对 R 的容差只有约 ±2%（σ 被压得极小），而**机械负载会自己在 150 ↔ 216 rpm 之间跳**（同一 58% 占空比下，两次采集分别稳定在 150 rpm 和 216 rpm，R 随之 13.9 ↔ 20~23.5）。

关键判据：**rpm 216 是真的**。编码器干净、电压干净、段内极稳，说明负载掉了约 30%，R 跟着变 47%，模型判异常**在逻辑上是对的**——这不是误报，是工况真的变了。

软件侧现在有「停机 0.5 s 再起转自动重学」兜底，但**根本解法是把电机 / 轮子固定住，别让负载变**。

答辩时这一点可以直接讲成「工况漂移下的在线自适应」，反而是加分项：先诚实承认问题，再展示两层应对（周期重学 + 停机重学），比声称「系统完美」可信得多。

### 8.3 三个教训（为什么 19 维失败）

**教训一：喂了 8 列常数。** 19 维里有 8 维是振动特征，而 MPU6050 已摘除，等于喂了 8 列 0 给模型。维度一多，每一维的 σ 都被噪声撑大，判别边界反而变模糊。

**教训二：冗余维度不是「更多信息」，是「更多噪声」。** 20 对变量 |r| > 0.9 说明 19 维的真实独立信息量远小于 19。把同一件事用 5 种算法各算一遍，只会让模型误以为这 5 个维度都重要。

**教训三：不做归一化，物理量之间会互相遮盖。** 裸转速下「负载降 17%」与「电量降 11%」完全重叠，这是 19 维方案里即使有转速维度也判不准的直接原因。除以电压之后才分开。

三条合起来，恰好是对老师意见的完整回答：**不是我们认为 19 维太多所以要砍，而是数据证明 19 维里有 18 维在重复同一件事。**

## 9 局限与后续工作

### 9.1 方案的边界（必须写进论文）

1. **只能检测「负载类」异常。** 转速对负载敏感，对突然的冲击不敏感——冲击持续时间 < 1 个窗口（3.2 s）时可能漏掉。轴承磨损、异物缠绕、卡滞、堵转属于能检的范围。
2. **只覆盖 1 档 58% 占空比。** 档位变化时 R 会变，必须按档位分别学习基线。当前固件只有 0 与 1 两档，0 档停转不检测，不冲突；若扩展到多档，需为每档维护一套基线。
3. **不能定位故障类型。** 单变量只能回答「有没有异常」，不能回答「是轴承还是绕组」。要进一步定位必须回到多变量或频域分析。
4. **样本量有限。** 3 批异常数据都是「手捏紧」模拟，不是真实的轴承磨损 / 绕组短路。论文必须写明「以外部加载模拟负载异常」。
5. **低电量批只有 1 批。** 归一化有效性还需要在更宽电压范围（9.0 ~ 12.6 V）再采 2~3 批确认。
6. **报警有 3.2 s 固有滞后。** 这是窗长的代价，已量化（2.3 节）。

### 9.2 后续可做（按性价比排序）

| 优先级 | 内容 | 价值 | 成本 |
|---|---|---|---|
| 高 | 固定电机安装（消除负载自跳） | 直接解决 7.10 的遗留问题 | 低（机械件） |
| 高 | 补采 2~3 批不同电量数据 | 让归一化结论更硬 | 中（约 2 小时） |
| 中 | 多档位各学一套基线 | 扩展适用范围 | 中 |
| 中 | 真实故障样本（拆轴承、加异物） | 从「模拟异常」升级到「真实故障」 | 高（需损坏件） |

## 10 答辩要点

### 10.1 三个必答题

**Q1：老师让你用单变量，那你为什么还要用 AI？直接设个阈值不就行了？**

A：阈值能分开离线的两类数据，但有两个它做不到的事。第一，阈值是静态的，而电机跑热后转速会升 2%，R 跟着升 2%，静态阈值会一直往误报方向偏；模型配合 10 分钟周期重学习，实测 32 分钟内自动重学 3 轮，全程零人工干预，相似度每次都回到 100。第二，阈值只给「是/否」，模型还给出连续相似度——实测捏到 103 rpm 时相似度 53、85 rpm 时 24、78 rpm 时 0，这条单调曲线能告诉我还剩多少余量，这是阈值给不出的。

**Q2：只有一台电机、9 批数据，100% 检出是不是过拟合？**

A：阈值只用了 1 个参数，且阈值两侧各有 3.9% 和 8.3% 的裕量，可用区间宽达 11.6~12.2。另外做了留一批验证：任意剔除 1 批正常数据，剩余 5 批定的阈值仍能正确分类留出批。参数少到不可能过拟合。更关键的是——模型参数里 `mean` 和 `std` 都只有一个元素，它学到的就是「正常 R 的均值 13.33 和标准差 0.107」，没有可过拟合的自由度。

**Q3：换个电机还准吗？换个人装还准吗？**

A：绝对值阈值 12.0 需要重标定，所以方案里给了相对写法：`阈值 = 0.90 × 上电学习到的基线`，换电机只要重新学习 10 秒，不用改代码。至于「换个人装」——这恰恰是我们放弃振动特征的原因。振动特征在实验室能 100% 分开，但 `accel_x_mean_g` 差 0.025 g 只相当于倾角变 1.4 度，换个安装就全变了；而转速不受安装姿态影响，电机装歪了转速还是那个转速。这是主动选择抗安装敏感的特征。

```bash
# ① 编译（Keil 命令行，退出码 0 = 成功）

"E:\Keil_v5\ARM\Segger\JLink.exe" -CommanderScript OBJ\burn_r64_20261019.jlink

# ③ 回读校验（不要信 J-Link 自报的 Verify）
"E:\Keil_v5\ARM\Segger\JLink.exe" -CommanderScript OBJ\readback_r64.jlink

# ④ 读板上状态（不带 device，避免复位目标）
#    mem8 0x20000084 8  -> phase / similarity / result_valid / initialized / alarm / lowRun / highRun / enabled
#    mem32 0x20000040 4 -> s_delta / s_rpm / s_ms

# ⑤ D1 mini 编译烧录
arduino-cli compile --fqbn esp8266:esp8266:d1_mini H:\毕设设计\github_repo\firmware_d1mini
arduino-cli upload  --fqbn esp8266:esp8266:d1_mini -p COM5 H:\毕设设计\github_repo\firmware_d1mini
```

**烧录前必做**（否则 RAM check failed）：先关掉 ADC2 + DMA2_Stream2，因为 J-Link 的 RAMCode 会压在 ADC 缓冲上，而 CPU 停住后 DMA 还在继续搬数据。

```
w4 0x40026440 0     /* DMA2_Stream2 CR */
w4 0x40012108 0     /* ADC2 CR2 */
w4 0x40012304 0     /* ADC2 CR1 */
```

**符号地址每次改完固件都要重新从 `.map` 取**，静态变量增删会导致整体平移（历史上 `s_fill` 从 0xC0 平移到 0xC4 就是加了一个 `g_winEmpty` 引起的）。
