## 1 输入特征的定义

模型吃的是 **32 点滚动峰峰值**，不是转速电平。逐点定义：

```
q[i] = rpm[i] / vbat[i]                                  原始空间，不做膝点归一化
r[i] = max(q[i-7 .. i]) - min(q[i-7 .. i])               滚动峰峰值，跨度 8 点 = 0.8 s
row  = [ r[0], r[1], ... , r[31] ]                       喂给模型的 32 点
```

选这个量而不是 R 电平，依据是同批 6840 个窗口上的实测对比：

| 判据 | 正常误报 | 捏轴检出 | 口径 |
|---|---|---|---|
| 32 点 R 电平（均值池化后） | 1.2% | **58.9%** | 模拟库内池化 |
| 滚动峰峰值（均值池化后） | 1.6% | **87.0%** | 离线预估 |
| 滚动峰峰值 → ICM 库 | **0.44%** | **92.0%** | 混淆矩阵实测 3108/3378 |
| 参考：dR 固定阈值 1.0（不经模型） | **0%** | **87.6%** | 每行 32 个 dR 取 max 与 1.0 比，2960/3378 |

原因：ZSM/ICM 这类库会对输入做池化压缩，电平信息被平均掉；而捏轴只占窗口一部分，
平均后跌落有限。峰峰值是"取最大值减最小值"，捏轴造成的瞬时跌落不会被平均抹平。

> **87.0% 与 92.0% 不是矛盾，是两个阶段**：87.0% 是**离线预估**——假设峰峰值进了库仍然会被均值池化，用来判断「换特征值不值得走」；真正训出来的 ICM 带 3 维特征（n95 / 峰值 / n25），第 4 节混淆矩阵给出的异常侧检出率是 **92.0%**（3108 / 3378）。对外表述统一写「离线预估 87.0%，实测 92.0%」。

## 6 与固件的接口

维度已对齐（32 × 1），`ai_monitor.c` 中
`AI_MONITOR_NEAI_IN_LEN == FEATURE_R_WINDOW` 的编译期断言依然成立，无需改动。

**但 `feature_r.c` 必须改**：目前 `feature_r_get()` 交出的是膝点归一化的 R 电平（约 13），

改造方案（**已于 2026-10-21 实施并上板验证**，见第 7~9 节）：

1. 增设 8 点环形缓冲，每 100 ms 存入一个 `q = rpm / vbat`
2. 环满后计算 `ptp = max - min`，压入新的 32 点窗口 `s_rwin`
3. `feature_r_get()` 改为返回 `s_rwin`，并要求 `s_rfill == 32`
   （即需 39 次采样 ≈ 3.9 s 才能出第一个窗口，与离线脚本"先整段算 r 再滑窗"一致）
4. 原 `s_win`（R 电平）与 `s_rippleAbs`（dR 规则）保留，供遥测与规则判据继续使用

## 7 链接错误 L6242E 与 `-fshort-wchar`（2026-10-21 21:00 解决）

第一次换库后 Keil 报 **17 个 `L6242E`**，全部形如：

```
Cannot link object neai_entry.o as its attributes are incompatible with the image attributes.
... wchart-16 clashes with wchart-32.
```

根因不是工具链选错，而是 **`wchar_t` 宽度不一致**：NanoEdge 导出的 `libneai.a` 由
Arm GNU Toolchain 13.2.1 编译，GCC 默认 `wchar_t` 为 **4 字节**；而 Keil（ARMCC 5.x）
编出的工程镜像是 **2 字节**。

### 定量证据

自写 `armattr.py` 解析 ELF 的 `.ARM.attributes`，取 `Tag_ABI_PCS_wchar_t`（tag 18）：

| 目标 | wchar_t | enum_size | VFP_args | FP_arch |
|---|---|---|---|---|
| 旧库 `libneai.a`（未勾选） | **4** | 1 | 1 | 6 |
| 新库 `libneai.a`（勾选后） | **2** | 1 | 1 | 6 |
| 工程自身 `ai_monitor.o` / `feature_r.o` | **2** | 1 | 1 | 6 |

24 个归档成员逐个检查，新旧库内部完全一致；新库与工程 `.o` 的四项属性逐项吻合。

### 解决办法

NanoEdge AI Studio 第 5 步 Deployment 页 → `Compilation Flags`，
把 **`fshort-wchar`** 勾上（原本只有 `mfloat-abi` 与 `fshort-enums` 是勾选状态），
然后 `DEPLOY LIBRARY` → Compile 对话框 `GET LIBRARY` → 出现绿色 `compiled.` →
`SAVE LIBRARY`。

编译标志变为：

```
float_abi = hard
fshort_enums = True
short_wchar = True      <- 本次新增
```

结果：**0 Error / 0 Warning**，`Code=22180 RO-data=6548 RW-data=260 ZI-data=17988`。

> 换库后 `NEAI_ID` 随之变化（库内容变了）：`6ad8b466f4c74310b9bc146f`，md5 `7dc1ed459f211e046cb17c1a1fc32968`，与 `metadata.json` 的 `library_md5sum` 一致。

## 8 固件侧必须同步改的四处

### 8.1 学习窗数（**不改会永远没有结果**）

`metadata.json` 里 `learning_min_lines = 368`，即从零学至少要 368 个窗（36.8 s）。
原文固件写死 `AI_MONITOR_LEARN_WINDOWS = 64`，按 64 就转检测会让 `detect()` 永远返回
`NEAI_LEARNING_IN_PROGRESS`，结果是没有相似度、永远不报警。

但库**自带预训练知识**（`NanoEdgeAI.h` 原文：pretrained model comes from NanoEdge AI
Studio and is embedded in the library），所以：

- `ai_monitor_init()` 改为先 `neai_anomalydetection_init(true)`，上电即可检测；
- 若 `init(true)` 失败才退回 `init(false)` 从零学；
- 「要不要继续学」交给库的返回值决定，`AI_MONITOR_LEARN_MAX = 400` 仅作兜底上限。

### 8.2 `feature_r_push_ripple()` 的复位块误粘（**致命 bug**）

上一版补丁在函数尾部误粘了一段复位代码，每推一个点就把 32 点窗口清零，导致
`s_rfill` 恒为 0、`feature_r_get()` 永远返回"窗口未满"，**AI 一次都不会跑**。
因为编译 0 Error，肉眼看不出来。已删除该块，并把小环与峰峰值窗口的复位补进
`feature_r_reset()`（原来只清 `s_win`）。

### 8.3 切档不再重学基线

峰峰值两档几乎重合（0.834 与 0.836，差 0.2%），档位不敏感，一份知识两档通用。
`ai_monitor_switch_level()` 只清窗、不再 `init(false)`；`ai_monitor_notify_stopped()`
只清报警与计数，不再重学。

### 8.4 周期重学习改为增量补学

由"清空重学"改为"每 6000 次检测补学 1 个窗"，补学期间不停检测。

## 10 电流显示为负的根因与修复（2026-10-21 21:40）

### 现象

新库烧录后 AI 判据全部正常，但屏幕上的电流值变成了负数
（停机零点 2.5897 V、带载读数 2.52 V → 差 -85 码 = **-0.37 A**）。
而当天早些时候同一工况（58% 档、140 rpm）用 D1 采集的 12 批数据
全是正值：`normal_58 ≈ +104 mA`、`grip_58 ≈ +196 mA`。

### 关键推理：先排除"接反"

第一反应是 ACS712 输出接反，于是给 `current.h` 加了 `CURRENT_SIGN (-1.0f)`
把结果整体取反。**这个方向是错的，已全部回退。**

判据很直接：ACS712 是**有符号、双向**的电流传感器，零点在 VCC/2。
如果真接反，停机时（无电流）读数仍应停在零点附近，取反只会把 0 变成 0；
而实测是**停机时零点准、带载才偏**，说明问题出在带载时的采样，
不在信号链的极性。

### 真正根因：PWM 纹波与采样节拍相位混叠

定量关系：

- TIM9 PWM 频率 20 kHz（2 MHz / ARR=99），周期 **50 µs**；
- 电流采样节拍 = 主循环 10 ms，`Current_GetAmp()` 每 10 ms 被调一次；
- 10 ms / 50 µs = **200 个整 PWM 周期**；
- 毫秒计时器 `nowMs` 的分辨率是 1 ms = 20 个 PWM 周期。

三个数都是整数倍，意味着**每次采样永远落在 PWM 周期的同一个相位上**。
`Current_UpdateFiltered()` 里的 8 点滑动平均本来是设计来压掉随机噪声的，
但采样点同相位 → 8 个样本几乎完全相同 → **平均等于没平均**，
直流分量被 PWM 纹波偏置顶歪，落到零点以下就显示成负值。

这解释了为什么只有带载才出错：PWM 关断（`duty == 0`）时没有纹波，
所以停机零点永远是准的（这也是 `Current_TrackZero()` 只在停机时工作的原因）。

### 修复：采样相位抖动（dither）

在每次读取 ADC 之前，用 DWT 周期计数器人为延后一小段，让 8 次采样
分别落在 PWM 周期的 8 个均匀相位上，8 点平均才真正覆盖一个完整纹波周期。

```c
#define CURRENT_DITHER_PHASES       8U      /* 把一个 PWM 周期切成 8 份 */
#define CURRENT_DITHER_STEP_CYCLES  1050U   /* 168 MHz 下 1050 周期 = 6.25 us */

static uint8_t g_i_dither = 0U;

/* 启动 DWT 周期计数器（Current_Init() 里调用一次） */
static void Current_EnableCycleCounter(void)
{
    CoreDebug->DEMCR |= CoreDebug_DEMCR_TRCENA_Msk;
    DWT->CYCCNT = 0U;
    DWT->CTRL |= DWT_CTRL_CYCCNTENA_Msk;
}

static void Current_WaitCycles(uint32_t cycles)
{
    uint32_t start = DWT->CYCCNT;
    while ((uint32_t)(DWT->CYCCNT - start) < cycles) { }
}

/* Current_UpdateFiltered() 里，raw = Current_ReadRaw(); 之前插入 */
Current_WaitCycles((uint32_t)g_i_dither * CURRENT_DITHER_STEP_CYCLES);
g_i_dither++;
if (g_i_dither >= CURRENT_DITHER_PHASES) { g_i_dither = 0U; }
```

8 x 1050 = 8400 周期 = **50 µs**，正好铺满一个 PWM 周期。
最大附加延迟 43.75 µs（7 步），相对 10 ms 节拍是 0.44%，可以忽略。

### 为什么用 DWT 而不是普通延时

`Delay_us()` 那种软件循环的精度受编译器优化和中断影响，几十微秒量级
抖动量本身就接近要测量的相位差，等于白做。DWT->CYCCNT 是内核周期计数器，
168 MHz 下分辨率 5.95 ns，没有累积误差。

## 11 关于 `AI_MONITOR_RELEARN_MIN_SIM = 20`

实测捏轴相似度 21，与这个硬故障门限只差 1。理论上持续轻度异常会被慢慢补学进去，
但补学速率只有每 6000 次检测 1 个窗（约 10 分钟 1 个），影响可忽略；
若把它提到 40（高于阈值 32），则会重新引入"工况漂移后永远锁在报警里"的死锁
（2026-10-19 板上踩过）。两者权衡后保持 20 不变。
