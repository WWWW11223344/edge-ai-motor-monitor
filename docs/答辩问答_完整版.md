## 一、项目概述

### 口述版

我这个项目做的是**电机状态监控**。场景是这样：工业现场和机器人上大量使用直流减速电机，电机一旦卡死、齿面损伤、轴承磨损，轻则停机重则烧电机，而人工巡检不可能 24 小时盯着。所以我做的是一个**能自己判断电机正常不正常、并且把结果直接显示在当地屏幕和手机上的小系统**。

具体做的事情是：用 STM32F407 做主控，用编码器测转速、用 ACS712 霍尔电流传感器测电流、用 MPU6050 测振动，三路数据每 10 毫秒采一次；然后在 MCU **本地**算出 19 维特征，交给一个用 NanoEdge AI 训练出来的异常检测模型，模型输出一个 0~100 的「相似度」，相似度低于阈值就报警。整个过程**不需要上位机、不需要联网也能工作**——这就是边缘 AI 的意思。

系统一共四个核心功能：**电机调速与急停控制**、**三路传感器的实时数据采集与 OLED 本地显示**、**板上边缘 AI 异常检测与报警**、**WiFi 上传到手机网页远程监控**。

### 背景与目标

- **背景**：电机故障诊断传统做法是「把振动信号传到电脑上做 FFT 分析」。但工业现场很多场合没有电脑、没有稳定网络，而且数据传上去再判断，延迟大、隐私和带宽都是问题。把模型直接塞进 MCU，让设备**自己会判断**，是这几年的主流方向，也是 ST、NXP 这些厂商主推的「TinyML / 边缘 AI」。
- **目标**（三条，都能验收）：
  1. 三路物理量（转速、电流、振动）能在 100 Hz 下稳定采集，不丢帧、不混叠；
  2. 异常检测模型能真正跑在 STM32 上，而不只是在电脑上跑仿真；
  3. 从「电机被卡住」到「屏幕上出现 ALARM」，整条链路能现场演示通。

### 核心功能与实现路径

| 功能 | 实现方式 |
|---|---|
| 电机调速 | TIM9 输出 20 kHz PWM，PE5 → D153C 的 AIN1，占空比 58%（软件限幅） |
| 急停 | KEY0（PE4）按下立刻把档位归零、PWM 清 0 |
| 转速测量 | 编码器 A/B 相 → PB6/PB7 → TIM4 硬件编码器模式四倍频计数 → 每 100 ms 算一次 rpm |
| 电流测量 | ACS712 → PA5（ADC1_IN5）→ 8 点滑动平均 → 零点在线跟踪 |
| 振动测量 | MPU6050 → **软件 I2C（PF0/PF1）** → 合成加速度模长 |
| 母线电压 | D153C 的 1/11 分压 → PA4（ADC1_IN4） |
| 本地显示 | 0.96 寸 SSD1306 OLED，软件 I2C（PB8/PB9），128×64 分 5 个区域轮询刷新 |
| 边缘 AI | 19 维特征 → NanoEdge Library 37（ZSM 模型）→ 相似度 → 事件级报警 |
| 远程监控 | USART3（PB10，AF7）57600 8N1 发二进制帧 → Wemos D1 mini → WiFi AP + 只读网页 |
| 数据留档 | 20 kHz 高速采样前端（ADC2 + DMA）并行抓原始块，供 J-Link 导出做 FFT |

### 系统数据流（一句话串起来）

```
编码器/ACS712/MPU6050 → 每 10 ms 采一帧 → 打包成 M2Frame（36 字节）
   ├─→ OLED 显示（分片刷新，50 ms 一轮）
   ├─→ 19 维特征提取（64 帧窗口 / 步长 16 帧）→ 4 帧一组的 76 float → 板上 AI
   └─→ USART3 二进制帧（42 字节含 CRC16）→ D1 mini → 手机网页
```

### 可能追问

- **« 你这个和市面上的电机保护器有什么区别？ »**
  市面上的热继电器/保护器是**事后保护**：靠电流过载发热才动作，响应慢、而且只能判断「过载」。我做的是**事前/过程中的状态识别**：用电流 + 振动 + 转速的联合特征，在负载还没到危险程度时就能识别出工况偏离正常态，而且能本地显示、能远程看。
- **« 为什么不直接用现成的 PLC 或工控机？ »**
  成本和一个 MCU 差两个数量级，而且现场很多点位根本放不下工控机。这个方案整机成本是几十块钱量级（开发板 + 一个电机 + 一个驱动板 + 三个传感器模块）。
- **« 你这个项目最难的地方在哪？ »**
  不是写 AI，是**把数据采干净**。我在第八节有一个完整记录：板子上的 100 Hz 采样和 20 kHz 的 PWM 载波正好是整数倍关系，载波会折叠到直流，导致电流读数出现假负号；而且电机的换向纹波、齿轮啮合频率全在采样带宽之外，被混叠掉了。我专门做了一次采样链路审计才把这个问题定量说清楚。

### 逐个说明「为什么选它」

**1. STM32F407ZGT6（神舟号 V2.0 开发板）**
选它的三个理由：① **有 FPU（浮点运算单元）**——这一点对本项目是刚需，因为特征计算和 AI 推理都是浮点，带 FPU 的 M4 比不带的速度差 10 倍以上；② 168 MHz 主频 + 192 KB SRAM，装得下 AI 库（Library 37 要 1.1 KB RAM / 0.5 KB Flash，很宽裕）；③ 板载资源多（OLED 用的 I2C、串口用的 CH340C、以太网 PHY 都有），省外围器件。
**代价**：这块板的 PA1、PA7、PC3、PC4 被板载以太网 PHY（LAN8720A）占用，**不能拿来用**。我最初的编码器方案本来设计在 PA6/PA7，查原理图发现 PA7 = RMII_CRS_DV 被 PHY 占了，才改成 PB6/PB7。

**2. WHEELTEC MG310 减速电机**
选它的原因：**自带霍尔编码器**（13 线），不用另外装测速装置，而且轮趣提供了完整的手册（Ke = 0.00064 V/rpm、电感 30.7 mH、减速比 1:20 这些参数我都是从手册表 4-1/4-2 查的）。额定 7.4 V、空载 500 rpm、堵转 2 A，正好在 ACS712-05B 的 5 A 量程内。

**3. WHEELTEC D153C 驱动板（TB6612FNG）**
选它是因为**不用焊接**——它的接口是**排针**，我全程用杜邦线接的，符合我的硬约束（零焊接）。TB6612FNG 是双 H 桥，支持 VM 4.5~13.5 V，PWM 频率上限 100 kHz（我用 20 kHz 很安全）。
这里面有两个必须讲清楚的接线点：
- **STBY 引脚**：D153C 手册写 STBY=1 才能输出，硬件上它没接、引到排针上，所以我在固件里把 **PA8 配成推挽输出并拉高**来使能。**这个漏了电机就完全不转。**
- **PWMA/PWMB**：我这一路用的是 **B 通道（MOTORC1 / Motor_B）**，PWMB 硬接 3V3，BIN1 接 PE5 走 PWM、BIN2 接 PE6 恒 0。这样电机端平均电压 = 占空比 × 母线电压。

**4. ACS712-05B 电流传感器模块**
选它的原因：**成品模块、有现成排针、零焊接**，而且是霍尔隔离型，串在主回路里不共地也没关系。5 A 量程够用（MG310 堵转 2 A）。
必须钉死的两个数字：**灵敏度 185 mV/A**，**零点是 VCC/2 = 2.5 V（不是 1.65 V！）**。网上很多资料写 1.65 V，那是把 3.3 V 供电版的参数套到 5 V 模块上，如果用 1.65 V 当零点，会引入约 +4.6 A 的固定偏差，整个电流通道直接废掉。
**接的位置也很关键**：最终我把 ACS712 **串在驱动板和电机之间**（不是电池和驱动板之间）。原因见第六节和第八节第 4 条——串在母线上测到的是被 20 kHz 斩波、又被母线电容平滑过的电流，读数抖且符号不稳；串到电机引线上，测的是电机的**连续绕组电流**，读数稳定、量级正确。

**5. MPU6050 GY-521**
选它是因为便宜、资料多、I2C 接口简单、自带 ±2g 量程刚好够测电机振动。
**接线上的一个被迫改动**：原本计划让 MPU6050 和 OLED 一起挂在板载 I2C（PB8/PB9）上，但现场**没有合适的 I2C 分线位置**，所以我给 MPU6050 单独写了一套**软件 I2C**，占 **PF0/PF1** 两个引脚。这两个脚在板上同时连着外部 SRAM 的地址线，本工程没启用外部 SRAM，所以可以用，**但不能同时启用 FSMC**。

**6. OLED（SSD1306，0.96 寸，128×64）**
选它的原因：I2C 只要两根线（PB8/PB9 是板载 I2C，自带 4.7 k 上拉，连上拉电阻都省了），而且 128×64 够我排 5 行数据。
**这里有个我自己做的设计**：8 页（每页 8 像素）全部排满，用**两种字号混排**——转速/电流/振动用 8×16 大字号（占 2 页），母线电压和状态用 6×8 小字号（占 1 页），正好 8 页不浪费。

**7. 3S 锂电池**
选它的原因：驱动板要 4.5~13.5 V，3S 锂电标称 10.8 V、满充 12.6 V，正好在范围内；而且锂电带载能力强，比 USB 供电可靠。
**这里面有一条我踩过的坑**：**58% 是占空比的硬上限**——12.6 V × 0.58 = 7.3 V，刚好等于 MG310 的额定 7.4 V。母线电压变了这个上限要重算，不能照抄。另外拿电脑 USB 的 5 V 给驱动板供电是**撑不住的**，电机一加速就把 USB 拉垮触发过流保护，要拔插一次才恢复。

**8. Wemos D1 mini（ESP8266）**
选它的原因：**它自己会连 WiFi、自己会跑 HTTP 服务器**，所以 STM32 侧只需要往串口发数据，**一行 AT 指令代码都不用写**。这是成本最低的方案。
接线：D1 的 D6/GPIO12 接 STM32 的 **PB10（USART3_TX）**，只用一根数据线 + 一根共地，**单向**（D1 只收不发，不驱动 STM32 的输入脚，避免电气冲突）。D1 用 USB 单独供电。
**顺带一个引脚排错**：原始硬件图上 PB10 标注是「P9 排针第 30 脚」，网上有些资料写成 P8，我对着图纸核对过是 **P9-30**。

### 整体接线的关键事实（可现场照着复述）

- 编码器：**必须从 D153C 的 H2 排针飞线**——`H2-2(E2A)→PB6`、`H2-1(E2B)→PB7`。**漏了这两根，屏上 Spd 永远 0**（我只插了电机 6P 排线就踩过这个坑）。
- 母线电压：`H2-5(ADC)→PA4`，板上有 10 k + 1 k 分压（1/11），直接接不会烧引脚。
- 6P 电机排线里同时走**电机电流（pin2/pin6）、编码器供电（pin3）、编码器信号（pin4/pin5）**——所以这根排线一松，会出现「电机不转 + 编码器也没脉冲」两个现象同时发生。这一点是我后面定性的关键依据。

### 每样工具的具体用法

**Keil MDK + StdPeriph V1.4**
整个固件是**四层结构**：`CORE/`（CMSIS 和启动文件）、`FWLIB/`（标准外设库）、`USER/`（`main.c`、中断服务、工程文件）、`HARDWARE/`（我自己写的板级驱动，一共 20 个源文件）。
编译我用**命令行**跑，因为可以接进自动化脚本：
```
UV4.exe -b USER\STM32F407_Template.uvprojx -j0 -o build.log
```
**判据**：退出码 0 = 编译成功（不是「没输出」）；日志是 GBK 编码；成功时会打印 `Program Size: Code=... RO-data=... RW-data=... ZI-data=...`。
最终版本：**Code = 20224 字节，RO-data = 3928，RW-data = 192，ZI-data = 16728，0 Error 0 Warning**。

**J-Link Commander —— 这个工具在我项目里的作用远不止烧录**
除了烧录，我做的最重要的一件事是**远程读内存调试**。原理是：Keil 编译后会生成 `.map` 文件，里面有所有全局/静态变量的**绝对地址**；然后用 J-Link 脚本 `mem32 <地址> <字数>` 直接读 RAM，就能在不打断程序运行的情况下看变量。
这一招在项目里救了我两次：一次是确认 PWM 的 `TIM9->CR1` 是不是被污染、`CNT` 有没有超过 `ARR`；一次是逐帧确认编码器计数器和 AI 的几个状态量是不是在推进。判据很直观：**读 `s_ms` 两次，间隔 500 ms，差值 ≈ 500 就说明程序在正常跑**。

**NanoEdge AI Studio 5.2**
用它的五步流程（Project Settings → Signals → Benchmark → Validation → Deployment）训练异常检测模型，最后导出可以直接链进 Keil 工程的静态库 `.a`。细节见第六节。
一个环境事实：**从 V4.3 起，NanoEdge AI Studio 对全部 STM32 型号免费、无限量**，所以这个工具链是零成本的。

**Python 上位机脚本**
负责三件事：① 解析 STM32 发出来的二进制帧，检查时序连续性（这是数据能不能用来训练的**门禁**）；② 按和板端**逐位一致**的算法算 19 维特征，导出成 NanoEdge 能读的 CSV；③ 把 20 kHz 原始采样块做 FFT，验证换向纹波这些频率分量真实存在。

**PowerShell 自动化脚本**
把「编译 → 备份原固件 → 烧录 → **独立回读并逐字节比对**」串成一条命令。最后这一步很重要：烧完之后把 Flash 整个读回来，和 HEX 文件比对，**差异 0 字节**才算烧录成功。最终版本回读结果就是 **0 differences**。

## 四、边缘 AI 与状态检测

### 口述版

**边缘 AI 是什么**：传统做法是把传感器数据全部传到云端或电脑上，在那边跑模型，再把结果传回来。边缘 AI（也叫 TinyML）是把**训练好的模型直接部署在设备本地的 MCU 上**，数据不出设备，本地就算出结果。好处有三个：**不依赖网络**（断网照常工作）、**响应快**（不用等网络往返）、**数据不出本地**（隐私和带宽都省了）。

**我这个项目怎么体现边缘 AI**：
模型是「在电脑上用 NanoEdge AI Studio 训练、导出成一个 `.a` 静态库、然后**链进 STM32 的 Keil 工程**、和我的固件一起编译成 HEX 烧进 MCU」。上电以后，**STM32 自己在板上跑推理**，整个过程不需要电脑参与。我甚至验证过：板子上的 `neai_anomalydetection_init()` 返回 `NEAI_OK`，`g_initialized = 1`，说明库在板上真的初始化成功了。

**状态检测是怎么实现的**：
用的是**半监督异常检测**。也就是说我只给模型「电机正常运行时」的数据，不给它故障样本。原理是模型学出正常数据的分布，运行时算当前数据和「学到的正常态」有多像，输出一个 **0~100 的相似度**。相似度低 = 偏离正常 = 异常。
具体到板上的流程：
1. 上电后，电机升到 58% 档，系统先进入 **LEARNING（屏上显示 LRN）**，攒 22 个特征块自己学「正常」长什么样；
2. 学完切到 **DETECTING（屏上显示 DET）**，每次推理出一个相似度；
3. 相似度**连续 2 次**低于阈值 48 → 置 ALARM（状态栏显示 ALARM）；
4. 相似度**连续 2 次**回到阈值以上 → 解除 ALARM，回到 RUN；
5. 每约 2 分钟自动重学一次，跟上工况漂移。

### 支撑细节

- **为什么用半监督而不是有监督**：现场拿到「电机坏了」的样本成本极高（要真把电机弄坏），而「正常运行」的数据随手可得。半监督只要求正常数据，更符合工程实际。
- **为什么板端要「自学习」而不是把模型权重硬写死**：电机个体差异、安装差异、供电差异都会让「正常」的数值基线不一样。让板子在上电后对着**自己这台电机当前的状态**学一遍正常基线，比出厂写死阈值鲁棒得多。
- **现场演示流程（我实测通过的）**：按 K1 升到 L1（58%）→ 屏底条显示 `LRN` → 约 15 秒后变成 `DET` → **用手捏紧转子** → 相似度掉到 9~12 → 状态栏变 `ALARM` → **松开** → 相似度回到 42~55 → 状态栏回到 `RUN`。

### 【诚实边界】（这一条答辩时一定要主动说，能加分）

我这个模型的 **19 维特征全部是幅值统计量**（均值、RMS、峰峰值、方差、波形因子），**没有一维需要「波形」这个概念存在**。所以在「电机有没有被额外加载」这个判别任务上，它和「设 19 个门限的多维阈值」在信息量上是等价的。

那 AI 相对阈值多出来的价值是什么？三点：
1. **多变量联合**：不是比单个电流，而是电流 5 维 + 三轴振动 15 维 + 转速 2 维 + 电压 1 维，共 19 个量**联合**判定；人工设阈值要设 19 个门限，还要考虑它们之间的相关性，模型自动学出这个联合分布。
2. **时序上下文**：模型的输入是 **19 轴 × 4 个连续窗口**，看的是约 1.1 秒的演化过程，不是单点瞬时值，所以能区分「持续捏住」和「瞬时抖动」——这也是我为什么必须加「连续 2 窗才算报警」的原因。
3. **板上自学习 + 周期重学**：不需要人工标定正常基线，而且每约 2 分钟自动重学一次，跟得上工况漂移（升温、电流零点漂移、电池电压下降）。

**并且我已经把「为什么是 AI」的正面论证写进了方案**：把异常的定义从「负载变了」改成「**平均负载基本不变、但纹波结构变了**」。像偏心附加质量（不平衡）、齿面损伤、安装松动、轴承阻力增加这四类故障，在同一转速下**平均电流几乎不变**，幅值阈值分不开，但纹波频带特征可以分。这就是 AI 在这个任务上不可替代的地方，而且**不需要换工况**。
**代价要说清楚**：要走到这一步，必须把采样率提上去（我现在已经做了 20 kHz 的高速采样前端，能出 FFT 证据），但**目前它还只是一条并行的取证路径，还没有成为模型的输入**。答辩时不要把「我采了 20 kHz」说成「AI 已经在用波形特征」。

## 五、知识运用

### 1. 模拟电路 / 传感器

| 知识 | 用在哪 |
|---|---|
| **电阻分压** | D153C 板载 10 k + 1 k 组成 1/11 分压，把最高 13.5 V 的母线电压降到 ADC 能接受的 1.23 V（3S 锂电 12.6 V 时），量程 3.3 × 11 = **36.3 V**，安全余量充足 |
| **霍尔电流传感原理** | ACS712 内部是霍尔元件 + 线性放大，输出 = 零点 + 灵敏度 × 电流；我据此推出 `I = (Vout − 2.5) / 0.185` |
| **ADC 采样定理与源阻抗匹配** | 分压电阻 10 k‖1 k ≈ 0.9 kΩ，源阻抗偏高，所以我把 ADC 采样时间设成 **480 周期**（不是默认的 3 周期），否则采样电容充不满、读数系统性偏低 |

| **H 桥驱动与续流** | 理解「AIN1 = PWM、AIN2 = 0」这种驱动—续流方式，是后面分析「为什么电流传感器位置很重要」的基础 |
| **开关电源纹波与母线电容** | 20 kHz 斩波电流主要由驱动板上的母线电容（220 µF）提供，ACS712 所在的支路看到的是被平滑过的电流，这解释了我最初对「母线电流是满幅方波」的误判 |

### 2. 数字电路与 MCU 外设

| 知识 | 用在哪 |
|---|---|
| **定时器 PWM 输出** | TIM9_CH1/CH2 → PE5/PE6，输出 20 kHz PWM 调速 |

| 知识 | 用在哪 |
|---|---|
| **滑动窗口与步长** | 64 帧（640 ms）窗口、16 帧（160 ms）步长提取一组特征；这样 100 Hz 采集下有 75% 的重叠，特征更新密度够 |

## 六、边缘 AI 部署（重点）

### 6.1 AI 功能是怎样部署完成的（完整链条）

**第 1 步：在 STM32 上建立数据采集链路**
`main.c` 每 10 ms 采一帧，打包成 `M2Frame` 结构（36 字节负载），一方面走 USART3 发给 D1 mini，一方面**同一帧直接喂给板上 AI**（`telemetry_poll()` 里调 `ai_monitor_feed_frame(&frame)`）——这样保证**板上 AI 和上位机看到的是完全相同的数值**，特征是一致的。

**第 2 步：在 STM32 上提取 19 维特征**
`feature19.c` 积累 64 帧（640 ms）后，算出一组 19 个 float。用双精度累加、输出 float，避免精度损失。

**第 3 步：采集训练数据送到电脑**
把正常运行的 3 组数据（`normal_running_04/05/06`）和「捏住转子」的 3 组数据（`grip_01/02/03`）通过遥测链路存到电脑上。每组约 371 个特征窗口。**采集有门禁**：必须 6000/6000 帧全部接受、无丢帧、单帧间隔 ≤ 20 ms 才算合格。

**第 4 步：在 NanoEdge AI Studio 里训练**
- Project Settings：Target = **STM32F4 Series**（同 M4 核、同 1 MB Flash / 192 KB RAM，兼容 F407ZG）；Sensor = **Time Series → Generic / 19 Axes**。
- Signals：正常和异常各导入 **278 行 × 76 列**（19 轴 × 4 连续样本）。
- Benchmark：搜索了 3066 个候选，跑了 2 小时 2 分 55 秒，选出**最优模型 = Library 37，ZSM 模型**。
- Validation / Deployment：导出 `libneai.a` + `NanoEdgeAI.h`。

**第 5 步：把库链进 Keil 工程**
这一步有**两个技术坑**，我都是实测解决的：
- **编译选项必须和工程一致**：从库的 `.ARM.attributes` 段里解出它要求 `Tag_ABI_VFP_args = 1`（硬浮点）、`Tag_ABI_PCS_wchar_t = 2`（2 字节 wchar）、`Tag_ABI_enum_size = 1`（最小 enum 容器），对应 Deployment 页要勾的三个选项；其中 **`fshort-wchar` 页面默认是不勾的，必须手动勾上**。
- **输入长度必须改**：旧库是「1 轴 × 19 采样 = 19 个 float」，新库是「**19 轴 × 4 样本 = 76 个 float**」。我把 `ai_monitor.c` 改成攒 4 帧特征的 76 float 累加器（**样本优先**排列：样本 0 的 19 轴，再样本 1 的 19 轴……），并加了编译期断言兜住。
- 链接验证：用工程现成的 56 个 `.o` + 新库，按 `--cpu Cortex-M4.fp --library_type=microlib --strict` 重新链接 → **exit 0**，生成的 map 里 `neai_anomalydetection_init / _learn / _detect` 符号齐全。
  （插一句：**armlink 是老版本程序，不认中文路径**，库要放在纯 ASCII 路径下才能链接。）

**第 6 步：调参并上板验收**
- 第一次烧上去跑，发现正常相似度会**随运行时间漂移**（刚学完 100，几分钟后掉到 42~63），在阈值 66 附近会造成误报；而且 RAM 里栈 1 KB 不够（会溢出）。
- 最终参数：**阈值 66 → 48**、**报警/解除窗口各 2 个**、**栈 1 KB → 8 KB**、**加周期重学习（每 180 次检测 ≈ 每 2 分钟重学一次，22 窗约 14 秒）**。
- 上板实测（J-Link 内存回读）：主循环 100 Hz 稳跑（`g_seq` 每秒 +300）、`g_skipped = 0` 无丢帧、`g_initialized = 1`（库初始化成功）、`g_phase` 在 LEARNING / DETECTING 之间正常切换。
- 现场演示验收：**K1 → LRN → DET → 捏紧转子 → ALARM → 松开 → RUN**，通过。

### 6.2 所有数据的含义、来源与获取方式

**板端每一帧（`M2Frame`）里的 6 个物理量**

| 字段 | 含义 | 单位 | 获取方式 |
|---|---|---|---|
| `value[0]` | 电机电流 | mA（原始 A × 1000） | ACS712 → PA5 → ADC1_IN5 |
| `value[1..3]` | 三轴加速度原始值 | mg（LSB × 1000 / 16384） | MPU6050 → 软件 I2C |
| `value[4]` | 转速 | rpm（×10） | 编码器 → TIM4 → 每 100 ms 计数差分 |
| `value[5]` | 母线电压 | mV（×1000） | D153C 1/11 分压 → PA4 → ADC1_IN4 |
| `seq` | 帧序号 | — | 每发一帧 +1，用于检测丢帧 |
| `uptimeMs` | 上电毫秒数 | ms | TIM7 累加 |
| `validMask` | 有效性掩码（6 位） | — | 每路传感器各自置位：电流 bit0 / X bit1 / Y bit2 / Z bit3 / 转速 bit4 / 电压 bit5 |

**19 维特征的具体含义（`feature19.c`，顺序固定）**

| 序号 | 特征 | 计算对象 | 说明 |
|---|---|---|---|
| 0~4 | mean / RMS / 峰峰值 / 方差 / 波形因子 | **电流**（64 帧全部） | 电流的 5 个统计量 |
| 5~9 | 同上 5 个统计量 | **X 轴加速度**（末 32 帧） | 振动 X |
| 10~14 | 同上 5 个统计量 | **Y 轴加速度**（末 32 帧） | 振动 Y |
| 15 | RMS | **Z 轴加速度**（末 32 帧） | 振动 Z，只取 RMS |
| 16 | 转速均值 / 500 | 转速（64 帧） | 归一化到约 0~1 |
| 17 | 转速标准差 / 500 | 转速（64 帧） | 转速波动 |
| 18 | 母线电压均值 / 12.6 | 电压（64 帧） | 归一化到 0~1 |

（振动只用末 32 帧是因为振动通道关心的是近期状态；电流和电压用全部 64 帧看的是整体水平。）

**数据来源与获取路径（一路走下来）**
```
传感器
  → STM32 每 10 ms 采一帧（100 Hz）
  → M2Frame（36 字节负载）
  → ① 板上：64 帧窗口 → feature19 → 76 float → AI
  → ② USART3/PB10 @57600 → D1 mini（D6）→ WiFi AP → 手机网页 /status
  → ③ 电脑端：USB 串口采集 → 解析 + 时序门禁 → 19 维 CSV → NanoEdge Studio
```
**注意路径 ③ 的时序门禁**：只有「6000/6000 帧全接受、无丢帧、最大帧间隔 ≤ 20 ms」的数据才能进训练集。这是我专门加的质量门槛——丢过帧的数据在时间轴上是不连续的，算出来的特征没有物理意义。

### 6.3 如何训练 AI（细节）

- **训练数据**：正常 278 个 buffer + 捏住 278 个 buffer。每个 buffer 是「19 轴 × 4 连续样本」= 76 个 float。
- **打包方式**：把 3 组采集**首尾拼接**成一条连续流，然后 `samples = 4, stride = 4` 切块——也就是说**板上推理也必须用非重叠的 4 帧块**，和训练时的打包方式一致（这是 `ai_monitor.c` 里 `g_neai_fill` 累加器的由来）。
- **搜索空间**：ICM / MML / ZSM / iPCA + 降维，共试了 3066 次。
- **最优模型**：**Library 37，ZSM（Z-Score Model）**，质量指标 99.7 pts。
- **资源占用**：**RAM 1.1 KB（1032 字节）、Flash 0.5 KB（488 字节）**。
- **最小学习迭代数**：22（所以板端设 `AI_MONITOR_LEARN_WINDOWS = 22`）。

### 6.4 如何区分正常与异常

模型输出一个 **0~100 的相似度**（similarity），含义是「当前数据和学到的正常态有多像」。

**我实测到的分布**（这是写论文最有用的数据）：

| 状态 | 相似度范围 |
|---|---|
| 刚学完的正常运行 | 87 ~ 100 |
| 运行一段时间后（漂移） | 42 ~ 63 |
| 轻捏转子 | 46 ~ 56（**和正常重叠，分不开**） |
| **捏紧转子** | **9 ~ 12**（稳定触发） |

**判定规则（三道关）**：
1. **域门限**：只有 `level == 1 && duty == 58 && validMask == 0x3F` 的帧才进模型。不在训练工况的帧直接丢弃并重置窗口——**这是有意设计，因为模型只见过 58% 档下的正常态**。
2. **连续性门限**：帧必须严格连续（`seq` 递增 1、时间戳递增且间隔 ≤ 20 ms），断过就重置窗口。
3. **事件级报警**：相似度**连续 2 次**低于 48 才置 ALARM（防止正常运行的瞬时下探造成误报）；回到阈值以上**连续 2 次**才解除。

### 7.2 为什么选这五个量显示

- **转速 + 电流 + 振动**是电机的三大基本运行量，也是我喂给 AI 的物理来源，用**大字号**显示——答辩时评委从两米外就能看清。
- **母线电压**：它决定了「转速和电流正不正常」的参照系。**转速和母线电压必须一起看**，不然拿一个绝对数下结论是不可靠的。原本这一行放的是假的相似度（`Sim 0.95`），我把位置让给了真实电压——**假数据不如不留**。
- **状态字 / AI 阶段 / 秒数 / 心跳**：状态字告诉人「现在系统认为电机是什么状态」；`LRN`/`DET` 告诉人 AI 在哪一步；运行秒数 `T` 和那个转圈的小风车（`| / - \`）是**心跳**——屏幕上有东西在动，就说明程序没卡死。

### 7.3 每一项数据是怎么来的 + 计算公式（重中之重）

#### （1）转速 Spd —— 单位 rpm

**硬件链路**：编码器 A/B 相 → PB6/PB7 → TIM4 编码器模式（硬件四倍频）→ 每 100 ms 读一次计数差。

**公式推导**（这一段必须能自己推，评委很爱问）：
```
单圈计数 CPR = 编码器线数 × 倍频 × 减速比
            = 13 ppr × 4（AB 双边沿四倍频）× 20（减速比 1:20）
            = 1040 counts / 输出轴一圈

采样窗口 T = 100 ms = 0.1 s

rpm = (ΔCount / CPR) / T × 60
    = ΔCount × 60 / (1040 × 0.1)
    = ΔCount × 60 / 104
    = ΔCount × 0.576923
```
**代码里的常数**：`ENC_RPM_PER_CNT = 0.576923f`（`encoder.h`）。
**举例**：100 ms 内数到 253 个脉冲 → 253 × 0.576923 ≈ 146 rpm。
**标定方法**（最省力的）：让电机用固定 PWM 自己转，读数和理论值 `67.57 rpm/V × 母线电压 × 占空比` 对照。手工标定是「用手转输出轴 1 秒 1 圈，屏上应该显示约 60 rpm」——但输出轴只有一小截杆子，手转很费劲，所以我一律优先让电机自己转。

#### （2）电流 Cur —— 单位 A

**硬件链路**：ACS712-05B 的 OUT → PA5（ADC1_IN5）→ 12 位 ADC。
**公式**：
```
① ADC 原始值转传感器输出电压：
     Vout = raw / 4095 × 3.3      (V)

② ACS712 的输出关系（5A 版）：
     Vout = 2.5 + 0.185 × I       →    I = (Vout − V_zero) / 0.185

   其中 2.5 V 是「零电流时的输出电压」（= VCC/2，VCC = 5 V）
        0.185 V/A 是灵敏度
        V_zero 是我上电校准出来的实际零点（实测 2.517 V）
```
**代码里的常数**（`current.h`）：`ACS712_SENSITIVITY = 0.185f`、`ACS712_VREF = 3.30f`、`ACS712_ADC_FULL = 4095.0f`。
**三个必须讲的工程处理**：
1. **上电零点校准**：电机停转时采 64 次取平均，得到这台设备的实际零点。**必须做**——ACS712 的零点容差是 ±1.5% VCC（等效 ±200 mA），不校准就会有固定偏置。
2. **8 点滑动平均**：`CURRENT_FILTER_WINDOW = 8`。**而且是在「原始 ADC 码」上做平均，不是换算成安培之后再平均**——因为整数平均可以做到完全精确，能消掉零点附近的单点符号翻转（就是屏幕上出现假负号的那个问题）。代价是约 70 ms 的滞后。
3. **停机零点在线跟踪**：只有确认「占空比 = 0 且转速 < 20 rpm」时才执行 `Current_TrackZero()`，用 `α = 0.02` 的一阶滤波把零点慢慢拉向当前读数。**电机一转就冻结零点**——这是为了防止「拿运行中的电流去改零点」把真实电流吃掉。

#### （3）振动 Vib —— 单位 g

**硬件链路**：MPU6050（±2g 量程）→ 软件 I2C（PF0/PF1）→ 读 3B 起 6 个寄存器得到 X/Y/Z 原始值。
**公式**：
```
① 原始值转 g：
     x = raw_x / 16384,  y = raw_y / 16384,  z = raw_z / 16384
   （16384 LSB/g 是 ±2g 量程下的灵敏度）

② 合成模长，再减掉重力 1 g：
     mag = |√(x² + y² + z²) − 1.0|

③ 开方用牛顿迭代（6 次）实现，不引 math 库
```
**代码位置**：`mpu6050.c` 的 `MPU6050_GetSnapshot()`，`Sqrtf()` 就是那个牛顿迭代开方。
**为什么这么算**：静止时电机只受重力，模长 = 1 g，减去 1 得 0；一旦有振动，模长偏离 1，偏离量就是振动幅度。取绝对值是因为不管往哪个方向偏都算振动。
**量程选择的理由**：±2g 是 MPU6050 最高分辨率档，电机这种小振动用 ±2g 才有足够的分辨率（16384 LSB/g）。原始值也一起发给上位机，因为 AI 的特征用的是原始值而不是 `vib_g`。

#### （4）母线电压 Bat —— 单位 V

**硬件链路**：D153C 的 H2-5（ADC 脚）→ PA4（ADC1_IN4）。板上有 **10 k + 1 k 的 1/11 分压**。
**公式**：
```
V_ADC = VM / 11
raw   = V_ADC / 3.3 × 4095
→  VM = raw / 4095 × 3.3 × 11
```
**代码**：`vbat.c` 的 `Vbat_GetVolt()`，`VBAT_DIV_RATIO = 11.0f`、`VBAT_ADC_AVG = 8`（8 次平均）。
**量程**：3.3 × 11 = **36.3 V**，3S 锂电 12.6 V 只用到 1/3，很安全；分辨率 3.3 / 4095 × 11 ≈ **8.9 mV**，足够判断「满 12.6 V / 该充电 9 V」。
**一条重要认识（这是我踩过坑才明白的）**：这个分压**只抽约 1 mA 电流**，所以它量到的是**近乎空载的电压**。结论是：**它能证明电池是健康的，但不能证明回路的带载能力**——如果电压是在「测压点之后」的环节丢掉的（比如接插件接触电阻），这一格是看不见的。这句话在第八节第 11 条会用上。

#### （5）状态字 ST —— 系统的四态判定

```
优先级从高到低：
  ① 任何一路传感器无效（speed/current/vib/vbat 任一 valid = 0）→ WARN
  ② 转速 < 20 rpm                                              → STOP
  ③ AI 处于 DETECTING 且已报警                                  → ALARM
  ④ 其余（数据有效且确实在转）                                   → RUN
```
**注意**：`RUN` 的含义是「**遥测数据有效且电机确实在转**」，**不是**「AI 判定电机健康」。真正的健康判定只有 ALARM 这一个出口。这个区分很重要——评委如果问「RUN 是不是代表没故障」，答案就是上面这句。

#### （6）AI 阶段 LRN / DET

- `LRN` = LEARNING，正在学正常态（22 窗，约 14 秒）；
- `DET` = DETECTING，正在检测；
- 都不显示时底条显示 `SIM`（提示当前是仿真/占位标记）。

#### （7）运行秒数 T 与心跳

- `T` = `uptime_s` = TIM7 累加的毫秒时基 / 1000；
- 心跳 = `| / - \` 四个字符轮换。

**【诚实边界】** 相似度的**数值本身没有上屏**——`ui.c` 里没有渲染相似度的代码，屏幕上只有 `LRN`/`DET` 和 `ALARM` 这两个**状态指示**，看不到 0~100 的数值。答辩演示时如果被要求「把相似度显示出来」，可以现场用 J-Link 读 `g_similarity`（地址 0x2000008D）指给评委看；要上屏需要再改一版 UI。

### 7.4 刷新策略（一个加分细节）

OLED 是软件 I2C、同步阻塞的，一次重画全部数值会长时间占住主循环，让 10 ms 的遥测帧出现空洞。所以我把刷新拆成 **5 个区域轮询**：每次主循环只发一个区域（转速 / 电流 / 振动 / 电压+状态 / 底条），5 次调用后整屏更新完。
**效果**：单次阻塞时间显著缩短，遥测帧间隔稳定在 11 ms 以内（门限 20 ms）。

## 八、问题与解决（重点）

按发生顺序，每条都按「现象 → 定位过程 → 根因 → 解决 → 判据」写全。

### 问题 1：PWM 配好了，电机一档都不转

- **现象**：PWM 初始化代码看上去完全正确，但四个档位电机全都不转，连「哼哼」的声音都没有。
- **定位过程**：用 J-Link 读 TIM9 的寄存器，发现三个致命现象：
  - `TIM9->CR1 = 0x038B`（正常应该只有 0x01~0x81）
  - `TIM9->CNT` 读到 15965 / 63493，**远大于** `ARR = 99`
  - `SR` 里的 `UIF` 一直为 0
- **根因**：`pwm.c` 用了 StdPeriph 的 `TIM_TimeBaseInitTypeDef` 结构体，但**没有初始化就把其中几个字段交给库函数处理**。`TIM_TimeBaseInit()` 会把 `TIM_ClockDivision` 这个 16 位字段和别的位一起 OR 进 `CR1`，而结构体没清零，栈上的垃圾值 **0x038A** 被 OR 了进去。结果 `CR1` 的 `UDIS`(bit1)、`OPM`(bit3)、`ARPE`(bit7) 全部被置 1：
  - `UDIS = 1` → 更新事件被禁止 → ARR 的预装载值 99 永远加载不进影子寄存器 → 计数器按 0xFFFF 跑 → PWM 周期从 50 µs 变成 33 ms、占空比不到 0.1%
- **解决**（三处一起改）：
  1. 结构体声明时 `= {0}` 清零；
  2. 显式赋值 `TIM_ClockDivision = TIM_CKD_DIV1`、`TIM_RepetitionCounter = 0`；
  3. 初始化前先 `TIM9->CR1 = 0`，把可能被污染的位彻底清干净。
- **判据**：改完 `CR1 = 0x01`、`ARR = 0x63`（= 99）、`CNT ≤ 99`、`CCR1` 随档位精确变化（58% 时 `CCR1 = 58`）。
- **沉淀下来的铁律**（写进项目规范）：**StdPeriph 的结构体必须 `= {0}`，用到的字段必须显式赋值**——「用到但没赋值」的字段是隐藏炸弹。这条也套用到了 `encoder.c`。

### 问题 2：屏幕上转速永远是 0

- **现象**：电机明明在转，`Spd` 那格恒为 0。
- **定位过程**：屏幕上报的电流/振动假值能用运行秒数 `T` 反算出来、完全对得上 → 说明主循环和 TIM7 中断都正常 → 那转速为 0 只可能是编码器这条链路的问题。
- **根因**：**只把电机的 6P 排线插上了 D153C，忘了从 H2 排针飞编码器的两根线**。这个驱动板的设计是：电机座只走电机电流，编码器信号另外从 H2 引出。
- **解决**：飞两根杜邦线 `H2-4(E1A) → PB6`、`H2-3(E1B) → PB7`。
- **判据**：屏上转速立刻从 0 变成 140+ rpm。

### 问题 3：按了按键档位卡死不动

- **现象**：按键按下去没反应，档位卡住。而且是**偶发的**，有时候好有时候坏。
- **定位过程**：`key.c` 原来用的是「全局 `key_locked` 锁 + 四颗键全部松开才解锁」的机制。J-Link 读 `s_idle` 发现有一路电平始终是高——那是 **PA0（WK_UP）**，它走的是**另一套电路**（独立的上拉/下拉网络），和其它三颗键不是一套。
- **根因**：只要 PA0 一直读到高，「四颗键全部松开」这个解锁条件**永远不成立**，锁就永远解不开 → 档位卡死。
- **解决**（架构级的改法）：
  1. **按键消抖和边沿检测全部挪进 TIM7 的 1 ms 中断**（每 5 ms 扫一次、连续 4 次相同才算稳定，即 20 ms 消抖），主循环只负责取「事件」，**没有任何锁**可以卡；
  2. **PA0 完全不参与**按键逻辑，只做下拉输入防止浮空；
  3. 按键的「静止电平」改成**上电后前 200 ms 自学习**（`KEY_LEARN_CNT = 40`，40 × 5 ms），之后判断「!= 静止电平」即为按下——这样**高电平有效和低电平有效两种接法都能自适应**；
  4. 功能分工改成**每颗键各管一件事**：KEY0（PE4）急停 / KEY1（PE3）档位 +1 / KEY2（PE2）档位 −1。
- **顺序坑**：`Key_Init()` **必须排在 `Tim7_Init()` 之前**。因为按键扫描跑在 TIM7 中断里，如果 TIM7 先启动，中断会在引脚还没配置（复位默认浮空输入）的时候就去「学习静止电平」，学到的基线是错的，之后所有按键判断都会反过来。

### 问题 4：屏幕上电流出现负号、读数乱跳

- **现象**：屏幕上 `Cur` 时不时显示负值；运行时读数抖动。
- **定位过程**：一开始怀疑是 ACS712 接反。但如果是极性接反，读数应该**稳定地**全为负；实测是**正负翻转、围绕零点抖动**，所以不是接反，是**零点附近的采样噪声 + 单点采样**。
- **根因（两层）**：
  1. **直接原因**：单点 ADC 采样正好落在校准零点以下，就出一个负值；
  2. **深层原因**（后来做采样链路审计才定量说清）：板上是 **100 Hz 采样**，而 PWM 载波是 **20 kHz = 200 × 100 Hz，是整数倍**。整数倍的异步采样会让 20 kHz 载波**折叠到直流**，表现为零点缓慢漂移——所以这个负号**不是随机噪声，是采样率和载波率的整数倍关系造成的**。
- **解决（分三层）**：
  1. **8 点滑动平均**（`CURRENT_FILTER_WINDOW = 8`），而且**在原始 ADC 码上做平均**（整数运算完全精确，消掉单点的符号翻转），代价是约 70 ms 滞后；
  2. **停机零点在线跟踪**（`Current_TrackZero()`，`α = 0.02`）：只在「占空比 = 0 且转速 < 20 rpm」时执行，把零点慢慢拉向当前读数；一旦电机转起来就**冻结零点**，防止把真实电流吃掉。理由：ACS712 的零点容差 ±1.5% VCC（≈ ±200 mA）而且会随温度漂移，一次上电校准不够；
  3. **换传感器位置**：把 ACS712 从「电池 ↔ 驱动板」之间**改串到「驱动板 ↔ 电机」之间**。母线上测到的是被 20 kHz 斩波、又被驱动板母线电容平滑过的电流；电机引线上测到的是**连续的绕组电流**（电机电感 30.7 mH 把 PWM 滤成了近直流，20 kHz 纹波只有约 4.8 mA 峰峰），读数稳定、量级和符号都正确。
- **判据**：停机时 `Cur` 稳定在 ±0.01 A；运行时读到稳定的正电流；遥测帧的有效性掩码刚好是 **0x3F（63，六路全有效）**。

### 问题 5：100 Hz 采样根本看不到电机的「波形特征」（采样链路审计）

- **现象（起因）**：有人指出「100 Hz 采样会混叠，你的 AI 实际退化成了阈值判断」。我需要判断这个说法对不对。
- **定位过程**：我写了一个脚本（`sampling_audit.py`）只读源码和手册做定量复核，结论是**这个批评是对的，而且比它说的更严重**：
  - 电流通道的有效带宽只有约 **0~5.6 Hz**（100 Hz 采样 + 8 点平均，Nyquist 25 Hz，-3 dB 截止 5.57 Hz）；
  - 20 kHz 载波 = 200 × 100 Hz，**折叠到 0 Hz**；
  - 电机的真实分量全在带宽之外：58% 档输出 145 rpm → 电机本体 2900 rpm → 换向纹波 **145~242 Hz**、齿轮啮合 **387~580 Hz**；
  - **严格证明**：100 Hz 采样下，240 Hz 和 40 Hz 的正弦在采样网格上**逐点相同**（240 = 2×100 + 40），脚本实测两个信号在 64 帧窗口内的**最大逐点差是 3.0×10⁻¹⁵ A**，19 维特征在小数点后 9 位完全一致。也就是说，**真实的 240 Hz 换向纹波和虚构的 40 Hz 信号，在板端 AI 眼里是同一个东西**。
  - 顺带修正了我自己的一个误判：我原来以为母线电流是「导通期满载、续流期为零」的方波，**忽略了驱动板上 220 µF 的母线电容**——电容在 20 kHz 下的容抗只有约 0.036 Ω，会把斩波电流基本旁路掉，所以「偶发负号」的主因更可能是 ACS712 自身噪声（21 mVrms ≈ 113 mA）而不是斩波本身。这个修正我也写进了报告。
- **解决（分三步）**：
  1. **硬件层**：把 ACS712 挪到电机引线（就是问题 4 的第 3 条）——从源头拿到连续、可解释的绕组电流；
  2. **固件层**：新写一个 **20 kHz 高速采样前端（`fastcap.c`）**：用 **ADC2 + DMA2 循环采集** PA5，采样率锁定 20 kHz（= 载波频率），每 10 ms 恰好一帧 200 点；**一帧 200 点的均值就是长度 10 ms 的矩形窗，零点精确落在 100 Hz 的整数倍上**——20 kHz 载波及其谐波被零点吃掉，这就是「载波折叠到直流」的正解，而不是靠后置平均去压。另外支持一次抓 2000 点（100 ms）原始块存 RAM，供 J-Link 导出做 FFT；
  3. **相位锁定**：为了让采样点落在 PWM 的 **ON 窗口中部**（避开开关振铃），我加了 `fastcap_align_to_pwm()`，把 ADC 触发相位锁到 `CNT = 29`（即 14.5 µs）。依据是「ON 窗口内母线电流 = 绕组电流（连续量）」。
- **过程中又踩了三个坑（都是实测定位出来的）**：
  1. **ADC 状态位读错**：我把 `bit4` 当成 OVR。F4 的 ADC 里 **bit4 是 STRT（正常状态）**，**bit5（0x20）才是 OVR**。判据：读到 0x10 是 STRT 不是 OVR。
  2. **循环 DMA 停摆**：DMA 缓冲区回卷后 ADC 不再发请求（NDTR 停在满值、EOC 卡住），根因是 `ADC_DMARequestAfterLastTransferCmd()` 没调用。
  3. **恢复序列竞态**：原来在 ADON 还没真正清 0 之前就清 SR，而且 ADON 和 DMA 请求使能之间有 1 ms 空窗，会自己造出一个 OVR 死循环。改成「等 ADON 清 0 → 复位 DMA → 清 SR → 先开 DMA 请求 → 再开 ADON」。
- **实测判据**：`g_fastcap_frames` 每秒 +100（前端持续出帧）；`g_fastcap_ovr = 0`（无溢出恢复）；手捏负载时原始块的直流均值从停机约 3160 变到 3060~3080（对应约 0.37~0.42 A），**证明采样点确实落在 ON 窗口内、读到的是真实绕组电流**；上位机对 2000 点原始块做 FFT，在 **约 300 Hz** 处看到谱线（与 6 换向片 × 47.7 转/秒 ≈ 286 Hz 吻合）。
- **【诚实边界】** 换向纹波确实存在，但**很弱**（约 17 mA rms，只有负载电流的约 5%），而且比 ACS712 自身噪声（约 113 mA）弱，还叠加了一个固定的约 5.1 kHz 干扰。所以这条路的定位是「**并行的取证/验证路径，可以出 FFT 证据**」，**目前还没有成为 AI 模型的输入**。答辩时不要把它说成「AI 已经在用波形特征」。

### 问题 6：训练数据质量门禁一直失败（每 60 秒出现 8~15 处 21~26 ms 的帧空洞）

- **现象**：连续两次 60 秒采集都 `qualityGatePassed = false`，检查发现帧间隔里有 8~15 处达到 21~26 ms（门禁要求 ≤ 20 ms）。
- **定位过程**：逐项排查主循环里的耗时操作，锁定两个：**软件 I2C 的阻塞延时**、以及**板上旧 AI 库的周期性推理**。
- **根因**：
  1. OLED 的软件 I2C 延时 `I2C_Delay = 40`，太慢，一次刷屏阻塞很久；
  2. 板上旧 NanoEdge 库（round-8 版本）每约 1.5 秒做一次学习/检测，**单次阻塞约 10 ms**——这是 21 ms 空洞的主因。
- **解决**：
  1. `oled.c` 的软件 I2C 提速：`I2C_Delay` 40 → 16（约 100 kHz → 330 kHz，仍在 SSD1306 的 400 kHz 上限内）；
  2. `mpu6050.c` 的软件 I2C 提速：`I2C_Delay` 240 → 40（约 20 kHz → 130 kHz，远低于 400 kHz 上限）；
  3. `ai_monitor.c` 新增 `ai_monitor_set_enabled()`，**纯采集阶段把板上 AI 关掉**（那一轮不需要板上模型），消除它的周期性阻塞。
- **判据**：修复后重采 60 秒 → `qualityGatePassed = true`、`trainingEligible = true`、**6000/6000 帧全部接受、缺帧/拒帧/时序断点全为 0、最大帧间隔 11 ms**。

### 问题 7：电机转速只有 134 rpm（理论上应该 443 rpm）

- **现象**：母线电压 11.3 V（电池健康，约 55% 电量），58% 档转速只有 132~146 rpm，而按 `67.57 rpm/V × 11.3 V × 0.58` 应该是约 443 rpm。而且 20% / 40% 档电机完全不转、也完全不哼。
- **定量分析**：
  ```
  反推电机端实际拿到的电压 = 132 / 67.57 ≈ 1.95 V
  应该拿到 = 11.3 × 0.58 = 6.55 V
  → 回路里丢掉了 4.60 V（占应得电压的 70%）
  → 若为串联电阻：回路 0.15 A ⇒ 约 31 Ω，而 MG310 绕组本身只有 2~5 Ω
  ```
- **已经排除的（都靠实测判据排除，不是猜）**：

  | 曾经怀疑 | 排除依据 |
  |---|---|
  | 固件 / PWM | `CR1 = 0x01`、`ARR = 99`、`CNT ≤ 99`、`CCR1` 随档位精确变化；时基 700 ms 推进 703 ms |
  | 编码器标定 | 满电时 58% 曾经读到 450~520 rpm，与 `13×4×20 = 1040` 完全对得上 |
  | 电池没电 | 屏上 11.3 V 是真的，充电前后扫描数字几乎不变 |
  | 机械堵转 | **58% 跑十秒，电机和驱动板都不烫**。如果是近乎堵转，大电流的 I²R 会在十秒内把电机烘烫 |
  | 静摩擦主导（「只是起步难」） | **58% 转着按 K2 落到 40% 就立刻停**。静摩擦比动摩擦大，如果只是起步难，40% 的 4.52 V 应该能维持它转 |
  | 电源线线型 | 那根红线**本来就是单股实芯线**（是原设计不是断剩的），载流截面正常 |
  | 驱动板（后来） | **换了一块全新的 D153C，转速还是 134 rpm** |
- **关键认识**：屏幕上的 `Bat` 那一格**看不见这 4.6 V**，因为 1/11 分压**只抽约 1 mA**，量到的是**近乎空载**的电压——**它能证明电池是健康的，但证明不了回路的带载能力**。丢掉的电压一定发生在「测压点之后的电路里」，这两件事可以同时成立。
- **当前状态【诚实边界】**：这个低转速问题**至今没有定位**。换新驱动板后仍然是 134 rpm，说明**和驱动板无关**，是一个独立的遗留问题，怀疑方向是电池带载掉压或功率回路的接触电阻。我 2026-10-14 明确决定**暂时搁置**，因为它**不阻塞 AI 闭环**（58% 档转速稳定、电流稳定、特征可复现）。**答辩时如实说「该异常已记录、待排查」，不要编一个原因**——这是我在文档里反复强调的。

### 问题 8：驱动板 TB6612 渐进性损坏 → 输入对地短路

- **现象（三个阶段）**：
  1. 长期只有约 134~143 rpm（就是问题 7 的读数）；
  2. 中途**有一次转速突然飙升到 500+ rpm**，按 RESET 之后恢复；
  3. 最后**一接上电池 D153C 就发烫**（还没按 K1，电机没转）——这说明板子**输入对地已经短路**，TB6612 的桥臂击穿了。
- **定位/证据链**（用来证明这是**渐进性器件老化**，不是我的固件或接线问题）：
  1. 健康的 TB6612 输出级只掉 0.1~0.3 V，而我的板子记录到「输出段丢压约 4.6 V」——**芯片早就在带病工作**；
  2. 那次「转速突然飙到 500+」正是**坏掉的桥臂瞬间给了满电压**（丢压消失），电机短时间回到了规格转速——这是最有力的证据；
  3. 之后 FET 彻底击穿 → 电机堵转 + 驱动板过热 → 输入对地短路。
- **同时也排除了一个嫌疑**：**不是 ACS712 电流接反**。ACS712 的电流端就是一个低阻导体，接反只会让读数符号反，**不改变任何电气行为**，既不会造成短路、也不会让转速飙升。
- **解决**：换一块新 D153C。换完硬件恢复正常。
- **【诚实边界·重要】** 虽然被这个问题折腾了很久，但**换新板后 58% 档转速仍然只有 134 rpm**——所以「低转速」是**独立的老问题**（问题 7），**不是驱动板造成的**。答辩时这两件事要分清，不要说成「换板以后转速就正常了」。

### 问题 9：板上 AI 一直进不了 DETECTING

- **现象**：烧上新库以后，AI 停在 LEARNING 状态不动，或者帧计数器 `g_count` 恒为 0。
- **定位过程**：J-Link 读状态量，发现 `g_count` 恒 0 —— 说明**每一帧都被域门限拦掉了**。追到 `main.c:225`：
  ```c
  d.speed_valid = (d.duty == 0U || d.speed_rpm >= 20.0f) ? 1U : 0U;
  ```
  因为当时电机不转（问题 7/8 的回路故障），`duty = 58` 而 `rpm = 0` → `speed_valid = 0` → 遥测掩码里少一位 → AI 的域门限要求 `validMask == 0x3F`（六路全有效）→ **每帧都被拒**。
- **根因**：不是固件 bug，是**上游电机不转**导致的连锁反应。**副作用是「电机不转 = AI 永远没法演示」**。
- **解决**：修好电机回路（问题 8 的换板）+ 把 AI 训练域明确收敛到「58% 档、六路全有效」，并在文档里写清「**停在档位 0 时 `g_count` 恒 0 是正常现象，不是故障**」——因为档位 0 的帧本来就该被域门限丢掉。
- **判据**：按 K1 升到 L1 后，约 15 秒进入 DETECTING（时间构成：填满首个 64 帧窗口 640 ms，一次 learn 吃 4 个特征块 = 640 ms，22 次 learn ≈ 14 s）。

### 问题 10：正常运行时相似度漂移 → 误报

- **现象**：刚学完的相似度是 87~100，但跑几分钟后掉到 42~63，在阈值附近，长时间运行有误报风险；有时报警也退不掉。
- **定位过程**：读 `g_similarity` 观察趋势，发现是**单调衰减**而不是跳变——说明是工况在缓慢偏离学习态。
- **根因**：板上模型是「开机学一次（22 窗），之后一直检测」。电机运行中工况会漂：**绕组升温、电流零点微漂、电池电压下降**。数据逐渐偏离学习时的那批数据，相似度就慢慢掉下来。
- **解决（两个措施一起上）**：
  1. **周期性重学习**：`AI_MONITOR_RELEARN_DETECTS = 180`——每完成 180 次检测（每次约 640 ms，合计约 115 秒 ≈ **每 2 分钟**）就把 `g_learned` 清零重新学一遍 22 窗（约 14 秒），同时清掉 alarm/lowRun/highRun 状态；
  2. **阈值下调**：**66 → 48**。
- **判据**：重学习上线后，相似度被周期性地拉回高位；实测正常在 42~63，捏紧 9~12，阈值 48 落在两者之间，实测报警/解除都正常。
- **【诚实边界·必须说】** **轻捏转子时相似度在 46~56，和正常（42~63）重叠，分不开**。原因是模型是用「持续用力捏」的数据训练的，对**轻微扰动**不敏感。这是模型对扰动幅度的固有敏感度边界，**演示和测试时要捏紧**。论文里我如实写「对轻微阻力不敏感」。

### 问题 11：新库一上板就重启 / 栈溢出

- **现象**：换成 Library 37 后，程序跑起来不稳定。
- **根因**：新库需要的栈空间比旧库大。原来工程给栈只留了 **1 KB**——旧库（输入 19 个 float）够用，新库（输入 76 个 float，而且内部有预处理链和 ZSM 上下文）1 KB 不够，**溢出**。
- **解决**：把栈从 **1 KB 扩大到 8 KB**。
- **旁证（这个数据很有意思）**：`ZI-data` 从 8464 涨到 16728 字节（含 8 KB 栈），而库本身的 RAM 占用（`preprocessing_ctx` 536 B + `zsm_ctx` 492 B + 1 B = 1032 B）**正好和 Studio 报告的 1.1 KB 对得上**——说明库的资源评估是准的，我只需要给栈留够空间。

### 问题 12：J-Link 在 4 MHz 下烧不进去（RAM check failed）

- **现象**：烧录稳定失败，报
  ```
  Failed to prepare for programming. RAM check failed while testing 0x2050 bytes
  @ addr 0x200006CC  →  Erase returned with error code -1
  ```
  而且**每次失败报的地址都不一样**（0x20000A0C / 0x20000A5C / 0x20000AEC）。
- **定位过程**：这个「地址每次都不同」的模式说明**有东西在持续改写被校验的内存区**。查 `.map` 发现：J-Link 的 RAMCode 和校验区范围是 **0x200006CC ~ 0x2000271C**，而这个范围**正好压在固件的 `.bss` 段和栈上**（本工程的链接脚本把栈紧贴在 ZI 段之后；旧固件 ZI 只到较低地址没冲突，新固件 ZI 已经涨到 0x20002554）。
- **根因**：**4 MHz 下 halt 没有真正生效**，CPU 还在跑，运行中的栈不断改写校验模式。
- **解决**：
  1. **把烧录速度从 4000 kHz 降到 1000 kHz**；
  2. 脚本里显式加 **`h`（halt）**。
  改完**一次就过**。
- **附带确认的一个版本差异**：V4.96d 这个版本的 J-Link Commander **没有 `connect` 命令**（报 `Unknown command`，无害但会带偏排查方向），也**不支持 `-ExitOnError`**（会报 `Unknown command line option` 然后整次都不执行）。我最后定的烧录脚本是：
  ```
  device STM32F407ZG
  speed 1000
  h
  erase
  loadfile <hex> 0x08000000
  r
  g
  exit
  ```
  （脚本必须 **LF 行尾、路径用正斜杠、必须以 `exit` 结尾**——否则 J-Link 会在文件结尾处无限循环写日志，真的把我的硬盘吃掉过 15 GB。）
- **判据**：最终烧录 `Erase 17.46 s → 编程 1 个 range（32768 字节）→ O.K. → Reset`；**回读 1048576 字节，与 HEX 逐字节 0 差异**。

### 问题 13（补充）：电机回路间歇性接触不良

- **现象**：编码器 0 脉冲 + 电流恒等于零点（0 A）同时出现，而且**是间歇性的**（前一天还能正常采集）。
- **定位过程**：J-Link 读 TIM4 的 `CNT`，跨 1.2 秒读三次**完全相同**（5280 不变）→ 编码器完全没脉冲；同时 `g_i_raw_avg` 和上电零点完全相同（3120 ≈ 2.517 V）→ 电流约 0 A。**MCU 侧全部正常（TIM9 的 CR1/CCMR1/CCER/PSC/ARR/CCR1 逐项核对都对）**，问题在电机回路下游。
- **根因（一个故障点同时解释两个现象）**：D153C 的 6P 电机座**一根排线里同时走四类信号**——`pin2/pin6` 是电机驱动电流、`pin3` 是编码器供电、`pin4/pin5` 是编码器信号。所以这根排线（或端子）一松：电机开路（**0 A / 高阻**）+ 编码器失电（**PB6/PB7 浮空、CNT 冻结**）——正好就是我观测到的全部现象，也解释了间歇性。
- **解决**：断电后把 6P 排线两端都拔下来重插，检查端子有没有夹到绝缘皮或氧化发黑。
- **一条通用经验**：**「端子夹到绝缘皮 / 氧化发黑」的典型特征就是「空载正常、带载掉压」，而且接触点会局部发热**——这也是问题 7 低转速的可能方向之一。

## 九、源码解析（重点）

工程结构：`CORE/`（CMSIS + 启动文件）、`FWLIB/`（StdPeriph V1.4）、`USER/`（应用层）、`HARDWARE/`（我写的板级驱动）。下面是按模块的解析。

### 9.1 `USER/main.c` —— 主循环与调度

**核心设计：非阻塞时间片**。主循环里没有任何一处「死等」，全靠比较时间戳：
```c
#define SENSOR_UPDATE_MS 10U    /* 传感器 + 遥测：10 ms */
#define REFRESH_MS       50U    /* OLED：每次只刷一个区域，50 ms 走一步 */
#define VBAT_UPDATE_MS   500U   /* 母线电压：500 ms 一次 */
```
**四个关键变量**（都是「上次执行时刻」）：
- `lastSensorMs`：上次传感器采样的时刻；
- `lastVbatMs`：上次读母线电压的时刻；
- `lastUiMs`：上次刷 OLED 的时刻。

**一个容易被问到的细节**：读母线电压的代码故意放在**给快照打时间戳之前**，而且读完**重新取一次时间**（`nowMs = Encoder_GetMs()`）。原因是 `Vbat_GetVolt()` 里要采 8 次 ADC、还有点延时，如果它发生在打时间戳之后，会把下一个 10 ms 的间隔**压缩**掉。这是一个典型的「慢 I/O 不能挤占快采样的时间基准」的处理。

**档位表**：
```c
static const uint8_t DUTY_LEVEL[2] = { 0U, 58U };   /* 0 档 = 停，1 档 = 58% */
#define LEVEL_MAX 1U
```
（历史上有过 4 档和 L4 自动扫描，2026-10-14 按设计决定收敛成「只有 0 和 58% 两个档位」。）

**主循环流程**：
1. `Key_Scan()` 取按键事件 → 改档位 → `Motor_Config(占空比, 1)`；
2. 500 ms 分支：读母线电压到 `d.vbat_v` / `d.vbat_valid`；
3. 10 ms 分支：读转速、电流、推进 20 kHz 前端、读 MPU6050 快照；
4. 算系统状态（WARN / STOP / RUN / ALARM 四级优先级）；
5. `telemetry_poll(&d, nowMs)` 打包并发送（**同时把同一帧喂给板上 AI**）；
6. 50 ms 分支：`UI_Update(&d)` 刷一个屏幕区域 + 翻转 LED（心跳）。

### 9.2 `HARDWARE/encoder.c/.h` —— 转速

**关键常数（`encoder.h`）**：
```c
#define ENC_PPR    13U     /* 编码器每转脉冲数 */
#define ENC_MULT   4U      /* AB 双边沿四倍频 */
#define ENC_GEAR   20U     /* 减速比 1:20 */
#define ENC_CPR    (ENC_PPR * ENC_MULT * ENC_GEAR)   /* = 1040 */
#define ENC_SAMPLE_MS 100U              /* 每 100 ms 采样一次 */
#define ENC_RPM_PER_CNT 0.576923f       /* 60 / (1040 × 0.1) */
```
**三个到处被问的 API 的区别**（这个我答过好几次）：
- `Encoder_GetRpm()`：**转速**（rpm，恒为正），UI 用的就是这个；
- `Encoder_GetDelta()`：**最近 100 ms 的计数差**（不是累计值！）；
- `Encoder_GetCount()`：TIM4 计数器的**绝对位置**（16 位，65536 回绕）——只有它才能用来标定「转一圈 1040 个脉冲」。

**中断里的采样**：
```c
static void Encoder_Sample(void) {
    int16_t now = (int16_t)TIM_GetCounter(TIM4);
    int16_t delta = (int16_t)(now - s_last_cnt);   /* 用 int16 回绕相减，0↔65535 跨越仍正确 */
    s_last_cnt = now;
    s_delta = delta;
    float rpm = (float)delta * ENC_RPM_PER_CNT;
    if (rpm < 0.0f) rpm = -rpm;    /* 只关心转速大小，取绝对值 */
    s_rpm = rpm;
}
```
**为什么必须放中断**：主循环要刷 OLED，一次刷屏要几十毫秒。如果采样在主循环里做，100 ms 的采样窗口会被刷新延迟拖到 100~160 ms，算出来的转速就忽高忽低。放进 1 ms 中断后，100 ms 窗口的抖动只有微秒级。

**初始化里两个关键点**：
- `TIM_EncoderInterfaceConfig(TIM4, TIM_EncoderMode_TI12, ...)`：**TI12 双边沿模式 = 四倍频**；
- `TIM_ICFilter = 10`：输入滤波，滤掉编码器线上的毛刺。

### 9.3 `HARDWARE/pwm.c` —— 电机驱动

**关键配置**：
```c
TIM_TimeBaseStructure.TIM_Prescaler = 84 - 1;   /* PSC */
TIM_TimeBaseStructure.TIM_Period    = 100 - 1;  /* ARR */
```
**频率推导（一定要会推）**：TIM9 挂在 APB2 上 → APB2 = 84 MHz → 定时器时钟 = 84 × 2 = **168 MHz** → 168 MHz / 84 = **2 MHz** → 2 MHz / 100 = **20 kHz**，周期 **50 µs**。
**一个很好用的巧合**：因为 `ARR = 99`，所以 `TIM_SetCompare1(TIM9, x)` 里的 `x` **直接就等于占空比的百分数**（写 58 就是 58%）。

**STBY 使能**：D153C 的 STBY 引脚硬件没接，引到排针上，所以固件里把 **PA8 配成推挽输出并拉高**：
```c
GPIO_SetBits(GPIOA, GPIO_Pin_8);   /* STBY = 1，使能输出 */
```
**这一行漏了电机就完全不转**——这是驱动板手册的要求（STBY=0 时输出级关闭、电机两端呈高阻）。

**电机转动 API**：
```c
void Motor_Config(uint16_t speed, uint16_t dir) {
    if (dir == 1) { TIM_SetCompare1(TIM9, speed); TIM_SetCompare2(TIM9, 0); }  /* 正转 */
    else          { TIM_SetCompare1(TIM9, 0);     TIM_SetCompare2(TIM9, speed); }  /* 反转 */
}
```
`dir = 1` 时 PE5（AIN1）给 PWM、PE6（AIN2）恒 0，所以**电机端平均电压 = 占空比 × 母线电压**。

### 9.4 `HARDWARE/current.c/.h` —— 电流（OLED 电流数据的来源）

**常数**：
```c
#define ACS712_SENSITIVITY 0.185f   /* V/A，5A 版 */
#define ACS712_VREF        3.30f    /* ADC 参考电压 */
#define ACS712_ADC_FULL    4095.0f  /* 12 位 */
#define ACS712_ADC_AVG     64U      /* 校准时取 64 次平均 */
#define ACS712_ZERO_MIN    2.10f    /* 零点合理性下限 */
#define ACS712_ZERO_MAX    2.90f    /* 零点合理性上限 */
#define CURRENT_FILTER_WINDOW 8U        /* 运行时 8 点滑动平均 */
#define CURRENT_ZERO_TRACK_ALPHA 0.02f  /* 停机零点跟踪系数 */
```
**静态变量**：`g_i_zero`（校准出来的零点电压）、`g_i_valid`（这一路的有效性）、`g_i_raw_history[8]`（滑动平均的历史）、`g_i_raw_avg`（平均后的原始码）。
**核心函数**：
- `Current_Calibrate()`：先 `Motor_Config(0,1)` 确保停转、延时 200 ms，然后采 64 次取平均得到 `g_i_zero`；**如果零点不在 2.10~2.90 V 之间就判 ACS712 没接**（`g_i_valid = 0`）；
- `Current_UpdateFiltered()`：把新读数推进环形缓冲并算平均——**注意这里平均的是「原始 ADC 码」而不是安培值**，整数平均精确，能消掉零点附近的符号翻转；
- `Current_GetAmp()`：`v = raw_avg / 4095 × 3.3`，然后 `return (v − g_i_zero) / 0.185`；
- `Current_TrackZero()`：只在停机时执行，`g_i_zero += 0.02 × (v − g_i_zero)`——一阶低通把零点慢慢拉向当前读数。

### 9.5 `HARDWARE/vbat.c/.h` —— 母线电压

**常数**：`VBAT_DIV_RATIO = 11.0f`（1/11 分压）、`VBAT_ADC_AVG = 8`（8 次平均）、`VBAT_VALID_MIN = 4.0f` / `VBAT_VALID_MAX = 16.0f`（合理范围）。
**公式**：`VM = sum/8 / 4095 × 3.3 × 11`。
**两个设计点**：
- **PA4/PA5 共用 ADC1**：所以 `ADC1_ReadChannel(ch)` 做成通用的——每次调用先 `ADC1->SR = 0` 清所有锁存的状态位、再选通道、再软件启动、然后轮询 EOC 并带超时保护（`ADC1_CONVERT_TIMEOUT = 100000`）。`current.c` 复用同一个函数读 PA5。
- **「传感器在不在」的检测**（`Vbat_CheckPresent()`）：**先把 PA4 配成输出并拉低放电 2 ms**，再配回模拟输入、等 2 ms 后读一次——如果线没接（浮空），放电后电压回不来，读数接近 0；如果接了 D153C 的分压，节点会被分压网络重新充到母线电压的 1/11。这是个很巧妙的「用放电再充电判断有没有源」的办法。
- **等待时间**：ADC 上电后要约 1 µs 稳定，所以 `Vbat_Init()` 里延时 10 ms 才做第一次采样，避免第一枪读到脏值。

### 9.6 `HARDWARE/mpu6050.c/.h` —— 振动（OLED 振动数据的来源）

**这一份是完整手写的软件 I2C**，包含：`I2C_Start` / `I2C_Stop` / `I2C_WriteByte`（含 ACK 检查）/ `I2C_ReadByte`（含 ACK/NACK）/ `I2C_BusRecover`（总线卡死恢复）。
**引脚与地址**：`SCL = PF0`、`SDA = PF1`、`MPU_ADDR = 0x68`（AD0 接地）。
**关键延时**：`I2C_Delay` 里是 `volatile uint16_t i = 40` 的空循环（从 240 优化到 40，约 130 kHz）。
**初始化顺序**（`MPU6050_Init`）：
```c
写 PWR_MGMT_1 = 0x80   /* 软件复位 */  → 延时 100 ms
写 PWR_MGMT_1 = 0x00   /* 唤醒，内部 8 MHz 时钟 */
写 SMPLRT_DIV = 0x00   /* 采样率 1 kHz */
写 ACCEL_CONFIG = 0x00 /* 量程 ±2g */
读 WHO_AM_I  == 0x68 ? s_ok = 1 : s_ok = 0   /* 确认器件在不在 */
```
**振动合成**（`MPU6050_GetSnapshot`）：
```c
x = ax / 16384.0f;  y = ay / 16384.0f;  z = az / 16384.0f;   /* 原始值 → g */
mag = Sqrtf(x*x + y*y + z*z) - 1.0f;                          /* 减去重力 1 g */
if (mag < 0) mag = -mag;                                      /* 取绝对值 */
```
`Sqrtf()` 用**牛顿迭代 6 次**实现，避免为了一次开方引入整个 `math` 库。
**容错设计（这套逻辑我改过两轮）**：
- `MPU_READ_RETRY_COUNT = 2`：单次采样最多重读 2 次——高速运行时允许一次瞬时 NACK，不立刻报警；
- `MPU_READ_FAILURE_LIMIT = 3`：连续 3 次采样都失败才升级为「芯片恢复」；
- `MPU_TryRecover()`：先重配 GPIO、用 9 个 SCL 脉冲释放卡死的总线、写 `PWR_MGMT_1 = 0x80` 复位芯片、重新配置寄存器、核对 `WHO_AM_I`——**最多试 2 轮**，不成功就等 25 次调用（约 250 ms）再试，**绝不无限等待**。
- 另外我在 2026-09-23 修过一个 bug：原来只检查从机地址的 ACK，**寄存器地址字节和数据字节的 NACK 不检查**——结果一次失败的事务会被误判成功。现在**每一个字节的 ACK 都检查**。

### 9.7 `HARDWARE/feature19.c/.h` —— 19 维特征提取（AI 的输入）

**常数**：
```c
#define FEATURE19_WINDOW     64U   /* 窗口 64 帧 = 640 ms */
#define FEATURE19_VIB_WINDOW 32U   /* 振动只用末 32 帧 = 320 ms */
#define FEATURE19_COUNT      19U   /* 19 维 */
#define FEATURE19_STRIDE     16U   /* 步长 16 帧 = 160 ms */
#define FEATURE19_MAX_GAP_MS 20U   /* 帧间隔上限 */
```
**两个核心函数**：
- `check_window()`：**先整体校验再计算**——逐帧检查 `validMask == M2_VALID_ALL`（六路全有效）、`level ≤ 4`、`duty ≤ 88`；逐帧检查 `seq` 严格递增 1（防止回绕掩盖重启）、时间戳递增且间隔 ≤ 20 ms、`level`/`duty` 不变。任一不满足就返回对应的错误码，**输出保持不变**（不会用零或旧值冒充当次结果）。
- `get_stats()`：对指定字段算 5 个统计量：`[均值, RMS, 峰峰值, 总体方差, 波形因子]`。**用两趟算法算方差**（先算均值再算偏差平方和），而不是 `E[x²] − E[x]²`——后者在数值上会严重抵消，浮点精度差。
- `feature19_get()`：按固定顺序填 19 维：
  ```c
  get_stats(frames, 64, 字段0(电流), ×1e-3, &result[0]);   /* 0~4  电流 5 维 */
  get_stats(&frames[32], 32, 字段1(X), ×1e-3, &result[5]);  /* 5~9  X 5 维 */
  ...Y → result[10]...                                     /* 10~14 Y 5 维 */
  result[15] = Z 轴的 RMS;                                  /* 15   Z 只取 RMS */
  result[16] = 转速均值 / 500;                              /* 16   归一化 */
  result[17] = 转速标准差 / 500;                            /* 17 */
  result[18] = 母线电压均值 / 12.6;                          /* 18   归一化 */
  ```
  最后再做一遍**数值合法性检查**（NaN / Inf / 超 float 范围），全通过才写入输出。**任何一步失败，输出都不动**——这是「要么给出可信结果，要么明确失败」的设计原则。
**为什么用 double 累加、float 输出**：累加 64 个数的平方和用 float 会累积明显误差，用 double 累加再转 float 精度足够而内存代价很小（这几个数组是栈上的临时量）。

### 9.8 `HARDWARE/ai_monitor.c/.h` —— 板上 AI（核心）

**状态变量**（都是 `static`，但通过 J-Link 按 `.map` 里的地址能读）：
```c
static M2Frame g_window[FEATURE19_WINDOW];   /* 64 帧滑动窗口，64 × 36 = 2304 字节 */
static size_t  g_count;                       /* 窗口里当前有几帧 */
static float   g_neai_in[76];                 /* 送进库的 76 float 累加器（19 × 4） */
static uint8_t g_neai_fill;                   /* 已经攒了几个样本（0~4） */
static uint32_t g_learned;                    /* 已经学了多少次 */
static uint32_t g_detectCount;                /* 检测了多少次（用于周期重学习） */
static AiMonitorPhase g_phase;                /* OFF / LEARNING / DETECTING / ERROR */
static uint8_t g_similarity;                  /* 最近一次的相似度 0~100 */
static uint8_t g_result_valid;                /* 最近结果是否有效 */
static uint8_t g_initialized;                 /* 库是否初始化成功 */
static uint8_t g_alarm;                       /* 当前是否处于 ALARM */
static uint8_t g_lowRun, g_highRun;           /* 连续低/高于阈值的计数 */
static uint8_t g_enabled = 1U;                /* 板上 AI 开关（采集阶段可关） */
```
**编译期断言**（防止换库导致越界）：
```c
typedef char ai_monitor_input_len_check[
    ((FEATURE19_COUNT * AI_MONITOR_SAMPLES) ==
     (NEAI_INPUT_AXIS_NUMBER * NEAI_INPUT_SIGNAL_LENGTH)) ? 1 : -1];
```
**主函数 `ai_monitor_feed_frame()` 的四道关**：
```c
① 域门限：frame->level != 1 || frame->duty != 58 || validMask != 0x3F → 重置窗口，直接返回
② 连续性：seq != 前一帧 seq+1 或 时间差 > 20 ms → 重置窗口
③ 攒窗口：g_window[g_count++] = *frame；攒满 64 帧才算一次特征
④ 攒样本：特征写进 g_neai_in[g_neai_fill × 19 ...]；攒满 4 个样本才调用库
```
**learn 与 detect 的切换**：
```c
if (g_learned < 22) {                        /* 学习阶段 */
    st = neai_anomalydetection_learn(g_neai_in);
    if (st 是 OK / IN_PROGRESS / DONE) g_learned++;
    g_phase = (g_learned >= 22) ? DETECTING : LEARNING;
} else {                                     /* 检测阶段 */
    st = neai_anomalydetection_detect(g_neai_in, &g_similarity);
    /* 事件级报警：连续 2 窗低于阈值才报警，连续 2 窗高于阈值才解除 */
    if (g_similarity < AI_MONITOR_THRESHOLD) { g_highRun = 0; if (++g_lowRun >= 2) g_alarm = 1; }
    else                                     { g_lowRun  = 0; if (++g_highRun >= 2) g_alarm = 0; }
    /* 周期重学习 */
    if (++g_detectCount >= 180) { g_detectCount = 0; g_learned = 0; g_alarm = 0; ... }
}
g_neai_fill = 0;     /* 非重叠分组：下一次推理必须从全新的 4 帧开始 */
slide_window();      /* 窗口前移 16 帧，保留时序连续 */
```
**关键的三个设计决定（一定会被问）**：
1. **为什么是「非重叠 4 帧分组」而不是重叠滑窗**？因为训练数据是用 `stride = samples = 4` 的非重叠方式打包的。如果推理时用重叠滑窗，会喂给模型**它在训练时从未见过的相位组合**，偏离学到的分布。
2. **为什么报警要「连续 2 窗」而不是单次低于阈值**？这是实测倒逼的：正常运行时相似度会**偶发下探**到阈值以下，单点判定会产生孤立误报。而被捏住的转子会让相似度**连续好几秒**低于阈值——所以用「连续 N 窗」区分「持续异常」和「瞬时抖动」。这一条也是「时序上下文」价值的直接体现。
3. **为什么 `slide_window()` 用 `memmove` 而不是环形缓冲**？因为 `feature19_get()` 要求输入必须是**时间上连续的线性数组**，`memmove` 一次搬 `(64 − 16) × 36 = 1728` 字节，在 168 MHz 上约十几微秒，代价可以接受，换来的是接口简单、不会算错。

### 9.9 `HARDWARE/telemetry.c` + `m2_protocol.c/.h` —— 遥测与 WiFi 数据源

**这一份是 WiFi 链路的 STM32 端**。
**硬件**：USART3，**PB10，AF7**，**57600 8N1**，**只发送不接收**（`USART_Mode_Tx`）——这是有意设计，避免 D1 mini 反过来驱动 STM32 的输入脚。
**帧格式（M2 二进制协议，`m2_protocol.h`）**：
```c
#define M2_SYNC0        0xA5U
#define M2_SYNC1        0x5AU
#define M2_VERSION      0x01U
#define M2_PAYLOAD_SIZE 36U     /* 6 个 int32 物理量 */
#define M2_FRAME_SIZE   42U     /* 2 同步 + 1 版本 + 1 长度 + 36 负载 + 2 CRC */
#define M2_TIMEOUT_MS   3000U   /* 超过 3 秒没新帧 = 链路失效 */
```
**有效性位定义**（这个在答辩里很实用）：
```c
#define M2_VALID_CURRENT (1U << 0)
#define M2_VALID_ACCEL_X (1U << 1)
#define M2_VALID_ACCEL_Y (1U << 2)
#define M2_VALID_ACCEL_Z (1U << 3)
#define M2_VALID_SPEED   (1U << 4)
#define M2_VALID_BATTERY (1U << 5)
#define M2_VALID_ALL     0x3FU      /* = 63，六路全有效 */
```
**发送机制（关键是「不阻塞」）**：
```c
void telemetry_poll(const UI_Data *data, uint32_t nowMs) {
    if (间隔 < 10 ms) return;                     /* 10 ms 一发 */
    if (g_txLength != 0U) { ++g_skipped; return; }/* 上一帧还没发完 → 跳过本帧，不等待 */
    duty = TIM9->CCR1 + TIM9->CCR2;               /* 从寄存器读真实占空比 */
    if (TIM9->ARR != 99 || duty > 88 || level > 4) { ++g_skipped; return; }  /* 参数自检 */
    ...按有效性逐路填充 frame.value[]... 
    ai_monitor_feed_frame(&frame);                /* 同一帧喂给板上 AI */
    length = m2_encode(&frame, g_txBuffer, sizeof(g_txBuffer));
    __DMB(); g_txLength = length; __DMB();        /* 内存屏障后交给中断 */
    USART_ITConfig(USART3, USART_IT_TXE, ENABLE);
}
```
**中断服务**（`USART3_IRQHandler`）**只做一件事：从缓冲区取一个字节塞进数据寄存器**——不做格式化、不做延时、不读传感器。TXE 中断优先级设成**最低的 15**，不干扰 1 ms 的 TIM7 时基。
**物理量缩放**：所有浮点量都缩成整数传输（`m2_scale()`），电流 ×1000 得 mA、转速 ×10、电压 ×1000 得 mV、加速度用 `(raw×1000 + 8192)/16384` 得 mg——**避免浮点的字节序和精度问题**。
**还有一个很实用的设计**：`frame.uptimeMs` 和 `frame.seq` 让上位机能判断「有没有丢帧」。我训练数据的门禁就是靠这两个字段做的。

### 9.10 `HARDWARE/ui.c` + `ui.h` + `oled.c` —— OLED 显示层

**核心设计：数据与显示解耦**。`ui.h` 定义了 `UI_Data` 结构体，传感器代码只往里填数，`ui.c` 只负责画。所以后面加传感器时**显示代码一行都不用改**。
**`UI_Update()` 的分片刷新**（这是性能优化的核心）：
```c
static uint8_t refreshRegion = 0U;    /* 记住上次刷到第几个区域 */
switch (refreshRegion) {
    case 0: 画转速;   break;
    case 1: 画电流;   break;
    case 2: 画振动;   break;
    case 3: 画母线电压 + 状态字; break;
    default: 画底条（AI 阶段 + 档位 + 秒数 + 心跳）; break;
}
refreshRegion = (refreshRegion + 1) % 5;   /* 轮流 */
```
**目的**：软件 I2C 是同步阻塞的，一次重画全部数值会长时间占住主循环、让遥测帧出现空洞。拆成 5 个区域后，单次阻塞时间降到 1/5，而整屏仍然每 5 次调用（250 ms）就更新完一遍。
**无效值的显示**：每一路都有 `xxx_valid` 标志，无效时显示 `--`（转速）、`--.--`（电流）、`--.---`（振动）、`--.-`（电压），并且**状态字强制变成 WARN**（不管其它数据多正常）。这是「宁可显示不知道，也不显示一个假的数」。
**残影处理**：状态字统一 5 个字符宽（`"STOP "` 带一个尾空格），电流/振动在写正数之前先补一个空格——因为正数比负数/无效串**少一列**，不补空格会残留上一次的字符。
**底条的自适应宽度**：电压和无效标记都是 4 列，所以同一个位置不会因为数值位数变化而留下残影。

### 9.11 `HARDWARE/key.c` —— 按键

**三个常数**：`KEY_SCAN_MS = 5`（每 5 ms 扫一次）、`KEY_STABLE_CNT = 4`（连续 4 次相同才认定，即 20 ms 消抖）、`KEY_LEARN_CNT = 40`（上电后 40 × 5 ms = 200 ms 学习静止电平）。
**自学习机制**：
```c
if (s_ready == 0U) {                 /* 阶段一：上电头 200 ms 学静止电平 */
    if (learn == 0U) { s_idle[i] = s_raw[i]; s_down[i] = 0; }
    learn++;
    if (learn >= 40) s_ready = 1U;
    return;
}
/* 阶段二：正常扫描 */
uint8_t down = (s_raw[i] != s_idle[i]) ? 1U : 0U;   /* 和静止电平不同就算按下 */
```
**为什么这么设计**：HIGH 有效和 LOW 有效两种按键接法都能自适应——**不用改代码**。本板实测是低电平有效（静止 1、按下 0）。
**事件只报一次**：只在「状态从松开变按下」的那一瞬间产生一个事件（`s_pending`），主循环取走就清空。这样**按住不放不会连续触发**，而且因为主循环只取事件、没有全局锁，也就没有「档位卡死」的可能（对比问题 3）。
**顺带一个小设计**：`s_hits[3]` 累计每颗键按了多少次，**故意不设上限也不用于逻辑**，就是留给 J-Link 读，用来判断「按键到底有没有被识别到」。

### 9.12 `HARDWARE/fastcap.c/.h` —— 20 kHz 高速采样前端（并行取证路径）

**作用**：用 ADC2 + DMA2 循环采集 PA5，以 **20 kHz**（= PWM 载波频率）连续采样，每 10 ms 恰好一帧 200 点。
**为什么这么做**：一帧 200 点的均值，等效于长度 10 ms 的矩形窗，**零点精确落在 100 Hz 的整数倍上**——20 kHz 载波及其各次谐波被零点吃掉。这是「载波折叠到直流」的正解，比事后做滑动平均强（滑动平均只能压低混叠后的分量，压不掉混叠本身）。
**相位锁定**：`fastcap_align_to_pwm()` 把 ADC 触发相位锁到 PWM 的 **ON 窗口中部**（`FASTCAP_ON_SAMPLE_CNT = 29`，即 14.5 µs，离起沿和落沿各约 14 µs，避开开关振铃）。依据：ON 窗口内母线电流 = 绕组电流（连续量）。
**原始块抓取**：`fastcap_arm_raw()` 一次性抓 **2000 点（100 ms）** 连续原始数据存 RAM（`g_fastcap_raw`，4000 字节），供 J-Link 直接读出，上位机做 FFT 出频谱——这是「换向纹波真实存在」的现场硬证据。
**诊断量**（都是非 static 的全局，方便 J-Link 按符号名读）：`g_fastcap_frames`（累计帧数）、`g_fastcap_ovr`（溢出次数）、`g_fastcap_last`（最近一帧的统计）、`g_fastcap_status`、`g_fastcap_alignTim9/alignTim3`（相位对齐诊断）。
**【诚实边界】** 这个前端目前**只做取证，不参与 AI 特征**（`main.c` 里明确注释「不改 `d.current_a`」）。

### 9.13 上位机与 D1 mini 端（WiFi 连接代码）

#### （1）STM32 端 WiFi 相关代码

见 9.9：`telemetry.c`（USART3/PB10 @57600）+ `m2_protocol.c`（编码 + CRC16 + 帧校验）。**STM32 侧不需要任何 WiFi 或 AT 指令代码**——这是选 D1 mini 方案的最大好处。

#### （2）D1 mini（ESP8266）端

**接线**：D6/GPIO12 ↔ STM32 的 PB10；**只接收**（`g_uart.enableTx(false)`），另外一根共地线。

**软件串口配置**（`d1mini_telemetry.ino`）：
```c
g_uart.begin(9600, SWSERIAL_8N1, 12, -1, false, 512, 2048);
// 参数：波特率, 格式8N1, RX=GPIO12, TX=-1（不给 TX 脚）, 非反相, RX缓冲512, TX缓冲2048
g_uart.enableTx(false);        /* 明确关掉发送 */
```
**`TX = -1` 这一手很关键**：D1 mini 的软件串口如果只给一个引脚，库会进入「单线半双工模式」——那样它可能会去驱动这根线。STM32 的 PB10 是**输出脚**，被对方驱动会造成电气冲突。所以我把 TX 设成 -1、显式禁用发送，**保证这条线永远只有 STM32 在驱动**。

**WiFi 配置**：
```c
WiFi.persistent(false);        /* 不写 Flash，避免反复擦写 */
WiFi.setAutoReconnect(false);  /* 关掉自动重连，避免后台扫描打断串口接收 */
snprintf(g_ssid, sizeof(g_ssid), "Motor-%06X", ESP.getChipId());   /* 热点名带芯片 ID */
/* 16 位随机密码，只存在 RAM 里，通过 USB 串口发小写 p 才打印出来 */
g_apReady = WiFi.mode(WIFI_AP) && WiFi.softAP(g_ssid, g_password, 1, false, 2);
```
**这里有两个刻意的设计**：
- **用 AP 模式（自己当热点）而不是 STA 模式（连路由器）**：现场不需要路由器、不受场地网络限制，手机直接连就行；
- **关掉自动重连**：因为 ESP8266 在 STA 模式下会周期性扫描信道，**扫描会打断软件串口的接收**，造成丢帧。用固定 AP 模式 + 关闭扫描，接收才稳。

**HTTP 服务**（两个路由）：
```c
g_server.on("/", HTTP_GET, [](){                      /* 只读网页 */
    g_server.send_P(200, "text/html; charset=utf-8", MONITOR_PAGE);  /* 页面存在 Flash 里(PROGMEM) */
});
g_server.on("/status", HTTP_GET, send_status);        /* JSON 接口 */
g_server.onNotFound([](){ g_server.send(404, "text/plain", "Not found"); });
```
**主循环（有界工作量的设计）**：
```c
void loop() {
    const int available = g_uart.available();
    if (g_uart.overflow()) {          /* 缓冲区溢出：丢掉残留数据重新同步 */
        m1_discard(&g_receiver);
        for (int i = 0; i < available; ++i) (void)g_uart.read();
    } else {
        for (int i = 0; i < available && i < 512; ++i) {   /* 每次最多处理 512 字节 */
            m1_feed(&g_receiver, (char)g_uart.read(), millis());
        }
    }
    if (g_apReady) g_server.handleClient();   /* 让 HTTP 也能得到执行时间 */
    delay(1);
}
```
**「每次最多处理 512 字节」+ `delay(1)`**：这是为了让 **HTTP 请求和 WiFi 调度不被串口接收饿死**。如果一次把串口缓冲全读完，网页会卡住。
**溢出处理**：`overflow()` 后不是接着读，而是**彻底丢弃并重新同步**——因为已经丢过字节的帧不可能靠继续读来修复，必须等下一个同步头 `A5 5A`。

#### （3）JSON 序列化（`status_json.cpp`）

**最重要的一条设计原则**：**「无效」和「为零」必须能区分**——无效的测量输出 JSON `null`，而不是 0。
```c
for (unsigned i = 0; i < 4; ++i) {
    if (live && (receiver->latest.validMask & (1U << i)) != 0U) {
        snprintf(values[i], sizeof(values[i]), "%ld", (long)receiver->latest.value[i]);
    } else {
        memcpy(values[i], "null", 5U);      /* 无效就是 null，不是 0 */
    }
}
```
输出的 JSON 字段：
```json
{"version":"2.1.9","link":"live","age_ms":12,"level":1,"duty":58,
 "valid_mask":63,"rpm_x10":1460,"current_mA":320,"vibration_mg":15,"battery_mV":11300,
 "frames":2971,"rejected":0,"duplicates":0,"resyncs":0}
```
**字段含义**：`link` 是链路状态（waiting / live / stale）；`age_ms` 是这一帧距今多少毫秒（**用来判断数据是不是过期的**）；`frames/rejected/duplicates/resyncs` 是接收统计（**用来判断链路有没有丢帧**）。
**链路超时**：超过 `M2_TIMEOUT_MS = 3000` 毫秒没有新帧，`link` 就变成 `stale`，网页上相关数值显示 `--`。
**网页端**：`monitor_page.h` 把整个 HTML 页面以 `PROGMEM` 常量存在 Flash 里（这样 RAM 只用来跑逻辑），页面每 1 秒重新请求一次 `/status`，请求超时 2.2 秒。

#### （4）实测验收结果

- **跨板通信实测通过**：手机连上 D1 的热点后，网页能显示有效帧数持续递增（290 → 481），异常帧始终为 0，数据年龄 0.3 s；
- **D1 固件正式部署**：版本 2.1.9，独立回读校验通过；
- **断线/恢复行为**：手机 WiFi 断开再连、STM32 按 RESET 停发，页面都能正确显示 waiting/stale 并在恢复后自动回到 live；
- **主机侧测试**：协议编解码 53360 项检查通过、遥测发送 369 项通过、浏览器模拟 320/390/1280 三种屏宽无横向溢出。

## 十、评委可能追问的问题（补充弹药）

### 关于技术选型

**Q：为什么用 NanoEdge AI 而不是自己训练一个神经网络？**
A：三个理由。① 它针对 MCU 做了极致的模型压缩和代码生成，导出的库 RAM 只占 1.1 KB、Flash 0.5 KB——手写一个 TFLite Micro 模型光解释器就几十 KB；② 它自动搜索了 3066 个候选模型（ICM/MML/ZSM/iPCA 四类算法 + 降维组合），这个搜索量手工做不出来；③ 它导出的库能直接用 Keil 的 AC5 编译器链进去，工具链打通了。
**代价**：它是**黑盒**，模型的内部结构和权重看不见，所以我在论文里只能报告「输入是什么、输出是什么、指标是多少」，不能像手写模型那样做逐层分析。

**Q：为什么输入是「19 轴 × 4 样本」而不是「19 轴 × 1」？**
A：因为「4 个连续样本」给了模型约 1.1 秒（4 × 160 ms 步长）的**时序上下文**。只给 1 帧的话，模型看到的是瞬时快照；给 4 帧，它能看到这一段时间内特征是怎么演化的。实测这个版本（Time Series，76 列）和早先的 Cross-Sectional 版本（19 列）在各自数据上都是 100%，但 Time Series 版本多了「区分持续异常和瞬时抖动」的能力——这也是我为什么要用「连续 2 窗才报警」的物理依据。

**Q：为什么阈值定 48？**
A：用库自带的 PC 模拟器跑的（模拟器跑的是和板上**完全相同的 C 代码**，所以主机和板上的结果一致）。在训练数据上实测：正常相似度最小值 95、中位数 100；捏住最大值 37、中位数 19。两类完全不重叠，**理论上 38~95 之间任何值都能分开**。原来是 66（两类极值的中点），但上板后发现正常相似度会**随运行漂移到 42~63**（工况漂移），66 会造成误报，所以下调到 **48**——同时配了周期重学习把相似度周期性地拉回高位。这两个措施是配套的。

**Q：为什么栈要给 8 KB 这么多？**
A：因为我实测 1 KB 会溢出（新库的预处理链 + ZSM 上下文比旧库用的栈深）。STM32F407 有 192 KB SRAM，我整个固件的 ZI 段加起来才 16728 字节，给栈 8 KB 完全负担得起——没必要为了省几百字节去冒溢出的风险。

### 关于数据与结论

**Q：你的 100% 准确率是不是过拟合？**
A：**准确说是「会话内」的准确率，不能当泛化能力**。我的正常样本和模型学习用的是同一次采集会话，只有「捏住」那 278 个是真正样本外的。不过有一点可以支撑它不是偶然：Studio 内部做了 **50 折交叉验证**，每一折的 balanced accuracy / F1 / MCC 都是 1.0000，标准差是 0——所以它不是单次数据划分的偶然。**要谈泛化必须另采一次独立会话的留出数据**，这个我在文档里明确写了。

**Q：为什么轻捏不报警？**
A：因为模型是用「持续用力捏」的数据训练的，对**轻微扰动**不敏感。实测轻捏的相似度落在 46~56，而正常（漂移后）是 42~63——两者重叠，分不开；捏紧时相似度掉到 9~12，能稳定触发。这是模型对扰动幅度的**固有敏感度边界**，不是 bug。要改善需要在训练集里加入各种幅度的扰动样本。**演示时捏紧就行**。

**Q：你说要「周期重学习」，那不就有 14 秒不检测的盲区吗？**
A：对，这是一个明确的**代价**。重学习期间（22 窗约 14 秒）不检测、不报警。我判断这个代价可以接受，因为：① 重学习是每约 2 分钟一次，占比约 12%；② 电机工况漂移是分钟级的慢过程，不是秒级的，14 秒的盲区不会漏掉真正的突发故障（突发故障表现为电流/转速突变，会被系统的有效性检查和多变量异常捕捉到）。如果要求更严，可以做成「新旧两个模型并行检测、学完再切换」，代价是 RAM 翻倍。

### 关于局限

**Q：你这个方案有什么局限？**
A：要说的话有四条，我都写在文档里了：
1. **19 维特征全是幅值统计**，没有波形频率特征。所以对「平均负载不变、只是纹波结构变了」这类故障（不平衡、齿面损伤）的分辨能力有限。我已经做了 20 kHz 高速采样前端来补这个短板，也拿到了 FFT 证据，但**还没接入模型**——这是下一步工作。
2. **模型只覆盖 58% 单一下载工况**。换占空比、换负载水平、换另一台电机都不保证有效（这是**有意的设计边界**，不是缺陷，工程上叫「限定工况的专用监测器」）。
3. **低转速问题未定位**：实测 134 rpm vs 理论 443 rpm，已排除固件、编码器、电池、机械堵转、驱动板，怀疑方向是电池带载掉压或回路接触电阻，待排查。
4. **没有做长期稳定性测试**：所有验收都是分钟级的，没有跑过几小时/几天的连续运行。

**Q：如果让你重新做，你会怎么改？**
A：三件事，按优先级：
1. **先做采样链路设计，再做特征和模型**。我这次是先把 100 Hz 的 AI 闭环做完了，才回头审计采样链路，发现带宽只有 5.6 Hz、载波折叠到直流——等于地基没打牢就盖了楼。重来的话我会先定「要检测的故障对应的频段是多少」，再反推采样率和传感器带宽。
2. **训练数据要分成训练会话和验证会话**，从一开始就保证有干净的留出集，这样准确率才敢往论文里写。
3. **直接选带抗混叠的传感器方案**（比如 INA240 + 采样电阻，噪声比 ACS712 低一个数量级），而不是用模块 + 后期补偿。
