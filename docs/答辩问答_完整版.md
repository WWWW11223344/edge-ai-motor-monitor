**【一句话项目定位】** 在 STM32F407 上用编码器测转速、用母线电压做归一化，把两者合成 **q = 转速 / 母线电压（rpm/V）**，再取它在 0.8 s 内的**滚动峰峰值 PtP**，按 100 ms 节拍攒成 32 点的定长序列（3.2 秒），交给 ST 的 NanoEdge AI 训练出的半监督异常检测模型（**68 号 ICM 库**）；同时用 **dR = 32 点窗内的峰峰值**做一条不依赖模型的显式判据（门限 1.0 rpm/V），**两条判据并联**。在 MCU 本地判断「电机被额外加载 / 卡滞」，本地 OLED 报警并把数据通过 WiFi 推到手机网页。

**【与早期版本的关键差异】** 本项目早期方案是「编码器 + ACS712 + MPU6050 三路传感器 → 19 维特征」。2026-10-19 做完单变量筛选后**收敛为单变量 R**，MPU6050 已彻底摘除（源码移入 `HARDWARE\_removed_mpu6050_20261019\`），模型从 Library 37 换成 Library 44，2026-10-21 又换成 **Library 68（ICM）**；判决量同时从 R 的水平值换成 **dR 峰峰值**，档位从单档 58% 扩到 **58% / 64% 两档**。答辩时如果手上有旧材料，以本文为准。

## 一、项目概述

### 口述版

我这个项目做的是**电机状态监控**。场景是这样：工业现场和机器人上大量使用直流减速电机，电机一旦卡死、齿面损伤、轴承磨损，轻则停机重则烧电机，而人工巡检不可能 24 小时盯着。所以我做的是一个**能自己判断电机正常不正常、并且把结果直接显示在当地屏幕和手机上的小系统**。

具体做的事情是：用 STM32F407 做主控，用编码器测转速、用母线电压做参照，两者相除得到一个「单位电压转速」R = rpm/V；每 100 毫秒采一个点，攒满 32 个点（3.2 秒）送进一个用 NanoEdge AI 训练出来的半监督异常检测模型，模型输出一个 0~100 的「相似度」，相似度低于阈值就报警。整个过程**不需要上位机、不需要联网也能工作**——这就是边缘 AI 的意思。

系统一共四个核心功能：**电机启停与急停控制**、**转速/电流/母线电压的实时采集与 OLED 本地显示**、**板上边缘 AI 异常检测与报警**、**WiFi 上传到手机网页远程监控**。

### 背景与目标

- **背景**：电机故障诊断传统做法是「把振动信号传到电脑上做 FFT 分析」。但工业现场很多场合没有电脑、没有稳定网络，而且数据传上去再判断，延迟大、隐私和带宽都是问题。把模型直接塞进 MCU，让设备**自己会判断**，是这几年的主流方向，也是 ST、NXP 这些厂商主推的「TinyML / 边缘 AI」。
- **目标**（四条，都能验收）：
  1. 转速、电流、母线电压能在 100 Hz 下稳定采集，不丢帧；
  2. 特征必须**不受电池电量影响**——这是我做 R 归一化的出发点；
  3. 异常检测模型能真正跑在 STM32 上，而不只是在电脑上跑仿真；
  4. 从「电机被捏住」到「屏幕上出现 ALARM」整条链路能现场演示通。

### 核心功能与实现路径

| 功能 | 实现方式 |
|---|---|
| 电机启停 | TIM9 输出 20 kHz PWM，PE5 → D153C 的 BIN1，占空比三档 `0`（停）/ `58%` / `64%` |
| 急停 | KEY0（PE4）按下立刻把档位归零、PWM 清 0 |
| 转速测量 | 编码器 A/B 相 → PB6/PB7 → TIM4 硬件编码器模式四倍频计数 → 每 100 ms 算一次 rpm |
| 电流测量 | ACS712 → PA5（ADC1_IN5）→ 8 点滑动平均 → 零点在线跟踪（**只做显示，不进 AI**） |
| 母线电压 | D153C 的 1/11 分压 → PA4（ADC1_IN4）→ 500 ms 一次 |
| 特征提取 | **R_new = (rpm / vbat) × (58 − 50) / (duty − 50)**（膝点归一化）；判决量取窗内 **dR = 峰峰值(rpm / vbat)**。100 ms 一点，32 点一窗 = 3.2 s |
| 边缘 AI | 32 点 PtP 序列 → NanoEdge **Library 68**（ICM，3 维特征 + 35 聚类中心）→ 相似度 0~100 → 事件级报警 |
| 远程监控 | USART3（PB10，AF7）57600 8N1 发 42 字节二进制帧 → D1 mini → WiFi AP + 只读网页 |
| 数据留档 | 20 kHz 高速采样前端（ADC2 + DMA）并行抓原始块，供 J-Link 导出做 FFT |

### 系统数据流（一句话串起来）

```
编码器 + ACS712 + 母线分压 → 每 10 ms 采一帧
   ├─→ OLED 显示（分片刷新，50 ms 一轮）
   ├─→ feature_r：每 100 ms 算一个 R 推入 32 点窗 → 窗满交 AI
   └─→ USART3 二进制帧（42 字节含 CRC16）→ D1 mini → 手机网页
```

### 可能追问

- **« 你这个和市面上的电机保护器有什么区别？ »**
  市面上的热继电器/保护器是**事后保护**：靠电流过载发热才动作，响应慢、而且只能判断「过载」。我做的是**过程中的状态识别**：用「单位电压转速」在负载还没到危险程度时就能识别出工况偏离正常态，而且能本地显示、能远程看。
- **« 为什么不直接用现成的 PLC 或工控机？ »**
  成本和一个 MCU 差两个数量级，而且现场很多点位根本放不下工控机。这个方案新增采购 **¥244.50**（开发板由实验室提供不计），软件授权 0 元——NanoEdge AI Studio 从 V4.3 起对全部 STM32 型号免费无限量。
- **« 你这个项目最难的地方在哪？ »**
  不是写 AI，是**把数据采干净**、以及**想清楚「什么量真的能反映负载」**。我在第八节有完整记录：板子上的 100 Hz 采样和 20 kHz 的 PWM 载波正好是整数倍关系，载波会折叠到直流，导致电流读数出现假负号；而更要紧的是我发现**裸转速根本不能当特征**——电池从 12.6 V 掉到 11.3 V 本身就让转速掉 11%，和「被捏住」造成的 17% 完全重叠。这一步推理是我整个方案的分水岭。

### 逐个说明「为什么选它」

**1. STM32F407ZGT6（神舟号 V2.0 开发板）**
选它的三个理由：① **有 FPU（浮点运算单元）**——这一点对本项目是刚需，因为特征计算和 AI 推理都是浮点，带 FPU 的 M4 比不带的速度差 10 倍以上；② 168 MHz 主频 + 192 KB SRAM，装得下 AI 库（Library 68 只要 **3668 B RAM / 3108 B Flash**，极其宽裕）；③ 板载资源多（OLED 用的 I2C、串口用的 CH340C、以太网 PHY 都有），省外围器件。
**代价**：这块板的 PA1、PA7、PC3、PC4 被板载以太网 PHY（LAN8720A）占用，**不能拿来用**。我最初的编码器方案本来设计在 PA6/PA7，查原理图发现 PA7 = RMII_CRS_DV 被 PHY 占了，才改成 PB6/PB7。

**2. WHEELTEC MG310 减速电机**
选它的原因：**自带霍尔编码器**（13 线），不用另外装测速装置，而且轮趣提供了完整的手册（Ke = 0.00064 V/rpm、电感 30.7 mH、减速比 1:20 这些参数我都是从手册表 4-1/4-2 查的）。额定 7.4 V、空载 500 rpm、堵转 2 A，正好在 ACS712-05B 的 5 A 量程内。

**3. WHEELTEC D153C 驱动板（TB6612FNG）**
选它是因为**不用焊接**——它的接口是**排针**，我全程用杜邦线接的，符合我的硬约束（零焊接）。TB6612FNG 是双 H 桥，支持 VM 4.5~13.5 V，PWM 频率上限 100 kHz（我用 20 kHz 很安全）。
这里面有两个必须讲清楚的接线点：
- **STBY 引脚**：D153C 手册写 STBY=1 才能输出，硬件上它没接、引到排针上，所以我在固件里把 **PA8 配成推挽输出并拉高**来使能。**这个漏了电机就完全不转。**
- **PWMB/BIN1**：我这一路用的是 **B 通道（MOTORC1 / Motor_B）**，PWMB 硬接 3V3，BIN1 接 PE5 走 PWM、BIN2 接 PE6 恒 0。这样电机端平均电压 = 占空比 × 母线电压。

**4. ACS712-05B 电流传感器模块**
选它的原因：**成品模块、有现成排针、零焊接**，而且是霍尔隔离型，串在主回路里不共地也没关系。5 A 量程够用（MG310 堵转 2 A）。
必须钉死的两个数字：**灵敏度 185 mV/A**，**零点是 VCC/2 = 2.5 V（不是 1.65 V！）**。网上很多资料写 1.65 V，那是把 3.3 V 供电版的参数套到 5 V 模块上，如果用 1.65 V 当零点，会引入约 +4.6 A 的固定偏差，整个电流通道直接废掉。
**接的位置也很关键**：最终我把 ACS712 **串在驱动板和电机之间**（不是电池和驱动板之间）。原因见第八节问题 4——串在母线上测到的是被 20 kHz 斩波、又被母线电容平滑过的电流，读数抖且符号不稳；串到电机引线上，测的是电机的**连续绕组电流**，读数稳定、量级正确。
**【诚实边界】这一路最终没有进 AI**：实测空载 0.04 A、捏住 0.06~0.10 A，而 ACS712 自身的噪声就有 ±0.03 A——信噪比约等于 1，物理上区分不开。这个否决过程见第六节 6.9。

**5. 为什么最终摘掉了 MPU6050（这是一个加分点，主动讲）**
早期方案里 MPU6050 是「振动通道」，我在它上面写过完整的软件 I2C、总线卡死恢复、失败重试三级容错。但 2026-10-19 做单变量筛选时结论很明确：
- **单变量 R 已经能分开正常与异常**（58% 档正常 6 批 13.23~13.53 rpm/V，握持 3 批 10.79~11.07 rpm/V，阈值取 12.0 时正常窗零误报、异常窗全检出）；这一版换成 dR 判决后更硬——正常 p99 只有 0.554、捏轴中位数 3.555，门限 1.0 的两侧余量分别是 1.8 倍与 3.5 倍；
- 所以我把 MPU6050 连同 `mpu6050.c/.h`、19 维特征模块一起摘除，模型输入从 19 维收敛到 1 维 × 32 点。**摘除后重新编译，hex 与摘除前逐字节相同**（说明原代码里那条通道已经被判为死代码，摘得很干净）。

**6. OLED（0.96 寸，128×64，SSD1306 / SSD1315 兼容）**
选它的原因：I2C 只要两根线（PB8/PB9 是板载 I2C，自带 4.7 k 上拉，连上拉电阻都省了），而且 128×64 够我排 4 行数据。
**这里有个我自己做的设计**：8 页（每页 8 像素）全部排满，用**两种字号混排**——转速、电流、R 用 8×16 大字号（各占 2 页），母线电压 + 状态字用 6×8 小字号（占 1 页），底条占 1 页，正好 8 页不浪费。

**7. 3S 锂电池（这一节直接回答「为什么只有一个档位」）**
选它的原因：驱动板要 4.5~13.5 V，3S 锂电标称 10.8 V、满充 12.6 V，正好在范围内；而且锂电带载能力强，比 USB 供电可靠。
**但这里埋了本工程最棘手的一个物理约束**：
- MG310 额定 **7.4 V**，而 3S 电池是 **11.1~12.6 V**——**电压不匹配，高了一档**；
- 要落到 7.4 V，占空比只能是 **7.4 / 12.6 ≈ 58%**，这就是 58% 这个数字的物理来源；
- **【2026-10-21 修正：这一段我早先写错了，现在收回】** 我曾记下「58% 档电机两端只有 1.96 V」与「满电时 58% 曾到 450~520 rpm」两个数，并据此推断工作点落在非线性区。**这两个数都是测量误判，已作废**：1.96 V 约等于 3.3 V × 0.594，是万用表直流档读 PWM 波形读出的**平均值**，不是电机端真实电压；450~520 rpm 则把别的档位的读数记成了 58%（74% 档才到 500+ rpm）。**决定性反证**是换上一块全新 D153C 后，在 11.87 V 母线电压下实测 **58% → 140 rpm、64% → 245 rpm、66% → 280 rpm**，与旧板的 142 rpm 完全一致——**旧板从来没有退化过**。
- 真实规律是**干净的线性**：`rpm ≈ 17.5 × (duty − 50)`，死区正好落在 **50%**。58% → 140 rpm（实测 140.0，完全吻合）、64% → 245 rpm（实测 245~262，58% 以上略上翘）、46% 代入为负值——这就解释了为什么低档起不来。可用区间只有 **50%~70%**：下限是静摩擦死区，上限是 3S 电池保护板（74% 直接拉闸）。原来那个「58% → 63% 跨不过去」也是错的——63% 那次是把归一化分母写成了 `duty`，改用 `(duty − 50)` 后 58 / 64 两档跨档残差只剩 **6.3%**，再由 dR 判据彻底绕开（详见问题 15）。
- 所以档位少的真实原因是**起动死区吃掉了一半刻度 + 保护板砍掉了上半段**，不是未定位的非线性。现在**已经有两个可用档位**（58% / 64%），不是只有一个。改进方向仍要算过账才敢说：**换 2S 电池不行**——电机端真正可用的窗口由「死区 + 额定上限」决定，换电池只是把它挪到占空比的另一段，宽度不变，还得另配 8.4 V 充电器（3S 充电器不能复用）。真正的做法是**把电机额定电压抬到与母线匹配**：换 12 V 额定电机，3S 12.6 V 下死区占比从 50% 降到 40%，可用区间约 40%~95%，档位数立刻能加上去。这一点答辩时要主动说，它把「缺陷」变成了「已定位的设计约束 + 算过账的改进路径」。
- 另外拿电脑 USB 的 5 V 给驱动板供电是**撑不住的**，电机一加速就把 USB 拉垮触发过流保护，要拔插一次才恢复。

**8. Wemos D1 mini（ESP8266）**
选它的原因：**它自己会连 WiFi、自己会跑 HTTP 服务器**，所以 STM32 侧只需要往串口发数据，**一行 AT 指令代码都不用写**。这是成本最低的方案。
接线：D1 的 D6/GPIO12 接 STM32 的 **PB10（USART3_TX）**，只用一根数据线 + 一根共地，**单向**（D1 只收不发，不驱动 STM32 的输入脚，避免电气冲突）。D1 用 USB 单独供电。
**顺带一个引脚排错**：原始硬件图上 PB10 标注是「P9 排针第 30 脚」，网上有些资料写成 P8，我对着图纸核对过是 **P9-30**。

### 整体接线的关键事实（可现场照着复述）

- 编码器：**必须从 D153C 的 H2 排针飞线**——`H2-2(E2A)→PB6`、`H2-1(E2B)→PB7`。**漏了这两根，屏上 Spd 永远 0**（我只插了电机 6P 排线就踩过这个坑）。
- 母线电压：`H2-5(ADC)→PA4`，板上有 10 k + 1 k 分压（1/11），直接接不会烧引脚。
- 6P 电机排线里同时走**电机电流（pin2/pin6）、编码器供电（pin3）、编码器信号（pin4/pin5）**——所以这根排线一松，会出现「电机不转 + 编码器也没脉冲」两个现象同时发生。这一点是我后面定性的关键依据。

### 每样工具的具体用法

**Keil MDK + StdPeriph V1.4**
整个固件是**四层结构**：`CORE/`（CMSIS 和启动文件）、`FWLIB/`（标准外设库）、`USER/`（`main.c`、中断服务、工程文件）、`HARDWARE/`（我自己写的板级驱动）。工程经过精简，从 57 个编译单元砍到 **27 个**（FWLIB 只保留 misc/adc/dma/gpio/rcc/tim/usart）。
编译我用**命令行**跑，因为可以接进自动化脚本：
```
UV4.exe -b USER\STM32F407_Template.uvprojx -j0 -o build.log
```
**判据**：退出码 0 = 编译成功（不是「没输出」）；日志是 GBK 编码；成功时会打印 `Program Size: Code=... RO-data=... RW-data=... ZI-data=...`。
最终版本：**Code = 22288 字节，RO-data = 6548，RW-data = 264，ZI-data = 17992，0 Error 0 Warning**。
**J-Link Commander —— 这个工具在我项目里的作用远不止烧录**
除了烧录，我做的最重要的一件事是**远程读内存调试**。原理是：Keil 编译后会生成 `.map` 文件，里面有所有全局/静态变量的**绝对地址**；然后用 J-Link 脚本 `mem32 <地址> <字数>` 直接读 RAM，就能在不打断程序运行的情况下看变量。
这一招在项目里救了我三次：一次是确认 PWM 的 `TIM9->CR1` 是不是被污染、`CNT` 有没有超过 `ARR`；一次是逐帧确认编码器计数器和 AI 的状态量是不是在推进；还有一次是**在电机转着的时候远程把 CCR 写进去强制起转**，验证归一化公式算得对不对。
判据很直观：**读 `s_ms` 两次，间隔 500 ms，差值 ≈ 500 就说明程序在正常跑**。

**NanoEdge AI Studio 5.2**
用它的五步流程（Project Settings → Signals → Benchmark → Validation → Deployment）训练异常检测模型，最后导出可以直接链进 Keil 工程的静态库 `.a`。细节见第六节。
一个环境事实：**从 V4.3 起，NanoEdge AI Studio 对全部 STM32 型号免费、无限量**，所以这个工具链是零成本的。

**Python 上位机脚本**
负责三件事：① 解析 STM32 发出来的二进制帧，检查时序连续性（这是数据能不能用来训练的**门禁**）；② 按和板端**逐位一致**的算法算 R，并按 32 点一窗、不重叠切块，导出成 NanoEdge 能读的 CSV（**每行恒 32 个数字、无表头、无标签**）；③ 把 20 kHz 原始采样块做 FFT，验证换向纹波这些频率分量真实存在。

**PowerShell 自动化脚本**
把「编译 → 备份原固件 → 烧录 → **独立回读并逐字节比对**」串成一条命令。最后这一步很重要：烧完之后把 Flash 整个读回来，和 HEX 文件比对，**差异 0 字节**才算烧录成功。

## 四、边缘 AI 与状态检测

### 口述版

**边缘 AI 是什么**：传统做法是把传感器数据全部传到云端或电脑上，在那边跑模型，再把结果传回来。边缘 AI（也叫 TinyML）是把**训练好的模型直接部署在设备本地的 MCU 上**，数据不出设备，本地就算出结果。好处有三个：**不依赖网络**（断网照常工作）、**响应快**（不用等网络往返）、**数据不出本地**（隐私和带宽都省了）。

**我这个项目怎么体现边缘 AI**：
模型是「在电脑上用 NanoEdge AI Studio 训练、导出成一个 `.a` 静态库、然后**链进 STM32 的 Keil 工程**、和我的固件一起编译成 HEX 烧进 MCU」。上电以后，**STM32 自己在板上跑推理**，整个过程不需要电脑参与。我验证过：板上的 `neai_anomalydetection_init(true)` 返回成功、`g_initialized = 1`，而且**库自带训练时学到的预训练知识，上电第一窗满就出相似度，不需要现场学基线**——这是这一版相对上一版最直观的变化。
**为什么只用「转速 / 电压」这一个量**（这是必答题）：
因为我实测过，**电压变化会把转速搅乱**。电池从满电 12.6 V 掉到 11.3 V，转速自己就掉 11%；而「被捏住」只让转速掉 17%。这两个数字在裸转速上**几乎重叠**，低电量时必然误报。把转速除以母线电压之后，电量变化被约掉了，R 就只反映电机本身的负载状态——58% 档实测正常 R 落在 **13.0~13.8**，捏住落在 **10.2~11.7**，同一档内两类自然分开。

但换一个档位，两簇会整体平移（64% 档分别是 **20.6~22.1** 与 **18.1~18.5**），所以判决层最终没用 R 的水平值，而是用它的**窗内峰峰值 dR**——这个量的跨档绝对差只有 **0.035 rpm/V**，一套阈值就能通吃两档。
**状态检测是怎么实现的**：
用的是**半监督异常检测**。也就是说我只给模型「电机正常运行时」的数据，不给它故障样本。原理是模型学出正常数据的分布，运行时算当前数据和「学到的正常态」有多像，输出一个 **0~100 的相似度**。相似度低 = 偏离正常 = 异常。
具体到板上的流程：
1. 上电后 `neai_anomalydetection_init(true)` 直接用库内预训练知识，**直接进 DETECTING（屏上显示 DET）**，不需要现场学基线；
2. 电机升到 58% 档、攒满第一窗（32 点 × 100 ms = 3.2 s）就出第一个相似度，之后每推进一点推理一次；
3. 相似度**连续 2 窗**低于阈值 **32** → 置 ALARM（状态栏显示 ALARM，PF9 红灯亮）；
4. 相似度**连续 2 窗**回到阈值以上 → 解除 ALARM；
5. 每 6000 次检测（约 10 分钟）用当前窗做一次增量 `learn`，跟上工况漂移（热机）；停转 0.5 s 只清报警与计数，保留知识，起转即恢复判定。
### 支撑细节

- **为什么用半监督而不是有监督**：现场拿到「电机坏了」的样本成本极高（要真把电机弄坏），而「正常运行」的数据随手可得。半监督只要求正常数据，更符合工程实际。
- **为什么这一版不要求「每次上电重学」**：上一版是 ZSM，32 点被池化成一个均值，样本量小、对温度敏感，所以必须上电重学。这一版换成 ICM，抽出的是 n95、peak_value、n25 三个特征，对峰的形状有分辨力，热机后相似度仍在阈值以上，实测不需要重学。真正需要跟上工况漂移时，靠的是第 5 条那个增量 `learn`——它是「补一点」，不是「清空重来」，所以不打断检测。
### 【诚实边界】（这一条答辩时一定要主动说，能加分）

**我这个模型不是深度学习，库里没有神经网络、也没有梯度下降。** 我是从库文件和 metadata 里把结构解出来的，不是猜的：

- 元信息：`input_size = 3`、`clust_nbr = 35`、`norm1 = 1`、`sensitivity = 0.5`；
- 预处理链三步：`absolute`（取绝对值）→ `extract_features(n95, peak_value, n25)`（从 32 点里抽三个特征：95 分位、峰值、25 分位）→ `interleaved`（三维交织成一个序列）；
- 判决方式：算这 3 个特征到 35 个聚类中心的最近距离（L1 范数），再经 `sensitivity = 0.5` 映射成 0~100 的相似度。

所以它的本质是**「以 35 个正常聚类中心为参照的距离度量」**，不是会自己发现新特征的网络。这一点必须主动说，因为评审一定会问「你这算 AI 吗」。

那它相对手写阈值的价值是什么？三点，都是真的：
1. **判据不是一行 if**：手写阈值只能卡「一个数落在哪个区间」；这里卡的是三个特征的联合距离，能区分「窗内一直偏低」与「窗内只掉了一下」两种形态。后者正是捏轴松开后的典型残余——上一版 ZSM 把 32 点池化成 1 个均值，这两种形态在它眼里完全一样。同一份数据、同样 32 点输入，**ZSM 只检出 58.9%，ICM 检出 92.0%**（离线预估 87.0%）；
2. **中心是学出来的**：35 个中心不是拍脑袋定的，是训练时从 2252 个正常窗里聚出来的，换一台电机、换一次装配，重训一次就跟着走；
3. **32 点窗本身带 3.2 秒平滑**：单点噪声被峰的统计量吸收掉，不会因为一个坏点就报警——这是「窗」这个结构带来的，纯阈值做不到。
**以及我为什么接受这个结论**：因为我的单变量分析早就证明了**这个任务本身就是一维可分的**——固定阈值 12.0 就能做到正常 0% 误报、异常 100% 检出。在一个一维可分的任务上，硬堆一个多维深度模型只是把简单问题复杂化。**我没有把它包装成「我训练了一个神经网络」，论文里写的就是「单变量 + 半监督异常检测」（现行实现是 ICM：3 维特征 n95 / peak_value / n25 + 35 个聚类中心的 L1 距离度量）。** 答辩时主动讲这一条，比被评委问出来强得多。

## 五、知识运用

按学科分类，每一条都说清楚「用在项目的哪个位置」。

### 1. 模拟电路 / 传感器

| 知识 | 用在哪 |
|---|---|
| **电阻分压** | D153C 板载 10 k + 1 k 组成 1/11 分压，把最高 13.5 V 的母线电压降到 ADC 能接受的 1.23 V（3S 锂电 12.6 V 时），量程 3.3 × 11 = **36.3 V**，安全余量充足 |
| **霍尔电流传感原理** | ACS712 内部是霍尔元件 + 线性放大，输出 = 零点 + 灵敏度 × 电流；我据此推出 `I = (Vout − 2.5) / 0.185` |
| **ADC 采样定理与源阻抗匹配** | 分压电阻 10 k‖1 k ≈ 0.9 kΩ，源阻抗偏高，所以我把 ADC 采样时间设成 **480 周期**（不是默认的 3 周期），否则采样电容充不满、读数系统性偏低 |
| **开漏输出与上拉** | I2C 的 SCL/SDA 是开漏 + 上拉（`GPIO_OType_OD` + `GPIO_PuPd_UP`），这是 I2C 总线的电气要求；OLED 那条走板载 I2C 自带 4.7 k 上拉 |
| **H 桥驱动与续流** | 理解「BIN1 = PWM、BIN2 = 0」这种驱动—续流方式，是后面分析「为什么电流传感器位置很重要」的基础 |
| **开关电源纹波与母线电容** | 20 kHz 斩波电流主要由驱动板上的母线电容（220 µF）提供，ACS712 所在的支路看到的是被平滑过的电流，这解释了我最初对「母线电流是满幅方波」的误判 |
| **直流电机的稳态方程** | `ω ≈ (V_a − I_a·R_a) / (K_e·Φ)`，其中 `V_a = D × V_bat`。用它推出「理想情况下 ω/V_bat ≈ D/(K_e·Φ)，与占空比成正比」，也是我做归一化的理论依据 |
| **执行器死区与归一化分母的选择** | 电机不是「占空比越大越转」，而是**过 50% 死区之后才线性**：`rpm ≈ 17.5 × (duty − 50)`，58% → 140 rpm、64% → 245 rpm、46% 代入为负（所以起不来）。这意味着做档位归一化时**分母必须是有效区间 `(duty − 50)`，不是设定值 `duty`**——我第一版用 `58 / duty`，跨档残差 61%；改成 `8 / (duty − 50)` 后降到 6.3%，再由 dR 判据彻底绕开。教训是通用的：凡是执行器带死区的系统（电机起动、阀门死行程、传感器盲区），设定值与有效量之间差一个常数偏移，直接相除一定出错 |

### 2. 数字电路与 MCU 外设

| 知识 | 用在哪 |
|---|---|
| **定时器 PWM 输出** | TIM9_CH1/CH2 → PE5/PE6，输出 20 kHz PWM 调速 |
| **定时器编码器模式** | TIM4 用硬件编码器模式（**TI12 双边沿**）对 A/B 相做四倍频计数，**纯硬件、不占 CPU** |
| **定时器中断做时基** | TIM7 每 1 ms 中断一次，在中断里做编码器采样（每 100 ms）、按键扫描（每 5 ms）——**把周期任务从主循环挪进中断**，避免主循环刷 OLED 阻塞导致 100 ms 窗口漂移 |
| **ADC 单次软件触发 + EOC 轮询** | PA4/PA5 共用 ADC1，每次读之前先选通道再软件启动，轮询 EOC 标志并带超时保护 |

| **USART 中断发送** | 遥测帧用 TXE 中断逐字节发，主循环只负责把帧丢给缓冲区，发送忙就跳过该帧（不阻塞） |
| **GPIO 复用功能（AF）** | PB6/PB7 是 AF2（TIM4）、PB10 是 AF7（USART3）、PE5/PE6 是 AF3（TIM9）——**AF 编号配错引脚就不工作** |

### 3. 信号处理与算法

| 知识 | 用在哪 |
|---|---|
| **量纲归一化 / 无量纲化** | 这是本方案的核心：`R = rpm / V_bat` 把「转/分」变成「转/分/伏」，消掉电量这个干扰量。判别力从「裸转速重叠」变成「空出 2 个 rpm/V 的间隔」 |
| **滑动窗口与步长** | 32 点（3.2 s）窗口，100 ms 一点；推理时窗满后**整体左移一点**（步长 1 点 = 100 ms），保证相似度每 100 ms 更新一次 |
| **均值池化（mean pooling）** | 库的预处理链把 32 点池化成 1 个均值——等效于一个 3.2 s 的滑动平均，压制单点噪声。**我从库里把这个参数解出来才确认了这件事** |
| **聚类距离判决** | ICM 的机理：把 32 点抽成 3 维特征，算到 **35 个聚类中心**的 L1 距离，`norm1 = 1`，再经 `sensitivity = 0.5` 映射成 0~100 的相似度 |
| **一阶低通 / 指数跟踪** | 电流零点在线跟踪用 `α = 0.02` 的一阶滤波，时间常数约 0.5 s |
| **信噪比评估** | 用它否决了电流路线：R 在同一次「捏轴」动作上变化 −16.3%、噪声 0.26%（**信噪比 65**），电流只变化 +0.03 A、噪声 ±0.03 A（**信噪比 1**） |
| **混叠（Aliasing）分析** | 定量证明了 100 Hz 采样下 240 Hz 与 40 Hz 信号在采样网格上**逐点相同**，必须提采样率才能看波形特征 |
| **FFT 频谱分析** | 上位机对 20 kHz 原始块做 FFT，在约 300 Hz 处确认了换向纹波谱线真实存在 |
| **CRC 校验** | 遥测帧用 CRC16-CCITT-FALSE 保护，接收端做语法 + 范围 + CRC 三重校验 |

### 5. 软件工程

| 知识 | 用在哪 |
|---|---|
| **分层架构** | `HARDWARE/` 是板级驱动，`USER/main.c` 是应用层；传感器只往 `UI_Data` 结构体填数，显示层只负责画——**两者解耦，加传感器不用改显示代码** |
| **时间片调度** | 主循环用「非阻塞时间比较」而不是 `Delay`：10 ms 走传感器、50 ms 刷一个 OLED 区域、500 ms 读一次母线电压 |
| **状态机** | AI 模块有 OFF / LEARNING / DETECTING / ERROR 四个状态；显示状态有 STOP / RUN / WARN / ALARM |
| **失效时主动丢窗** | `feature_r_tick()` 在「停转 / 电压失效 / 掉进启动死区」时**不只是不推点，而是把已攒的窗全部丢掉**——否则恢复后窗里混着停机前的旧数据，模型算出的相似度是错的 |
| **编译期断言** | `typedef char ai_monitor_input_len_check[(32 == NEAI_INPUT_SIGNAL_LENGTH) ? 1 : -1];`——换库时长度不匹配直接**编译失败**，而不是上板以后静默越界 |
| **定点与浮点** | 遥测帧里所有物理量都缩成整数（转速 ×10、电流 ×1000、电压 ×1000）传输，避免浮点字节序问题；特征计算内部用 float |
| **数据有效性分离** | 把「数值」和「数值是否可信」分成两件事传：传感器没接时返回安全值，同时把有效性标志清零，屏幕显示 `--`、状态显示 WARN |
| **死代码识别** | 判据是看 `.map` 的 Global Symbols：某个 `.o` 保留符号 0 个即为死代码。我用这条依据砍掉了 30 个编译单元 |

### 6. 边缘 AI / 机器学习

| 知识 | 用在哪 |
|---|---|
| **半监督异常检测** | 只用正常数据训练，运行时用「相似度」衡量偏离程度。训练集里虽然也有异常样本，但异常样本只用于**验证**（算 Balanced Accuracy），不参与学习 |
| **Z-score 判决** | 模型内部的判决就是 **\|z\| ≤ 1.206**，我把参数解出来验证过 |
| **模型压缩与资源评估** | 最终模型 RAM **3668 B** / Flash **3108 B**——比上一版 ZSM（56 B / 40 B）大六十倍，但换来的是检出率从 58.9% 提到 **92.0%**（混淆矩阵实测 3108/3378；离线预估 87.0%）。在 192 KB / 1 MB 的 F407 上，这个代价可以忽略 |
| **预训练知识 + 增量学习** | 库带着训练时学到的 **35 个聚类中心**，`init(true)` 直接可用；运行中用 `neai_anomalydetection_learn()` 做增量微调，不清空、不打断检测 |

## 六、边缘 AI 部署（重点）

### 6.1 AI 功能是怎样部署完成的（完整链条）

**第 1 步：在 STM32 上建立数据采集链路**
`main.c` 每 10 ms 读一次转速和电流、每 500 ms 读一次母线电压。转速和电压不是直接喂给 AI，而是先进 `feature_r` 模块算成 R——**AI 只认 R 这一个量**。

**第 2 步：在 STM32 上把 R 攒成 32 点序列**
`feature_r.c` 每 100 ms 推一个点到 `s_win[32]`，攒满 32 点（**3.2 秒**）才算一窗。`feature_r_get()` 把 32 个 float 按「先旧后新」的顺序拷出来——**顺序不能反，因为训练时 CSV 里就是先旧后新**。

**第 3 步：采集训练数据送到电脑**
正常运行的 6 批（`normal_running_01~06`）和「用手握住转子」的 3 批（`grip_01~03`）通过遥测链路存到电脑上。另有 1 批低电量敲击数据（`tabletop02`，母线仅 9.85 V）专门用来验证「电量变化会不会误报」。
**采集有门禁**：必须 6000/6000 帧全部接受、无丢帧、单帧间隔 ≤ 20 ms 才算合格。

**第 4 步：在 NanoEdge AI Studio 里训练**
- Project Settings：Target = **STM32F4 Series**（同 M4 核、同 1 MB Flash / 192 KB RAM，兼容 F407ZG）；Sensor = **Time Series → Generic / 1 Axis**（注意只有 1 轴，不是 19 轴）。
- Signals：正常导入 **2252 行 × 32 列**，异常导入 **3378 行 × 32 列**。**每行就是 1 个窗的 32 个 PtP 值，没有表头、没有标签列。**
- STFT（短时傅里叶）不用管，因为 32 < 64，Studio 自动禁用了它。
- Benchmark：搜索了 **29,060** 个候选（16 核 11 线程并行），跑了 **3856 秒（1 小时 4 分 16 秒）**，选出**最优模型 = Library 68，ICM**，质量得分 **0.9344**，主 KPI **0.9578**。

**第 5 步：把库链进 Keil 工程**
这一步有**两个技术坑**，我都是实测解决的：
- **编译选项必须和工程一致**：从库的 `.ARM.attributes` 段里解出它要求 `Tag_ABI_VFP_args = 1`（硬浮点）、`Tag_ABI_PCS_wchar_t = 2`（2 字节 wchar）、`Tag_ABI_enum_size = 1`（最小 enum 容器），对应 Deployment 页要勾的三个选项；其中 **`fshort-wchar` 页面默认是不勾的，必须手动勾上**。
- **输入长度必须改**：旧库（Library 37）是「19 轴 × 4 样本 = 76 个 float」，新库是「**1 轴 × 32 采样 = 32 个 float**」。所以 `ai_monitor.c` 里那个 76 float 的累加器整个删掉了，改成直接调 `feature_r_get(g_neai_in, 32)` 拿 32 个点。我在改的时候加了编译期断言兜住长度。
- 链接验证：生成的 map 里 `neai_anomalydetection_init / _learn / _detect` 符号齐全，`fshort-wchar` 相关的 warning 为 0。
  （插一句：**armlink 是老版本程序，不认中文路径**，库要放在纯 ASCII 路径下才能链接。）

**第 6 步：调参并上板验收**
- 上一版用 ZSM 时，`LEARN_WINDOWS` 从 16 加到 64 才稳定；这一版换 ICM 后不需要现场学，`AI_MONITOR_LEARN_MAX = 400` 只作为 `init(true)` 失败时的兜底上限（库端要求 368）。
- 周期重学习定 **6000 次检测**（约 10 分钟），门槛**只有一个**：`g_similarity >= RELEARN_MIN_SIM = 20`（相似度太低时不允许重学，否则会把「异常态」学成「正常」——这是最危险的一种失效）。初版还额外要求 `g_alarm == 0`，上板发现会与工况漂移互相锁死（详见 9.7），该条件已删除。
- 上板实测（J-Link 内存回读）：`g_phase = 2`（DETECTING）、`sim = 100`、`alarm = 0`、`s_rpm = 140.0`、`g_i_raw_avg` 对应 +101 mA、`s_rippleAbs ≈ 0.16`；捏轴后 `s_rpm = 77.31`、`sim = 0`、`alarm = 1`、`s_rippleAbs = 3.23`，约 3 s 触发。

### 6.2 所有数据的含义、来源与获取方式

**板上每一帧遥测（`M2Frame`，36 字节负载）里的字段**

| 字段 | 含义 | 单位 | 获取方式 |
|---|---|---|---|
| `value[0]` | 电机电流 | mA（原始 A × 1000） | ACS712 → PA5 → ADC1_IN5 |
| `value[4]` | 转速 | rpm（×10） | 编码器 → TIM4 → 每 100 ms 计数差分 |
| `value[5]` | 母线电压 | mV（×1000） | D153C 1/11 分压 → PA4 → ADC1_IN4 |
| `seq` | 帧序号 | — | 每发一帧 +1，用于检测丢帧 |
| `uptimeMs` | 上电毫秒数 | ms | TIM7 累加 |
| `validMask` | 有效性掩码 | — | 电流 bit0 / 转速 bit4 / 电压 bit5（**加速度 bit1~3 已不再置位**） |

**板上 AI 的实际输入（只有这一个量）**

| 项 | 含义 | 值 |
|---|---|---|
| 特征 | R_new = (rpm / V_bat) × (58 − 50) / (duty − 50)（膝点归一化） | 单位 rpm/V；58% 档系数为 1.0，64% 档折算后与 58% 档一致（R = 11.79） |
| 采样节拍 | 每 100 ms 一点 | `FEATURE_R_PUSH_MS = 100` |
| 窗口长度 | 32 点一窗 | 3.2 秒 |
| 送进库的数据 | 32 个 float（先旧后新） | `NEAI_IN_LEN = 32` |
| 窗内无效判据 | rpm < 20 或 vbat < 1.0 V 或 duty < 45% | 直接丢窗，不喂模型 |

**数据来源与获取路径（一路走下来）**
```
编码器 + 母线分压
  → STM32 每 10 ms 采一次（100 Hz）
  → feature_r 每 100 ms 算一个 R、攒 32 点
  → ① 板上：window 满 → 32 float → AI
  → ② USART3/PB10 @57600 → D1 mini（D6）→ WiFi AP → 手机网页 /status
  → ③ 电脑端：USB 串口采集 → 解析 + 时序门禁 → 32 列 CSV → NanoEdge Studio
```
**注意路径 ③ 的时序门禁**：只有「6000/6000 帧全接受、无丢帧、最大帧间隔 ≤ 20 ms」的数据才能进训练集。丢过帧的数据在时间轴上不连续，算出来的窗没有物理意义。

### 6.3 如何训练 AI（细节）

- **训练数据**：正常 **2252 个窗**、异常 **3378 个窗**，每窗 32 个 float。这一版刻意让异常样本多于正常——异常侧才是要检出的对象，样本多一点，漏报的统计才可信。半监督训练时异常样本不参与学习，只用于算 Balanced Accuracy。
- **打包方式**：32 点一窗、**窗与窗不重叠**（`samples = 32` 的意义上）。板上推理时也是攒满 32 点才算一窗，和训练一致。
- **数据集形态的硬证据**：`nb_cols = 32`、`signal_len = 32`。这证明**这是单变量、每行恒 32 个数的数据集**——不是 19 维、不是多通道。
- **搜索空间**：ICM / MML / ZSM / iPCA + 降维组合，共试了 **29,060** 次，耗时 **3856 秒（1 小时 4 分 16 秒）**。
- **最优模型**：**Library 68，ICM（3 维特征 + 35 个聚类中心）**，质量得分 **0.9344**。
- **资源占用**：**RAM 3668 B、Flash 3108 B**。
- **最小学习行数**：**368**（`learning_min_lines = 368`）。PC 端训练时已消化完，上电 `init(true)` 直接可用，板上不必再学。
### 6.4 如何区分正常与异常

模型输出一个 **0~100 的相似度**（similarity），含义是「当前数据和学到的正常态有多像」。

**我实测到的分布**（这是写论文最有用的数据）：

| 状态 | 相似度 | 说明 |
|---|---|---|
| 刚学完的正常运行 | 100 | 窗均值落在判决带正中 |
| 热机后（运行十几分钟） | 67 ~ 75 | R 从 12.9 涨到 13.2，逼近判决带上界 |
| 轻触 / 轻捏转子 | 60 ~ 80 | 压不下去，**分不开** |
| **捏紧转子** | 100 → 68 → 16 → **0** | 约 **3~3.5 秒**降到 0，稳定触发 |

**判定规则（三道关）**：
1. **域门限**：`feature_r` 内部判——转速 ≥ 20 rpm、母线电压 ≥ 1.0 V 且通路有效、占空比 ≥ 45%。不满足就**丢窗**（不是不推点，是把已攒的窗全部作废），因为窗里混着停机前的数据会让相似度算错。**这一条也解释了「停在档位 0 时 AI 不动是正常的，不是故障」。**
2. **连续性**：窗必须由**连续**的 100 ms 点组成，中途被打断就重置。
3. **事件级报警**：相似度**连续 2 窗**低于 32 才置 ALARM；回到 32 以上**连续 2 窗**才解除。

### 6.5 检测所依据的标准特征值（这一节必须背下来）

这一版的判据是**两道并联**：一道显式（dR 峰峰值），一道来自模型（相似度）。

**第一道：dR 峰峰值（可当场手算）**

```
dR = 窗内 (rpm / V_bat) 的峰峰值        ← 32 点 = 3.2 s
门限：dR > 1.0 rpm/V，且连续 2 窗 → 判异常
```

实测分布（三个数据集，每行就是一个窗的 32 个点算出的 dR）：

| 数据集 | 窗数 | dR 中位 | dR p99 | dR 范围 |
|---|---|---|---|---|
| `Ripple32_regular_normal`（正常，覆盖 58% / 64% 两档） | 2252 | 0.111 | 0.554 | 0.004 ~ 0.554 |
| `Ripple32_abnormal_grip`（捏轴，同样覆盖两档） | 3378 | 3.555 | 4.242 | 0.000 ~ 4.242 |
| `Ripple32_test_normal`（独立测试批，未参与训练） | 1126 | — | — | 用于检验泛化 |

**这张表能看出三件事**：
1. **两侧余量都够**：正常窗的 p99 只有 0.554，门限 1.0 留了 **1.8 倍**；捏轴窗中位数 3.555，是门限的 **3.5 倍**。区分度 6.4 倍；
2. **门限不需要按档位标定**：58% 档捏轴时 dR 上升约 2.53、64% 档约 2.11，差 0.42，而门限固定 1.0，两档都过得去。物理原因是捏力恒定 → 负载力矩恒定 → `Δω = ΔT·Ra/Ke²` **与工作点无关，是绝对量**；
3. **为什么不能用相对百分比**：58% 档从 140 掉到 110 是 **−21%**，64% 档从 245 掉到 220 是 **−10%**，相对降幅差一倍，跨档没法共用阈值；而绝对降幅 30 rpm 与 25 rpm 几乎相同。**这一条是实测纠正过的——我第一版做的就是相对百分比，方向错了。**

**第二道：模型相似度（阈值 32）**

ICM 把 32 点抽成 3 个特征（n95 分位、峰值、n25 分位），算到 **35 个聚类中心**的 L1 距离，再映射成 0~100 的相似度；**低于 32 且连续 2 窗**判异常。

这一道我没法像 dR 那样手算，但它和 dR 是两个独立视角：**dR 看「峰有多高」，ICM 看「形状像不像」**——实测两者同时触发，互相印证。

**关于阈值选择的实测依据（`threshold_table.txt`）**：

下面这张表是**上一版**（ZSM、R 水平值口径）扫出来的，作为「为什么不用 R 水平值」的对照保留：

| 报警线 T（R < T 判异常） | 正常 6 批误报 | 异常 3 批检出 | 低电量批误报 |
|---|---|---|---|
| 12.6 | 0.00% | 100.00% | **100.0%** |
| 12.4 | 0.00% | 100.00% | **89.6%** |
| **12.2** | 0.00% | 100.00% | 0.0% |
| **12.0** | 0.00% | 100.00% | 0.0% |
| 11.6 | 0.00% | 100.00% | 0.0% |
| 11.4 | 0.00% | 97.84% | 0.0% |
| 11.0 | 0.00% | 67.30% | 0.0% |

**可用阈值区间是 11.6 ~ 12.2**，取 12.0 在正中间。注意 12.6 那一行——阈值松到 12.6，低电量批会 100% 误报。**这就是「为什么不直接用裸转速」的量化答案。**

但同一条表也暴露了 R 水平值的问题：它只在**一个档位内**成立。换到 64% 档，正常 R 是 20.6~22.1、捏轴是 18.1~18.5，整张表要重扫一遍。所以我最终把判决量换成了 dR——**R 只作为 AI 的输入特征，判决交给 dR。**

### 6.6 准确率 / 区分概率

- **质量得分 0.9344（93.44），主 KPI 0.9578**（Studio 的 Benchmark 结果）。
- 混淆矩阵：正常 **2242 / 10**、异常 **270 / 3108**，Balanced Accuracy = (2242/2252 + 3108/3378) / 2 = **95.78%**。
- **【诚实边界·必须说】**：正常那 2252 窗**和模型学习用的是同一批采集会话**，所以「10 个误报」这个数字偏乐观；只有「握持」那 3378 窗是真正样本外的（半监督训练时不用异常样本）。要谈泛化必须看独立测试批——这一版另采了 **1126 窗**独立数据，结论一致。**答辩时照实说，不要吹成「模型泛化能力 100%」。**
- 另一个诚实的观察：这个任务本身「好分」——正常 dR 的 p99 只有 0.554，握持中位数 3.555，中间空出将近 6 倍。所以 **95.78% 不能当成「我的 AI 很厉害」的证据**，它证明的是「整条链路是通的、模型是能上板的」。真正的对比是同一份数据下 ZSM 只有 58.9%、ICM 有 **92.0%**（离线预估 87.0%）——**换库带来的提升，比调阈值大得多。**

### 6.8 单变量筛选：为什么最后只剩下一个量（这一节是方法论，很能拿分）

我不是一开始就选 R 的。做过一轮 19 维特征的筛选，把所有候选量按「标准化效应量 |d|」排序，结果如下（`result.txt`，正常 1114 窗 / 握持 1113 窗）：

| 变量 | 正常 mean±sd | 异常 mean±sd | \|d\| | 单变量准确率 |
|---|---|---|---|---|
| speed_mean_norm（转速均值） | 0.29441±0.00096 | 0.24195±0.00463 | **15.69** | 100.00% |
| accel_x_mean_g（振动 X） | −0.92146±0.00139 | −0.94267±0.00364 | 7.71 | 100.00% |
| accel_z_rms_g | 0.25743±0.00214 | 0.16498±0.01830 | 7.09 | 100.00% |
| speed_std_norm（转速波动） | 0.00051±0.00020 | 0.00171±0.00047 | 3.32 | 98.07% |
| current_mean_A（电流均值） | 0.08248±0.00964 | 0.10459±0.01059 | 2.18 | 87.38% |
| current_rms_A | 0.08631±0.00930 | 0.10740±0.01034 | 2.14 | 86.48% |
| current_peak_to_peak_A | 0.10540±0.02194 | 0.10226±0.02009 | 0.15 | 53.12% |

**三条结论**：
1. **转速是最强的单变量**，效应量 15.69，比第二名高一倍——所以特征的主干必须是转速；
2. **电流几乎没用**，效应量只有 2.18，峰峰值更是 0.15 完全无判别力（原因见 6.9）；
3. 振动的效应量 7.71 也不错，但要额外传感器、额外标定、对安装姿态敏感，在转速单独就 100% 的情况下没有增量价值——**这就是摘掉 MPU6050 的决策依据**。
4. 另外这 19 个量之间高度冗余：`current_mean` 和 `current_rms` 相关系数 **+0.995**，`accel_x_mean` 和 `accel_x_rms` 是 **−1.000**——19 维里真正独立的信息远远不到 19 个。这也是「降维到 1 维反而更好」的旁证。

**但「转速」本身有两个致命缺陷，必须归一化**：
- **电量干扰**：3S 电池从 12.6 V 掉到 11.3 V，转速自己掉 11%；
- **档位干扰**：占空比一变，转速整体平移。

所以我做了两步归一化：`除母线电压` 消掉电量、`乘 (58 − 50) / (duty − 50)` 消掉档位。第一步是纯物理（同一负载下电压升高、转速升高）；第二步的关键是**分母取「占空比减膝点 50」**，而不是占空比本身——原因见问题 13。

注意 64% 档的系数是 `8 / 14 = 0.571`，不是 1。这一点在最终版里是真在用的（两档），不再是「留接口」。
**归一化前后的量化对比**（这是最有说服力的一段）：

| 场景 | 裸转速 | R = rpm/V | 膝点归一化后 R_new |
|---|---|---|---|
| 正常（58% 档，11.3 V） | 147.2 rpm | 13.23 ~ 13.53 | 13.23 ~ 13.53（系数 8/8 = 1.0） |
| 正常（64% 档，11.3 V） | 约 253 rpm | 20.6 ~ 22.1 | **13.4 左右**（系数 8/14 = 0.571） |
| 握持（58% 档，11.3 V） | 121.8 rpm（−17.2%） | 10.79 ~ 11.07（−18%） | 10.79 ~ 11.07 |
| **低电量（9.85 V，台面敲击）** | 约 122 rpm（**−17%，和握持重叠**） | **12.37（−7%，和握持分得开）** | 12.37（−7%） |

**看懂这张表就懂我的方案了**：裸转速下，「低电量」和「手握住」都是掉 17% 左右，**物理上不可能分开**，低电量时必然误报；除以电压后，电量造成的那部分偏差被压到 −7%，负载造成的仍是 −18%，两者拉开到 5 个百分点，用 12.0 一个阈值就能同时做到「正常零误报、低电量零误报、负载全检出」。

再看第三列：64% 档的裸转速比 58% 档高 72%，膝点归一化之后却回到 **13.4**，与 58% 档的 13.2 只差 **1.5%**——**这才是能跨档用的量**。不过 R_new 的跨档残差仍有 6.3%（13.054 / 13.878），所以这一版的模型是拿两档数据一起训的；而**判决**根本不看 R_new 的水平值，用的是它的窗内峰峰值 dR。
### 6.9 为什么电流被否决（用信噪比算，不靠感觉）

我一开始是打算用电流的（毕竟「电机带载电流会涨」是常识）。实测把它否掉了：

| 指标 | 数值 |
|---|---|
| 空载电流（3 次采样） | 0.038 / −0.002 / 0.059 A |
| 捏轴后电流（3 次采样，rpm 从 237 掉到 197） | 0.064 / 0.094 / 0.103 A |
| 电流变化量 | **约 +0.03 A** |
| ACS712 噪声（5A 版，185 mV/A） | **±0.03 A**（21 mVrms ≈ 113 mA） |
| **电流信噪比** | **≈ 1**（变化量和噪声同量级，分不开） |
| 同一动作 R 的变化 | 19.89 → 16.65（**−16.3%**） |
| R 的噪声 | 0.26% |
| **R 信噪比** | **65** |

**信噪比差 65 倍**，这就是我不做电流特征的硬理由。物理原因也清楚：MG310 空载电流只有 40 mA，被 20 kHz 斩波后在电机电感（30.7 mH）上滤得几乎干净，手上那点负载产生的增量被 ACS712 自身的霍尔噪声淹掉了。
**答辩时如果有人问「为什么不用电流」，把这张表背出来就行**——不是我不想用，是这颗传感器的分辨率不够。

### 6.10 老师问「你只有两个档位太少了」——完整回答（这一条准备充分，能反打）

**回答的顺序**：先说结论 → 再给物理原因 → 最后给改进路径。

1. **结论**：占空比的可用区间被两头夹住了——**下半段是电机的起动死区（50% 以下根本起不来），上半段是 3S 电池保护板的过流硬边界（74% 直接拉闸）**，真正能用的只有 **50%~70%** 这 20 个百分点。在这段区间里我已经放了 **58% 与 64% 两个档位**（140 rpm / 245 rpm）。再多放几个物理上仍不成立，理由见第 3 条；换低电压的 2S 电池也算过账，同样不行（见第 6 条）。
2. **直接原因（2026-10-21 已定位并修正）**：早先我写过「58% 档电机两端只有 1.96 V，`V_bat × D` 该有 6.55 V，落差成因未定位」——**这条已作废，是测量误判**（详见第 4 条）。真实情况是转速对占空比**过 50% 死区后线性**：`rpm ≈ 17.5 × (duty − 50)`。MG310 额定 7.4 V、3S 电池 11.1~12.6 V，要让电机端拿到 7.4 V，占空比确实约 58%（7.4/12.6）——这一层没错；错的是我把它当成了「非线性谜团」。
3. **实测证据（关键，2026-10-21 重测）**：换上一块全新 D153C，在 11.87 V 母线电压下逐档实测：**58% → 140 rpm、64% → 245 rpm、66% → 280 rpm**，与旧板的 142 rpm 完全一致——**旧板从未退化，早先的低转速数据是测错了**。把这些点画出来是一条**过 50% 的直线**：`rpm ≈ 17.5 × (duty − 50)`。早先那个「58% → 142、63% → 237，占空比 +8.6% 转速 +67%，所以非线性」的推论，是因为**没意识到分母该减 50**：63% 的有效量是 13、58% 是 8，比值 1.625，实测 237/142 = 1.67，**其实非常线性**。
4. **这一段我早先写错了，现在明确收回**：原文是「74% 档 500+ rpm、66% 档约 350 rpm、58% 档只有 150 rpm、20% / 40% 完全不转、电机两端只有 1.96 V、满电时 58% 曾到 450~520 rpm——数据互相矛盾，成因未定位，我不编结论」。**现在定位清楚了：那是测量误判，不是物理谜团。** 三条判据：
   ① **1.96 V 约等于 3.3 V × 0.594**——这个数精准得可疑，是万用表直流档读 PWM 波形读出的**平均值**，不是电机端真实电压；
   ② **450~520 rpm 那次是把别的档位的读数记成了 58%**，同一批记录里 74% 档本来就到 500+ rpm；
   ③ **换一块全新 D153C，11.87 V 下 58% 仍是 140 rpm**，与旧板 142 rpm 一致——如果回路真有问题，换板一定变。
   至于 20% / 40% 不转、74% 只撑几秒，现在都有干净解释：**前者在 50% 起动死区以下，后者被保护板拉闸**。
   这三条合起来的教训是：**记录数据时必须把「档位」与「测点」一起记下来，否则事后根本分不清「物理上未定位」和「当时记错了」**——我把后者当成前者排查了很久。答辩时主动讲这一条，很加分。
5. **我做过的尝试和结果（这一条是真正的收获）**：我给公式加过 `× (58 / duty)` 的档位归一化，结果 63% 折算后仍然偏离判决带——**根因不是「非线性」，是分母选错了**。有效量是 `(duty − 50)`，不是 `duty`：50% 以下电机根本不转，那部分占空比不产生任何转速。改成膝点归一化 `R_new = (rpm / V_bat) × 8 / (duty − 50)` 后，跨档残差从 **61% 降到 6.3%**。剩下的 6.3% 是曲线在 58% 以上略上翘造成的（64% 实测 262.7，线性预测 245，高 7%），公式消不掉，**最终靠两档数据一起重训 + 判决量改用 dR 解决**。现在档位表是 `{0, 58, 64}` 三档，不再回滚。
6. **改进路径（算过账的）**：先说一条我**算过并否掉**的方案——换 2S 电池。根子不在串数，而在**电机额定电压相对母线太低**：电机端真正可用的窗口由「起动死区 + 额定上限」决定，换电池只是把这个窗口挪到占空比的另一段，**宽度不变**，还得另配 8.4 V 充电器（3S 充电器不能复用）。真正可行的两条：**第一条，换 12 V 额定电机**（如 MG513 12 V 版），3S 12.6 V 下可用区间约 **40%~95%**，转速档位立刻能加上去（但要注意：**加档位只是多几个转速，不等于多工况**，见本条末尾），这是首选；**第二条，保留 MG310 但先加一级降压把母线稳压到 8.4 V**，可用区间固定为 87%~100%（不随电量漂），代价是余量仍偏紧。这两条落地之前，多档位在物理上不成立——这就是我把它列为「已知边界、未做」的原因。
   再补两句，都是我想清楚之后不再往好里说的（**先明确：运行档现在是 58% 与 64% 两档；63% 是早先做归一化实验时临时改的档，早已废弃**）。**（1）58% 与 64% 之间现在跨得过去，但只跨了「转速」，没跨「工况」**——膝点归一化后两档残差 6.3%，dR 判据跨档只差 0.035 rpm/V，技术上两档通用；但**两个转速点仍然是同一负载下的两个工作点，不是两种工况**。再往上加档位也没有新信息：66% → 280 rpm 已接近可用上限，74% 会被 3S 保护板直接拉闸。**（2）靠人工加负载凑「多工况」也不行**——用胶带、配重给轴上加阻力，跟用手捏在物理上是同一件事（都是外加转矩），等于**把故障当正常训**，只会造出一个「带胶带工况专用监测器」，判决带反而更窄。要真正做宽工况，必须**增加第二路信号**来区分「负载重」和「坏了」（电流或振动），而这两路我都实测排除了：ACS712 被自身霍尔噪声淹掉（信噪比差 65 倍）、MPU6050 已连同 19 维特征一起摘除。所以我的方案定位明确是**固定负载下的专用监测器**——这是**信息量决定的边界**，不是调参能绕过去的，也不是换块电池能解决的。
7. **额外一条**：上限是电池保护板给的硬边界，不是软件能绕过去的——实测 **74% 档会被 3S 保护板直接拉闸**（恒负载下抬高电压会推高转速，风阻与减速箱损耗随转速上升，电流被抬起来触发过流保护）。固件里用 `#if (DUTY_x > 70U) #error` 把 70% 以上的档位在**编译期**就拦住，避免手滑配出会拉闸的档位。

### 7.2 为什么选这几个量显示

- **转速 + 电流**是电机的两大基本运行量，用**大字号**显示——答辩时评委从两米外就能看清。
- **R（归一化转速比）**：**这一格是给评委看的「现象窗口」**。它把转速按母线电压和档位膝点归一化，跨档、跨电量都能直接比。评委能亲眼看到「捏住转子时它从 13.3 掉到 11 以下」，比讲十句话都直观。**注意 R 只上屏，不是模型输入**——模型吃的是 rpm/V 的滚动峰峰值序列 PtP，两者的关系见第三章。
- **母线电压**：它是 R 的分母，**没有它 R 就没有意义**。这一行原本放的是假相似度（`Sim 0.95`），把位置让给真实电压——**假数据不如不留**。
- **相似度 + 状态字 + 档位 + dR + 秒数**：状态字告诉人「现在系统认为电机是什么状态」；相似度是模型输出的**原始数值**（答辩时可以直接指着屏幕说「100 正在往 0 掉」）；`LRN`/`DET` 告诉人 AI 在哪一步；`dR` 是窗内 rpm/V 的绝对峰峰值，也就是显式判据本身，**常驻底条，不切页就能看到「离报警还有多远」**；运行秒数是给演示计时用的。

### 7.3 每一项数据是怎么来的 + 计算公式（重中之重）

#### （1）转速 Spd —— 单位 rpm

**硬件链路**：编码器 A/B 相 → PB6/PB7 → TIM4 编码器模式（硬件四倍频）→ 每 100 ms 读一次计数差。

**公式推导**（这一段必须能自己推，评委很爱问）：
```
单圈计数 CPR = 编码器线数 × 倍频 × 减速比
            = 13 ppr × 4（AB 双边沿四倍频）× 20（减速比 1:20）
            = 1040 counts / 输出轴一圈

采样窗口 T = 100 ms = 0.1 s

rpm = (ΔCount / CPR) / T × 60
    = ΔCount × 60 / (1040 × 0.1)
    = ΔCount × 60 / 104
    = ΔCount × 0.576923
```
**代码里的常数**：`ENC_RPM_PER_CNT = 0.576923f`（`encoder.h`）。
**举例**：100 ms 内数到 253 个脉冲 → 253 × 0.576923 ≈ 146 rpm。
**标定方法**（最省力的）：让电机用固定 PWM 自己转，读数和理论值 `67.57 rpm/V × 母线电压 × 占空比` 对照。手工标定是「用手转输出轴 1 秒 1 圈，屏上应该显示约 60 rpm」——但输出轴只有一小截杆子，手转很费劲，所以我一律优先让电机自己转。

#### （2）归一化转速比 R —— 单位 rpm/V（屏显量；模型输入是它的滚动峰峰值 PtP）

**这不是一个测量量，是一个算出来的量**，而且是**两级归一化**（缺一不可）：
```
q = rpm / V_bat                      ← 第一级归一化后的中间量
R = q × (58 − 50) / (duty − 50)      ← 第二级膝点归一化，只用于屏显
```
**先把要说清的口径摆出来**（这是最容易讲错的地方）：

| 量 | 算法 | 用途 |
| --- | --- | --- |
| `q` | `rpm / V_bat`，每 100 ms 一点 | 中间量，不直接使用 |
| **`PtP`** | 0.8 s（8 点）内 `q` 的峰峰值，32 点成窗 | **模型输入**（ICM 的 3 个内部特征都由它来） |
| **`dR`** | 3.2 s 窗内 `q` 的最大值减最小值 | 显式阈值判据（门限 1.0），**不喂模型** |
| `R` | `q × 8 / (duty − 50)` | **仅屏显**，给人看 |

所以「模型输入是 R」是不准确的：**模型的输入是 q 的 8 点滚动峰峰值，32 点一条序列**；R 只是把 q 再按档位膝点折到基准档，好让屏上的数字跨档可比。
**第一级除母线电压**，把「电池有多少电」这个和电机健康无关的变量除掉；
**第二级乘膝点比**，把「当前是第几档」这个同样与健康无关的变量除掉。

**为什么分母是 `(duty − 50)` 而不是 `duty`**：本工程实测的标定曲线是
`rpm = 17.5 × (duty − 50)`，死区正好落在 50%：

| 占空比 | 实测转速 |
| --- | --- |
| 58% | 140 rpm |
| 64% | 245 rpm（实测 245~262，58% 以上略上翘） |
| 66% | 280 rpm |

即 `rpm / V_bat` 对 `(duty − 50)` 才是线性的。若按老式的 `(58 / duty)` 归一，
等于假设 R 正比于 duty，档位越高偏得越远——实测三档残差达 **61%**，64% 档必然误报。
改成膝点归一化后残差收到 **6.3%**。

**举例**：58% 档、转速 140 rpm、母线 11.87 V →
R = (140 / 11.87) × 8/8 = **11.79 rpm/V**；64% 档、转速 245 rpm、母线 11.87 V →
R = (245 / 11.87) × 8/14 = **11.79 rpm/V**。**两档完全一致**，这正是膝点归一化的目的。
电池放到 10.7 V 时 R = **13.08**。

**2026-10-22 实测复核（烧录新固件后在板上直接读内部变量）**：

| 档位 | 实测转速 | 实测 R（`s_lastR`） | 相似度 | dR | 保护 |
| --- | --- | --- | --- | --- | --- |
| 58% | ~124 rpm | **12.20 ~ 12.27** | 100 | 0.13 | 未触发 |
| 64% | **242.3 rpm** | **12.79** | 100 | 0.24 | 未触发 |

- **两档 R 实测只差 5%**（12.2 vs 12.8），落在膝点归一化的预期残差 6.3% 以内。
  这条比上面的推算更有说服力：**老式 `×(58/duty)` 在这两档会差 61%，必然误报**。
- 64% 档实测 242.3 rpm，与标定值 245 rpm 吻合。
- R 是**两位数**（12.x），所以 OLED 必须给 2 位整数位 —— 详见 7.1 节的显示修正。

**物理含义**：R 是「折算到基准档后，每伏母线电压能换来多少转速」。
**捏住转子**：58% 档转速掉到 120 rpm、母线不变 → R = (120/11.87) × 1 = **10.11**，
掉出正常带，触发报警。

**三重有效性判据**（任何一条不满足就丢窗）：`rpm ≥ 20`、`V_bat ≥ 1.0 V 且通路有效`、
`duty > 50%`（落在起动死区，R 没有物理意义）。

**跨档位的补充说明**：膝点归一化把跨档残差压到 6.3%，但仍大于模型 ±1% 的判决带宽，
所以**两个档位并用必须用两档数据重训模型**（本项目的 68 号 ICM 库就是这样训的）。
真正做到跨档通用、不需要按档位标定任何系数的是 **dR 判据**——
dR 是窗内 rpm/V 的绝对峰峰值，58% 档 0.188、64% 档 0.223，只差 0.035（阈值 1.0 的 3.5%），
一套阈值直接覆盖两档。这也是我最终选 dR 做显式判决量的根本原因。

#### （3）电流 Cur —— 单位 A（只做显示，不进 AI）

**硬件链路**：ACS712-05B 的 OUT → PA5（ADC1_IN5）→ 12 位 ADC。
**公式**：
```
① ADC 原始值转传感器输出电压：
     Vout = raw / 4095 × 3.3      (V)

② ACS712 的输出关系（5A 版）：
     Vout = 2.5 + 0.185 × I       →    I = (Vout − V_zero) / 0.185

   其中 2.5 V 是「零电流时的输出电压」（= VCC/2，VCC = 5 V）
        0.185 V/A 是灵敏度
        V_zero 是我上电校准出来的实际零点（实测 2.517 V）
```
**代码里的常数**（`current.h`）：`ACS712_SENSITIVITY = 0.185f`、`ACS712_VREF = 3.30f`、`ACS712_ADC_FULL = 4095.0f`。
**三个必须讲的工程处理**：
1. **上电零点校准**：电机停转时采 64 次取平均，得到这台设备的实际零点。**必须做**——ACS712 的零点容差是 ±1.5% VCC（等效 ±200 mA），不校准就会有固定偏置。如果零点不在 2.10~2.90 V 之间，直接判「传感器没接」。
2. **8 点滑动平均**：`CURRENT_FILTER_WINDOW = 8`。**而且是在「原始 ADC 码」上做平均，不是换算成安培之后再平均**——因为整数平均可以做到完全精确，能消掉零点附近的单点符号翻转（就是屏幕上出现假负号的那个问题）。代价是约 70 ms 的滞后。
3. **停机零点在线跟踪**：只有确认「占空比 = 0 且转速 < 20 rpm」时才执行 `Current_TrackZero()`，用 `α = 0.02` 的一阶滤波把零点慢慢拉向当前读数。**电机一转就冻结零点**——这是为了防止「拿运行中的电流去改零点」把真实电流吃掉。

#### （4）母线电压 Bat —— 单位 V（R 的分母，非常关键）

**硬件链路**：D153C 的 H2-5（ADC 脚）→ PA4（ADC1_IN4）。板上有 **10 k + 1 k 的 1/11 分压**。
**公式**：
```
V_ADC = VM / 11
raw   = V_ADC / 3.3 × 4095
→  VM = raw / 4095 × 3.3 × 11
```
**代码**：`vbat.c` 的 `Vbat_GetVolt()`，`VBAT_DIV_RATIO = 11.0f`、`VBAT_ADC_AVG = 8`（8 次平均）。
**量程**：3.3 × 11 = **36.3 V**，3S 锂电 12.6 V 只用到 1/3，很安全；分辨率 3.3 / 4095 × 11 ≈ **8.9 mV**，足够判断「满 12.6 V / 该充电 9 V」。
**为什么这个量对 AI 至关重要**：它是 R 的分母。如果这一路读错 10%，R 就整体偏 10%——而判决带只有 ±0.96%，**直接爆带**。所以母线电压通路的有效性（`vbat_valid`）是硬门限：一路无效，`feature_r` 立刻丢窗，宁可显示 `--` 也不给模型喂错的 R。
**一条重要认识（这是我踩过坑才明白的）**：这个分压**只抽约 1 mA 电流**，所以它量到的是**近乎空载的电压**。结论是：**它能证明电池是健康的，但不能证明回路的带载能力**——如果电压是在「测压点之后」的环节丢掉的（比如接插件接触电阻），这一格是看不见的。

#### （5）状态字 ST —— 系统的四态判定

```
优先级从高到低：
  ① 任何一路传感器无效（speed / current / vbat 任一 valid = 0）→ WARN
  ② 转速 < 20 rpm                                              → STOP
  ③ AI 处于 DETECTING 且已报警                                  → ALARM
  ④ 其余（数据有效且确实在转）                                   → RUN
```
**注意**：`RUN` 的含义是「**数据有效且电机确实在转**」，**不是**「AI 判定电机健康」。真正的健康判定只有 ALARM 这一个出口。这个区分很重要——评委如果问「RUN 是不是代表没故障」，答案就是上面这句。
**另外**：WARN 会优先于 ALARM——因为报警结论建立在数据可信的前提上，数据不可信时不能给「健康」也不能给「故障」，只能说「不知道」。

#### （6）AI 阶段 LRN / DET

- `LRN` = LEARNING，正在补学正常样本。**本版上电就会先进这一态**（启动现场自适应学习）：先补满 64 个相似度 ≥ 32 的正常窗（约 6.4 秒；最长 192 窗超时兜底），期间页 6 中间那 5 格显示 `n/64` 进度；补满即转 `DET`，**之后不再重复学习**。ICM 库带预训练知识，`init(true)` 成功后检测分支立即可用，这段补学只是把「现场这台电机」的正常区间对齐一次；
- `DET` = DETECTING，正在检测，此时 `S:` 后面的相似度是真实值；
- 不在以上两态时，相似度显示 `---`（`ai_monitor_has_result()` 为 0）。

#### （7）运行秒数

- `T` = `uptime_s` = TIM7 累加的毫秒时基 / 1000，底条占 5 位（够显示到 99999 秒，约 27.7 小时）；
- 秒数后面**不再画心跳**：IWDG 已经在跑（真卡死会直接复位），屏上没必要再放一个存活指示，而且实物照片上那个四帧轮转的笔画会被看成脏点或乱码。

### 7.4 刷新策略（一个加分细节）

OLED 走 I2C、同步阻塞，一次重画全部数值会长时间占住主循环，让 10 ms 的遥测帧出现空洞。所以我把刷新拆成 **4 个区域轮询**：每次主循环只发一个区域（转速 / 电流 / R / 电压+状态+底条），4 次调用后整屏更新完。
**效果**：单次阻塞时间显著缩短，遥测帧间隔稳定在 11 ms 以内（门限 20 ms）。

## 八、问题与解决（重点）

按发生顺序，每条都按「现象 → 定位过程 → 根因 → 解决 → 判据」写全。

### 问题 1：PWM 配好了，电机一档都不转

- **现象**：PWM 初始化代码看上去完全正确，但四个档位电机全都不转，连「哼哼」的声音都没有。
- **定位过程**：用 J-Link 读 TIM9 的寄存器，发现三个致命现象：
  - `TIM9->CR1 = 0x038B`（正常应该只有 0x01~0x81）
  - `TIM9->CNT` 读到 15965 / 63493，**远大于** `ARR = 99`
  - `SR` 里的 `UIF` 一直为 0
- **根因**：`pwm.c` 用了 StdPeriph 的 `TIM_TimeBaseInitTypeDef` 结构体，但**没有初始化就把其中几个字段交给库函数处理**。`TIM_TimeBaseInit()` 会把 `TIM_ClockDivision` 这个 16 位字段和别的位一起 OR 进 `CR1`，而结构体没清零，栈上的垃圾值 **0x038A** 被 OR 了进去。结果 `CR1` 的 `UDIS`(bit1)、`OPM`(bit3)、`ARPE`(bit7) 全部被置 1：
  - `UDIS = 1` → 更新事件被禁止 → ARR 的预装载值 99 永远加载不进影子寄存器 → 计数器按 0xFFFF 跑 → PWM 周期从 50 µs 变成 33 ms、占空比不到 0.1%
- **解决**（三处一起改）：
  1. 结构体声明时 `= {0}` 清零；
  2. 显式赋值 `TIM_ClockDivision = TIM_CKD_DIV1`、`TIM_RepetitionCounter = 0`；
  3. 初始化前先 `TIM9->CR1 = 0`，把可能被污染的位彻底清干净。
- **判据**：改完 `CR1 = 0x01`、`ARR = 0x63`（= 99）、`CNT ≤ 99`、`CCR1` 随档位精确变化（58% 时 `CCR1 = 58`）。
- **沉淀下来的铁律**（写进项目规范）：**StdPeriph 的结构体必须 `= {0}`，用到的字段必须显式赋值**——「用到但没赋值」的字段是隐藏炸弹。这条也套用到了 `encoder.c`。

### 问题 2：屏幕上转速永远是 0

- **现象**：电机明明在转，`Spd` 那格恒为 0。
- **定位过程**：屏幕上报的运行秒数 `T` 在正常递增 → 说明主循环和 TIM7 中断都正常 → 那转速为 0 只可能是编码器这条链路的问题。
- **根因**：**只把电机的 6P 排线插上了 D153C，忘了从 H2 排针飞编码器的两根线**。这个驱动板的设计是：电机座只走电机电流，编码器信号另外从 H2 引出。
- **解决**：飞两根杜邦线 `H2-2(E2A) → PB6`、`H2-1(E2B) → PB7`。
- **判据**：屏上转速立刻从 0 变成 140+ rpm。

### 问题 3：按了按键档位卡死不动

- **现象**：按键按下去没反应，档位卡住。而且是**偶发的**，有时候好有时候坏。
- **定位过程**：`key.c` 原来用的是「全局 `key_locked` 锁 + 四颗键全部松开才解锁」的机制。J-Link 读 `s_idle` 发现有一路电平始终是高——那是 **PA0（WK_UP）**，它走的是**另一套电路**（独立的上拉/下拉网络），和其它三颗键不是一套。
- **根因**：只要 PA0 一直读到高，「四颗键全部松开」这个解锁条件**永远不成立**，锁就永远解不开 → 档位卡死。
- **解决**（架构级的改法）：
  1. **按键消抖和边沿检测全部挪进 TIM7 的 1 ms 中断**（每 5 ms 扫一次、连续 4 次相同才算稳定，即 20 ms 消抖），主循环只负责取「事件」，**没有任何锁**可以卡；
  2. **PA0 完全不参与**按键逻辑，只做下拉输入防止浮空；
  3. 按键的「静止电平」改成**上电后前 200 ms 自学习**（`KEY_LEARN_CNT = 40`，40 × 5 ms），之后判断「!= 静止电平」即为按下——这样**高电平有效和低电平有效两种接法都能自适应**；
  4. 功能分工改成**每颗键各管一件事**：KEY0（PE4）急停 / KEY1（PE3）档位 +1 / KEY2（PE2）档位 −1。
- **顺序坑**：`Key_Init()` **必须排在 `Tim7_Init()` 之前**。因为按键扫描跑在 TIM7 中断里，如果 TIM7 先启动，中断会在引脚还没配置（复位默认浮空输入）的时候就去「学习静止电平」，学到的基线是错的，之后所有按键判断都会反过来。

### 问题 4：屏幕上电流出现负号、读数乱跳

- **现象**：屏幕上 `Cur` 时不时显示负值；运行时读数抖动。
- **定位过程**：一开始怀疑是 ACS712 接反。但如果是极性接反，读数应该**稳定地**全为负；实测是**正负翻转、围绕零点抖动**，所以不是接反，是**零点附近的采样噪声 + 单点采样**。
- **根因（两层）**：
  1. **直接原因**：单点 ADC 采样正好落在校准零点以下，就出一个负值；
  2. **深层原因**（后来做采样链路审计才定量说清）：板上是 **100 Hz 采样**，而 PWM 载波是 **20 kHz = 200 × 100 Hz，是整数倍**。整数倍的异步采样会让 20 kHz 载波**折叠到直流**，表现为零点缓慢漂移——所以这个负号**不是随机噪声，是采样率和载波率的整数倍关系造成的**。
- **解决（分三层）**：
  1. **8 点滑动平均**（`CURRENT_FILTER_WINDOW = 8`），而且**在原始 ADC 码上做平均**（整数运算完全精确，消掉单点的符号翻转），代价是约 70 ms 滞后；
  2. **停机零点在线跟踪**（`Current_TrackZero()`，`α = 0.02`）：只在「占空比 = 0 且转速 < 20 rpm」时执行，把零点慢慢拉向当前读数；一旦电机转起来就**冻结零点**，防止把真实电流吃掉。理由：ACS712 的零点容差 ±1.5% VCC（≈ ±200 mA）而且会随温度漂移，一次上电校准不够；
  3. **换传感器位置**：把 ACS712 从「电池 ↔ 驱动板」之间**改串到「驱动板 ↔ 电机」之间**。母线上测到的是被 20 kHz 斩波、又被驱动板母线电容平滑过的电流；电机引线上测到的是**连续的绕组电流**（电机电感 30.7 mH 把 PWM 滤成了近直流，20 kHz 纹波只有约 4.8 mA 峰峰），读数稳定、量级和符号都正确。
- **判据**：停机时 `Cur` 稳定在 ±0.01 A；运行时读到稳定的正电流；遥测帧的有效性掩码 bit0/bit4/bit5 全部置位。

### 问题 5：100 Hz 采样根本看不到电机的「波形特征」（采样链路审计）

- **现象（起因）**：有人指出「100 Hz 采样会混叠，你的 AI 实际退化成了阈值判断」。我需要判断这个说法对不对。
- **定位过程**：我写了一个脚本（`sampling_audit.py`）只读源码和手册做定量复核，结论是**这个批评是对的，而且比它说的更严重**：
  - 电流通道的有效带宽只有约 **0~5.6 Hz**（100 Hz 采样 + 8 点平均，Nyquist 25 Hz，−3 dB 截止 5.57 Hz）；
  - 20 kHz 载波 = 200 × 100 Hz，**折叠到 0 Hz**；
  - 电机的真实分量全在带宽之外：58% 档输出 145 rpm → 电机本体 2900 rpm → 换向纹波 **145~242 Hz**、齿轮啮合 **387~580 Hz**；
  - **严格证明**：100 Hz 采样下，240 Hz 和 40 Hz 的正弦在采样网格上**逐点相同**（240 = 2×100 + 40），脚本实测两个信号的最大逐点差是 **3.0×10⁻¹⁵**。也就是说，**真实的 240 Hz 换向纹波和虚构的 40 Hz 信号，在板端 AI 眼里是同一个东西**。
  - 顺带修正了我自己的一个误判：我原来以为母线电流是「导通期满载、续流期为零」的方波，**忽略了驱动板上 220 µF 的母线电容**——电容在 20 kHz 下的容抗只有约 0.036 Ω，会把斩波电流基本旁路掉，所以「偶发负号」的主因更可能是 ACS712 自身噪声（21 mVrms ≈ 113 mA）而不是斩波本身。这个修正我也写进了报告。
- **这个批评带来的最重要后果**：它直接导致我**放弃了「用波形特征做 AI」的路线**，转向「单变量 + 归一化 + 统计判决」。既然 100 Hz 采不到波形，就不该硬吹波形——**这是我方案定位的关键转折**。
- **解决（分三步）**：
  1. **硬件层**：把 ACS712 挪到电机引线（就是问题 4 的第 3 条）——从源头拿到连续、可解释的绕组电流；
  2. **固件层**：新写一个 **20 kHz 高速采样前端（`fastcap.c`）**：用 **ADC2 + DMA2 循环采集** PA5，采样率锁定 20 kHz（= 载波频率），每 10 ms 恰好一帧 200 点；**一帧 200 点的均值就是长度 10 ms 的矩形窗，零点精确落在 100 Hz 的整数倍上**——20 kHz 载波及其谐波被零点吃掉，这就是「载波折叠到直流」的正解，而不是靠后置平均去压。另外支持一次抓 2000 点（100 ms）原始块存 RAM，供 J-Link 导出做 FFT；
  3. **相位锁定**：为了让采样点落在 PWM 的 **ON 窗口中部**（避开开关振铃），我加了 `fastcap_align_to_pwm()`，把 ADC 触发相位锁到 `CNT = 29`（即 14.5 µs）。依据是「ON 窗口内母线电流 = 绕组电流（连续量）」。
- **过程中又踩了三个坑（都是实测定位出来的）**：
  1. **ADC 状态位读错**：我把 `bit4` 当成 OVR。F4 的 ADC 里 **bit4 是 STRT（正常状态）**，**bit5（0x20）才是 OVR**。判据：读到 0x10 是 STRT 不是 OVR。
  2. **循环 DMA 停摆**：DMA 缓冲区回卷后 ADC 不再发请求（NDTR 停在满值、EOC 卡住），根因是 `ADC_DMARequestAfterLastTransferCmd()` 没调用。
  3. **恢复序列竞态**：原来在 ADON 还没真正清 0 之前就清 SR，而且 ADON 和 DMA 请求使能之间有 1 ms 空窗，会自己造出一个 OVR 死循环。改成「等 ADON 清 0 → 复位 DMA → 清 SR → 先开 DMA 请求 → 再开 ADON」。
- **实测判据**：`g_fastcap_frames` 每秒 +100（前端持续出帧）；`g_fastcap_ovr = 0`（无溢出恢复）；手捏负载时原始块的直流均值从停机约 3160 变到 3060~3080（对应约 0.37~0.42 A）；上位机对 2000 点原始块做 FFT，在 **约 300 Hz** 处看到谱线（与 6 换向片 × 47.7 转/秒 ≈ 286 Hz 吻合）。
- **【诚实边界】** 换向纹波确实存在，但**很弱**（约 17 mA rms，只有负载电流的约 5%），而且比 ACS712 自身噪声（约 113 mA）弱。所以这条路的定位是「**并行的取证/验证路径，可以出 FFT 证据**」，**没有成为 AI 模型的输入**。答辩时不要把它说成「AI 已经在用波形特征」。

### 问题 6：训练数据质量门禁一直失败（每 60 秒出现 8~15 处 21~26 ms 的帧空洞）

- **现象**：连续两次 60 秒采集都 `qualityGatePassed = false`，检查发现帧间隔里有 8~15 处达到 21~26 ms（门禁要求 ≤ 20 ms）。
- **定位过程**：逐项排查主循环里的耗时操作，锁定两个：**软件 I2C 的阻塞延时**、以及**板上旧 AI 库的周期性推理**。
- **根因**：
  1. OLED 的软件 I2C 延时 `I2C_Delay = 40`，太慢，一次刷屏阻塞很久；
  2. 板上旧 NanoEdge 库（round-8 版本）每约 1.5 秒做一次学习/检测，**单次阻塞约 10 ms**——这是 21 ms 空洞的主因。
- **解决**：
  1. `oled.c` 的 I2C 提速：`I2C_Delay` 40 → 16（约 100 kHz → 330 kHz，仍在 SSD1306 的 400 kHz 上限内）；
  2. 给 `ai_monitor.c` 加 `ai_monitor_set_enabled()`，**纯采集阶段把板上 AI 关掉**（那一轮不需要板上模型），消除它的周期性阻塞；
  3. MPU6050 摘除后，它那条软件 I2C 的延时也一并消失了。
- **判据**：修复后重采 60 秒 → `qualityGatePassed = true`、`trainingEligible = true`、**6000/6000 帧全部接受、缺帧/拒帧/时序断点全为 0、最大帧间隔 11 ms**。

### 问题 7：电机转速只有 134 rpm（理论上应该 443 rpm）

- **现象**：母线电压 11.3 V（电池健康，约 55% 电量），58% 档转速只有 132~146 rpm，而按 `67.57 rpm/V × 11.3 V × 0.58` 应该是约 443 rpm。而且 20% / 40% 档电机完全不转、也完全不哼。
- **定量分析**：
  ```
  反推电机端实际拿到的电压 = 132 / 67.57 ≈ 1.95 V
  应该拿到 = 11.3 × 0.58 = 6.55 V
  → 回路里丢掉了 4.60 V（占应得电压的 70%）
  → 若为串联电阻：回路 0.15 A ⇒ 约 31 Ω，而 MG310 绕组本身只有 2~5 Ω
  ```
- **已经排除的（都靠实测判据排除，不是猜）**：

  | 曾经怀疑 | 排除依据 |
  |---|---|
  | 固件 / PWM | `CR1 = 0x01`、`ARR = 99`、`CNT ≤ 99`、`CCR1` 随档位精确变化；时基 700 ms 推进 703 ms |
  | 编码器标定 | 换全新 D153C 后 58% 档实测 140 rpm，与旧板 142 rpm 一致；按 `13×4×20 = 1040` counts/圈反算自洽（早先「满电 58% 读到 450~520 rpm」是档位记错，已作废） |
  | 电池没电 | 屏上 11.3 V 是真的，充电前后扫描数字几乎不变 |
  | 机械堵转 | **58% 跑十秒，电机和驱动板都不烫**。如果是近乎堵转，大电流的 I²R 会在十秒内把电机烘烫 |
  | 静摩擦主导（「只是起步难」） | **58% 转着按 K2 落到 40% 就立刻停**。静摩擦比动摩擦大，如果只是起步难，40% 的 4.52 V 应该能维持它转 |
  | 电源线线型 | 那根红线**本来就是单股实芯线**（是原设计不是断剩的），载流截面正常 |
  | 驱动板（后来） | **换了一块全新的 D153C，转速还是 134 rpm** |
- **关键认识**：屏幕上的 `Bat` 那一格**看不见这 4.6 V**，因为 1/11 分压**只抽约 1 mA**，量到的是**近乎空载**的电压——**它能证明电池是健康的，但证明不了回路的带载能力**。丢掉的电压一定发生在「测压点之后的电路里」，这两件事可以同时成立。
- **当前状态【2026-10-21 更新：已定因，早先的「无法定因」收回】**：换上一块全新 D153C，在 11.87 V 母线电压下逐档实测 **58% → 140 rpm、64% → 245 rpm、66% → 280 rpm**，与旧板的 142 rpm 完全一致——**旧板从未退化，早先那些「互相矛盾」的数据是测量误判**。三组关键点：
   ① **1.96 V 是万用表直流档读 PWM 波形读出的平均值**（≈ 3.3 V × 0.594），不是电机端真实电压；
   ② **「满电时 58% 曾读到 450~520 rpm」是档位记错**（74% 档才到 500+ rpm）；
   ③ **20% / 40% 不转是 50% 起动死区、74% 拉闸是保护板过流**，两者都不是故障。
   真正的规律是 `rpm ≈ 17.5 × (duty − 50)`，干净线性。
- **已排除（都有实测判据）**：驱动板（换新 D153C 仍 134 rpm）、固件 PWM、编码器标定、电池空载电压、机械堵转（58% 跑 10 秒不烫）、静摩擦主导（58% 转着落 40% 立刻停）。
- **已经测完、结论明确**：58% 运行时电池两端实测 **11.87 V**（3.96 V/节，约 60% 电量），**带载不塌压**，「电池带载能力不足」这一假设因此被否掉。同一轮还顺带解决了**电流显示为负**的问题——真因不是 ACS712 接反，而是 **PWM 纹波与采样节拍的相位混叠**：TIM9 周期 50 µs、采样周期 10 ms、`nowMs` 分辨率 1 ms 三者成整数倍，每次采样都落在同一相位，8 点滑动平均等于没平均。用 DWT 周期计数做相位抖动后即消除，实测停机 +4 mA、空载 +82~+130 mA、捏轴 +196 mA，方向与量级都对。
- **补充一句**：正因为转速只有 134 rpm（远低于规格 500 rpm），我选的 R 是**实测出来的量**，而不是理论推导量——理论值 443 rpm 对应的 R 会是 39.2，和我实测的 13.3 差了 3 倍。所以模型学的是「这台机器当前的真实基线」，不是手册值。

### 问题 8：驱动板 TB6612 渐进性损坏 → 输入对地短路

- **现象（三个阶段）**：
  1. 长期只有约 134~143 rpm（就是问题 7 的读数）；
  2. 中途**有一次转速突然飙升到 500+ rpm**，按 RESET 之后恢复；
  3. 最后**一接上电池 D153C 就发烫**（还没按 K1，电机没转）——这说明板子**输入对地已经短路**，TB6612 的桥臂击穿了。
- **定位/证据链**（用来证明这是**渐进性器件老化**，不是我的固件或接线问题）：
  1. 健康的 TB6612 输出级只掉 0.1~0.3 V，而我的板子记录到「输出段丢压约 4.6 V」——**芯片早就在带病工作**；
  2. 那次「转速突然飙到 500+」正是**坏掉的桥臂瞬间给了满电压**（丢压消失），电机短时间回到了规格转速——这是最有力的证据；
  3. 之后 FET 彻底击穿 → 电机堵转 + 驱动板过热 → 输入对地短路。
- **同时也排除了一个嫌疑**：**不是 ACS712 电流接反**。ACS712 的电流端就是一个低阻导体，接反只会让读数符号反，**不改变任何电气行为**，既不会造成短路、也不会让转速飙升。
- **解决**：换一块新 D153C。换完硬件恢复正常。
- **【诚实边界·重要】** 虽然被这个问题折腾了很久，但**换新板后 58% 档转速仍然只有 134 rpm**——所以「低转速」是**独立的老问题**（问题 7），**不是驱动板造成的**。答辩时这两件事要分清，不要说成「换板以后转速就正常了」。

### 问题 9：板上 AI 一直进不了 DETECTING

- **现象**：烧上新库以后，AI 停在 LEARNING 状态不动，屏底条一直显示 `LRN`。
- **定位过程**：J-Link 读状态量，发现 `feature_r_fill()` 恒为 0 —— 说明**每个点都被有效判据拦掉了**。追到 `feature_r_tick()` 的三个门限，发现当时电机不转（问题 7/8 的回路故障），`duty = 58` 而 `rpm = 0` → 直接判无效 → 窗永远是空的 → `feature_r_get()` 永远返回 0 → AI 永远拿不到数据。
- **根因**：不是固件 bug，是**上游电机不转**导致的连锁反应。**副作用是「电机不转 = AI 永远没法演示」**。
- **解决**：修好电机回路（问题 8 的换板），并在文档里写清「**停在档位 0 时 `LRN` 不动是正常现象，不是故障**」——因为停转时 R 没有物理意义，本来就不该喂给模型。
- **判据**：按 K1 升到 L1 后，约 3.2 秒窗就攒满（32 点 × 100 ms），屏上相似度开始更新；本版上电即 `DET`，正常不会再停在 `LRN`。

### 问题 10：冷机/热机基线不一致 → 上一版热机后相似度掉到 67~75

- **现象（ZSM 那一版）**：刚学完（冷机）相似度 100，运行十几分钟后掉到 67~75，离阈值 32 还有余量但明显在下滑。
- **定位过程**：读 `g_similarity` 和 `s_lastR` 观察趋势，发现是**单调缓慢衰减**而不是跳变——说明是工况在缓慢偏离学习态，不是数据坏了。
- **根因（有实测数据）**：
  ```
  冷机：rpm ≈ 140，R ≈ 12.9
  热机：rpm 上升约 2%，R ≈ 13.2
  ZSM 判决带：[13.202, 13.459]，±0.96%
  ```
  **漂移发生在转速侧，不是电压侧**——电机绕组升温后磁钢性能略降、轴承润滑变稀，空载转速上升约 2%，R 就跟着涨 2%。而 ZSM 的判决带只有 ±0.96%，热机后 R 逼近上界，相似度就从 100 掉到 67~75。**这是一个真实的物理现象，不是标定错了。**
- **这一版怎么处理（换成 ICM）**：判据从「均值落在一条 ±0.96% 的窄带里」改成「三个特征的联合距离」，容差宽得多，同样的 2% 漂移不会再把它推到边界；同时保留两条机制兜底：
  1. **周期增量学习**：`AI_MONITOR_RELEARN_DETECTS = 6000`——每完成 6000 次检测（每次 100 ms，合计约 **10 分钟**）就用当前窗做一次增量 `learn`，把基线慢慢拉到当前热机状态。它不清空知识、也不打断检测，与上一版「清零重学 64 窗」是两回事；
  2. **门槛只有一道：相似度 ≥ 20**（`RELEARN_MIN_SIM = 20`）——相似度低于 20 时不允许学习，因为那说明系统正处于明显异常，重学等于「把故障学成健康」。**这是整个 AI 模块里最需要小心的一处失效模式。** 初版还加过第二道「未报警才计数」（`g_alarm == 0`），上板实测证明那是错的：工况整体漂移时相似度长期偏低、报警又不解除，两个条件互相当锁，重学习永不触发（`g_detectCount` 冻结在 2428），系统再也回不到正常。**结论是：防「学坏」只能靠相似度本身，不能靠报警标志位——因为报警标志位本身就可能被同一个漂移卡住。**
- **判据**：捏住时 3 s 内掉到 0 并报警；松开后回到 100。ICM 版连续运行中尚未观察到相似度下滑，但长时热机数据时长还不足以完全排除，所以增量学习仍然保留作兜底。
- **【诚实边界】** 上一版的 67~75 是有完整曲线的；这一版我还没有同等时长的热机长跑，所以答辩时说「判据容差变宽了、并有增量学习兜底」，不要说「这个问题已经不存在了」。
### 问题 11：新库一上板就重启 / 输入长度对不上

### 问题 12：J-Link 烧录「静默失败」——打印 O.K. 但根本没写进去

- **现象**：`loadbin` 打印 `O.K.`，但回读 md5 与烧录前**完全一致**，也就是一个字都没改。这一条最坑，因为它**不报错**。
- **定位过程**：翻 J-Link 的日志，发现 `erase` 那一步其实被拒了：
  ```
  Please select a device with "device <DeviceName>" before using this command.
  ```
  而且 `JLinkLog.txt` 的时间戳还停在三周前，说明近期根本没走过 Keil 的下载通道。
- **根因**：我写的烧录脚本**漏了第一行 `device STM32F407ZG`**。没有 device 就没有 flash 编程算法，`erase` 被静默拒绝，后面 `loadbin` 实际上什么都没做却照样回 O.K.。
- **解决**：脚本首行加 `device STM32F407ZG`。同时定下规矩：**每次烧完必须独立回读校验**，不能相信 J-Link 自报的 Verify。
- **判据**：回读 1048576 字节，与 HEX 逐字节比对 **0 差异**（某个版本实测 5564 字节不同、首个差异在 `0x08000194` 中断向量表——那次就是没烧进去）。
- **沉淀下来的铁律**：**「工具说成功」和「结果真的变了」是两件事，必须用独立手段验证。** 这一条同样适用于后面的问题 13。

### 问题 13：J-Link 在 4 MHz 下烧不进去（RAM check failed）

- **现象**：烧录稳定失败，报
  ```
  Failed to prepare for programming. RAM check failed while testing 0x2050 bytes
  @ addr 0x200006CC  →  Erase returned with error code -1
  ```
  而且**每次失败报的地址都不一样**（0x20000A0C / 0x20000A5C / 0x20000AEC）。
- **定位过程**：这个「地址每次都不同」的模式说明**有东西在持续改写被校验的内存区**。查 `.map` 发现：J-Link 的 RAMCode 和校验区范围是 **0x200006CC ~ 0x2000271C**，而这个范围**正好压在固件的 `.bss` 段和栈上**。
- **根因（两层，缺一不可）**：
  1. **4 MHz 下 halt 没有真正生效**，CPU 还在跑，运行中的栈不断改写校验模式；
  2. **CPU 停了但 DMA 还在跑**——ADC2 + DMA2_Stream2 是 20 kHz 循环采集，它自己会往 RAM 写数据，把 J-Link 刚写进去的校验模式冲掉。**这就是「地址每次都不同」的真正原因。**
- **解决**（三步，都要做）：
  1. **把烧录速度从 4000 kHz 降到 1000 kHz**；
  2. 脚本里显式加 **`h`（halt）**；
  3. **烧前先用 `w4` 把 ADC/DMA 关掉**：`w4 0x40026440 0`（DMA2_Stream2 CR）、`w4 0x40012108 0` / `w4 0x40012304 0`（ADC2 CR2 / CR1）。
  改完**一次就过**。
- **附带确认的一个版本差异**：V4.96d 这个版本的 J-Link Commander **没有 `connect` 命令**（报 `Unknown command`，无害但会带偏排查方向），也**不支持 `-ExitOnError`**。我最后定的烧录脚本是：
  ```
  device STM32F407ZG
  speed 1000
  h
  w4 0x40026440 0
  w4 0x40012108 0
  w4 0x40012304 0
  erase
  loadfile <hex> 0x08000000
  r
  g
  exit
  ```
  （脚本必须 **LF 行尾、路径用纯 ASCII 正斜杠、必须以 `exit` 结尾**——否则 J-Link 会在文件结尾处无限循环写日志，真的把我的硬盘吃掉过 15 GB。）
- **判据**：最终烧录 `Erase 17.46 s → 编程 1 个 range（32768 字节）→ O.K. → Reset`；**回读 1048576 字节，与 HEX 逐字节 0 差异**。

### 问题 14（补充）：电机回路间歇性接触不良

- **现象**：编码器 0 脉冲 + 电流恒等于零点（0 A）同时出现，而且**是间歇性的**（前一天还能正常采集）。
- **定位过程**：J-Link 读 TIM4 的 `CNT`，跨 1.2 秒读三次**完全相同**（5280 不变）→ 编码器完全没脉冲；同时 `g_i_raw_avg` 和上电零点完全相同（3120 ≈ 2.517 V）→ 电流约 0 A。**MCU 侧全部正常（TIM9 的 CR1/CCMR1/CCER/PSC/ARR/CCR1 逐项核对都对）**，问题在电机回路下游。
- **根因（一个故障点同时解释两个现象）**：D153C 的 6P 电机座**一根排线里同时走四类信号**——`pin2/pin6` 是电机驱动电流、`pin3` 是编码器供电、`pin4/pin5` 是编码器信号。所以这根排线（或端子）一松：电机开路（**0 A / 高阻**）+ 编码器失电（**PB6/PB7 浮空、CNT 冻结**）——正好就是我观测到的全部现象，也解释了间歇性。
- **解决**：断电后把 6P 排线两端都拔下来重插，检查端子有没有夹到绝缘皮或氧化发黑。
- **一条通用经验（也用于判「电机为什么不转」的排查顺序）**：
  1. **先看 CCR1**——如果是 0，说明在停机档，不是故障；
  2. **再读 `g_i_raw_avg`**——如果 ≈ 0，说明功率回路断了；
  3. **最后读 TIM4 的 CNT**——如果冻结，说明编码器断了。
  这个顺序能在一分钟内把「档位错 / 回路断 / 编码器断」三种原因分开。
- **另一条通用经验**：**「端子夹到绝缘皮 / 氧化发黑」的典型特征就是「空载正常、带载掉压」，而且接触点会局部发热**——这也是问题 7 低转速的可能方向之一。

### 问题 15（重要，这一条是方案层面的）：加上档位归一化之后，63% 档仍然对不上

- **现象**：为了让「多档位」成立，我给特征加了 `× (58 / duty)` 的档位归一化，把档位表改成 `{0, 63, 66}`、基准档设成 63。理论上归一化后不同档位应该折算到同一基线，结果**实测折算后仍然偏离判决带**，而且 66% 档只能稳定转 10 秒左右。
- **定位过程**：
  1. 实测同一母线电压下：**58% → 142 rpm，63% → 237 rpm**。占空比 +8.6%，转速 +67%——这根本不是「转速 ∝ 占空比」。
  2. 把三档实测点画出来才发现：曲线不是过原点的直线，而是**过 50% 的直线**。拟合得到 `rpm ≈ 17.5 × (duty − 50)`：58% → 140（实测 140.0，完全吻合）、64% → 245（实测 245~262，58% 以上略上翘）、46% → 负值（所以起不来，这就是起动死区的来源）。
  3. 也就是说，`×(58 / duty)` 的**分母选错了**：应该用**有效区间** `(duty − 50)`，而不是 `duty` 本身。拿 `58 / duty` 等于假设 R 正比于占空比，档位越高偏得越远。
- **改成膝点归一化**：`R_new = (rpm / V_bat) × (58 − 50) / (duty − 50)`。跨档残差从 61% 明显下降。58% 档因为 `8 / 8 = 1`，新老两式恒等，所以这一改动对一档零影响。
  > 【此处曾有一个被推翻的中间结论】按归档数据算残差曾得到 1.5%（三档 13.21 / 13.41 / 13.54），但那批数据的 64% 档电池电压只有 10.16 V、温度也不同，掩盖了真实残差。改用两档同条件实测数据重新核算后，残差是 **6.3%**（见下一条），1.5% 作废。
- **但残差没到零，还差最后一步**：把两档数据放在一起看，残差其实是 **6.3%**（13.054 / 13.878），仍大于模型带宽。公式消不掉它，因为曲线在 58% 以上确实略上翘（64% 实测 262.7，线性预测 245，高 7%）。所以这一版**直接拿两档数据一起重训**，让模型自己吃掉这段非线性。
- **最终的判决量不是 R，是 dR**：R 的水平值跨档要重训、跨电池电压也会漂，而 dR（窗内峰峰值）跨档只差 **0.035 rpm/V**。所以分工是——**R_new 喂 AI 学正常水平，dR 做显式判决**。
- **判据**：`DUTY_LEVEL[3] = {0, 58, 64}`、`LEVEL_MAX = 2`；`#if (DUTY_x > 70U) #error` 在编译期硬拦住会被 3S 保护板拉闸的档位；切档时调 `ai_monitor_switch_level()` 清窗重判。
- **教训**：**归一化的分母要选「有效区间」，不是「设定值」。** 凡是执行器带死区的系统（电机起动、阀门死行程、传感器盲区），设定值和有效量之间差一个常数偏移，直接相除一定出错。另外，归一化只能修线性部分，修不了曲率——曲率要靠重训模型或换判据，不能靠在软件里再加一个系数。

## 九、源码解析（重点）

工程结构：`CORE/`（CMSIS + 启动文件）、`FWLIB/`（StdPeriph V1.4，精简到 7 个外设）、`USER/`（应用层）、`HARDWARE/`（我写的板级驱动）。工程共 **27 个编译单元**。下面是按模块的解析。

### 9.1 `USER/main.c` —— 主循环与调度

**核心设计：非阻塞时间片**。主循环里没有任何一处「死等」，全靠比较时间戳：
```c
#define SENSOR_UPDATE_MS 10U    /* 传感器 + 遥测：10 ms */
#define REFRESH_MS       50U    /* OLED：每次只刷一个区域，50 ms 走一步 */
#define VBAT_UPDATE_MS   500U   /* 母线电压：500 ms 一次 */
```
**四个关键变量**（都是「上次执行时刻」）：
- `lastSensorMs`：上次传感器采样的时刻；
- `lastVbatMs`：上次读母线电压的时刻；
- `lastUiMs`：上次刷 OLED 的时刻。

**一个容易被问到的细节**：读母线电压的代码故意放在**给快照打时间戳之前**，而且读完**重新取一次时间**（`nowMs = Encoder_GetMs()`）。原因是 `Vbat_GetVolt()` 里要采 8 次 ADC、还有点延时，如果它发生在打时间戳之后，会把下一个 10 ms 的间隔**压缩**掉。这是一个典型的「慢 I/O 不能挤占快采样的时间基准」的处理。

**档位表**：
```c
static const uint8_t DUTY_LEVEL[2] = { 0U, 58U };   /* 0 档 = 停，1 档 = 58% */
#define LEVEL_MAX 1U
```
（历史上有过 4 档和 L4 自动扫描，2026-10-14 收敛成两档；2026-10-20 试过 `{0, 63, 66}` 想加档位，因 58%→63% 非线性回滚，详见第八节问题 15。）

**10 ms 分支里最核心的三行**（AI 数据的唯一来源）：
```c
if (feature_r_tick(d.speed_rpm, d.vbat_v, d.vbat_valid, (float)d.duty, nowMs) != 0U)
{                     /* 得益于 100 ms 节拍，真的推进了一个新点 */
    ai_monitor_tick();        /* 窗口每攒满一次就推一次模型 */
}
d.r_ratio = feature_r_current();     /* 屏显用 */
```
**注意 `ai_monitor_tick()` 只能写在这里**：它是被 `feature_r_tick()` 的返回值守卫的，而 `feature_r_tick()` 在停机时直接返回 0。如果把 `ai_monitor_tick()` 挪进 `feature_r_tick()` 内部，停机后它永远不会被调用（死代码）。

**停机通知（一个容易漏的关键点）**：
```c
if (d.speed_rpm < 20.0f)      /* 电机没转 */
{
    ai_monitor_notify_stopped();      /* 累计停机时间 */
}
```
停机持续 0.5 s 以上就会把 AI 置回 LEARNING 状态（`AI_MONITOR_STOP_TICKS = 50`，50 × 10 ms）。**为什么要有这个**：我的模型容差只有 ±2% R，而机械负载会让转速在 150↔216 rpm 之间自跳；一旦停机再起转，工况已变，必须重学基线。这一条 **必须写在 main.c 的 10 ms 块里**——写在 `feature_r_tick()` 里是死代码（因为停转时它提前 return 了）。

**主循环流程**：
1. `Key_Scan()` 取按键事件 → 改档位 → `Motor_Config(占空比, 1)`；
2. 500 ms 分支：读母线电压到 `d.vbat_v` / `d.vbat_valid`；
3. 10 ms 分支：读转速、电流、推进 20 kHz 前端、调 `feature_r_tick()`；
4. 算系统状态（WARN / STOP / RUN / ALARM 四级优先级）；
5. `telemetry_poll(&d, nowMs)` 打包并发送；
6. 50 ms 分支：`UI_Update(&d)` 刷一个屏幕区域。

### 9.2 `HARDWARE/encoder.c/.h` —— 转速

**关键常数（`encoder.h`）**：
```c
#define ENC_PPR    13U     /* 编码器每转脉冲数 */
#define ENC_MULT   4U      /* AB 双边沿四倍频 */
#define ENC_GEAR   20U     /* 减速比 1:20 */
#define ENC_CPR    (ENC_PPR * ENC_MULT * ENC_GEAR)   /* = 1040 */
#define ENC_SAMPLE_MS 100U              /* 每 100 ms 采样一次 */
#define ENC_RPM_PER_CNT 0.576923f       /* 60 / (1040 × 0.1) */
```
**三个到处被问的 API 的区别**（这个我答过好几次）：
- `Encoder_GetRpm()`：**转速**（rpm，恒为正），UI 和 `feature_r` 用的都是这个；
- `Encoder_GetDelta()`：**最近 100 ms 的计数差**（不是累计值！）；
- `Encoder_GetCount()`：TIM4 计数器的**绝对位置**（16 位，65536 回绕）——只有它才能用来标定「转一圈 1040 个脉冲」。

**中断里的采样**：
```c
static void Encoder_Sample(void) {
    int16_t now = (int16_t)TIM_GetCounter(TIM4);
    int16_t delta = (int16_t)(now - s_last_cnt);   /* 用 int16 回绕相减，0↔65535 跨越仍正确 */
    s_last_cnt = now;
    s_delta = delta;
    float rpm = (float)delta * ENC_RPM_PER_CNT;
    if (rpm < 0.0f) rpm = -rpm;    /* 只关心转速大小，取绝对值 */
    s_rpm = rpm;
}
```
**为什么必须放中断**：主循环要刷 OLED，一次刷屏要几十毫秒。如果采样在主循环里做，100 ms 的采样窗口会被刷新延迟拖到 100~160 ms，算出来的转速就忽高忽低。放进 1 ms 中断后，100 ms 窗口的抖动只有微秒级。**而 R 的判决带只有 ±0.96%，转速抖 1% 就会爆带**——所以这一条对 AI 的可靠性是硬需求，不是「优化」。

**初始化里两个关键点**：
- `TIM_EncoderInterfaceConfig(TIM4, TIM_EncoderMode_TI12, ...)`：**TI12 双边沿模式 = 四倍频**；
- `TIM_ICFilter = 10`：输入滤波，滤掉编码器线上的毛刺。

### 9.3 `HARDWARE/pwm.c` —— 电机驱动

**关键配置**：
```c
TIM_TimeBaseStructure.TIM_Prescaler = 84 - 1;   /* PSC */
TIM_TimeBaseStructure.TIM_Period    = 100 - 1;  /* ARR */
```
**频率推导（一定要会推）**：TIM9 挂在 APB2 上 → APB2 = 84 MHz → 定时器时钟 = 84 × 2 = **168 MHz** → 168 MHz / 84 = **2 MHz** → 2 MHz / 100 = **20 kHz**，周期 **50 µs**。
**一个很好用的巧合**：因为 `ARR = 99`，所以 `TIM_SetCompare1(TIM9, x)` 里的 `x` **直接就等于占空比的百分数**（写 58 就是 58%）。

**STBY 使能**：D153C 的 STBY 引脚硬件没接，引到排针上，所以固件里把 **PA8 配成推挽输出并拉高**：
```c
GPIO_SetBits(GPIOA, GPIO_Pin_8);   /* STBY = 1，使能输出 */
```
**这一行漏了电机就完全不转**——这是驱动板手册的要求（STBY=0 时输出级关闭、电机两端呈高阻）。

**电机转动 API**：
```c
void Motor_Config(uint16_t speed, uint16_t dir) {
    if (dir == 1) { TIM_SetCompare1(TIM9, speed); TIM_SetCompare2(TIM9, 0); }  /* 正转 */
    else          { TIM_SetCompare1(TIM9, 0);     TIM_SetCompare2(TIM9, speed); }  /* 反转 */
}
```
`dir = 1` 时 PE5（BIN1）给 PWM、PE6（BIN2）恒 0，所以**电机端平均电压 = 占空比 × 母线电压**。
**一个实验技巧**：AI 调试时如果需要远程起转，可以直接用 J-Link 写 `w4 0x40014034 0x3A`（CCR1 = 58）。**但要注意**：这样改不会更新 `d.duty`，会造成寄存器里的占空比和软件里的档位不一致——我在第八节问题 15 里就是靠这个错配反而验出了归一化公式是对的。**正式实验要改档位只能用按键。**

### 9.4 `HARDWARE/current.c/.h` —— 电流（OLED 电流数据的来源）

**常数**：
```c
#define ACS712_SENSITIVITY 0.185f   /* V/A，5A 版 */
#define ACS712_VREF        3.30f    /* ADC 参考电压 */
#define ACS712_ADC_FULL    4095.0f  /* 12 位 */
#define ACS712_ADC_AVG     64U      /* 校准时取 64 次平均 */
#define ACS712_ZERO_MIN    2.10f    /* 零点合理性下限 */
#define ACS712_ZERO_MAX    2.90f    /* 零点合理性上限 */
#define CURRENT_FILTER_WINDOW 8U        /* 运行时 8 点滑动平均 */
#define CURRENT_ZERO_TRACK_ALPHA 0.02f  /* 停机零点跟踪系数 */
```
**静态变量**：`g_i_zero`（校准出来的零点电压）、`g_i_valid`（这一路的有效性）、`g_i_raw_history[8]`（滑动平均的历史）、`g_i_raw_avg`（平均后的原始码）。
**核心函数**：
- `Current_Calibrate()`：先 `Motor_Config(0,1)` 确保停转、延时 200 ms，然后采 64 次取平均得到 `g_i_zero`；**如果零点不在 2.10~2.90 V 之间就判 ACS712 没接**（`g_i_valid = 0`）；
- `Current_UpdateFiltered()`：把新读数推进环形缓冲并算平均——**注意这里平均的是「原始 ADC 码」而不是安培值**，整数平均精确，能消掉零点附近的符号翻转；
- `Current_GetAmp()`：`v = raw_avg / 4095 × 3.3`，然后 `return (v − g_i_zero) / 0.185`；
- `Current_TrackZero()`：只在停机时执行，`g_i_zero += 0.02 × (v − g_i_zero)`——一阶低通把零点慢慢拉向当前读数。

### 9.5 `HARDWARE/vbat.c/.h` —— 母线电压（R 的分母，最关键的一路）

**常数**：`VBAT_DIV_RATIO = 11.0f`（1/11 分压）、`VBAT_ADC_AVG = 8`（8 次平均）、`VBAT_VALID_MIN = 4.0f` / `VBAT_VALID_MAX = 16.0f`（合理范围）。
**公式**：`VM = sum/8 / 4095 × 3.3 × 11`。
**三个设计点**：
- **PA4/PA5 共用 ADC1**：所以 `ADC1_ReadChannel(ch)` 做成通用的——每次调用先 `ADC1->SR = 0` 清所有锁存的状态位、再选通道、再软件启动、然后轮询 EOC 并带超时保护（`ADC1_CONVERT_TIMEOUT = 100000`）。`current.c` 复用同一个函数读 PA5。
- **「传感器在不在」的检测**（`Vbat_CheckPresent()`）：**先把 PA4 配成输出并拉低放电 2 ms**，再配回模拟输入、等 2 ms 后读一次——如果线没接（浮空），放电后电压回不来，读数接近 0；如果接了 D153C 的分压，节点会被分压网络重新充到母线电压的 1/11。这是个很巧妙的「用放电再充电判断有没有源」的办法。**这一路的值直接进 R 的分母，所以「有没有接」必须能自动识别，不能靠人看。**
- **等待时间**：ADC 上电后要约 1 µs 稳定，所以 `Vbat_Init()` 里延时 10 ms 才做第一次采样，避免第一枪读到脏值。

### 9.6 `HARDWARE/feature_r.c/.h` —— 峰峰值窗与 dR 判据（模型输入的生产者）

**全部宏定义**（`feature_r.h`，一共 9 个）：
```c
#define FEATURE_R_WINDOW         32U     /* 窗口 32 点，每点 100 ms → 3.2 s */
#define FEATURE_R_PUSH_MS        100U    /* 每 100 ms 推一点 */
#define FEATURE_R_RPM_MIN        20.0f   /* 低于此转速视为没转，丢窗 */
#define FEATURE_R_VBAT_MIN       1.0f    /* 低于此电压分压通路不可信 */
#define FEATURE_R_START_RISE_PCT 2.0f    /* 正向上升率超此值判为起动爬升期，不推点 */
#define FEATURE_R_RIPPLE_SPAN    8U      /* 短窗跨度 8 点 = 0.8 s，算滚动峰峰值用 */
#define FEATURE_R_DUTY_REF       58.0f   /* 膝点归一化的基准档 */
#define FEATURE_R_DUTY_KNEE      50.0f   /* 实测 rpm = 17.5 × (duty − 50)，死区在此 */
#define FEATURE_R_DUTY_MIN       40.0f   /* 低于此占空比 R 无意义，丢窗 */
```
**静态变量**：
```c
static float    s_win[FEATURE_R_WINDOW];   /* 32 个 float = 128 字节 */
static uint8_t  s_fill;                    /* 已攒点数，满窗后恒等于 32 */
static float    s_lastR;                   /* 最近一次 R，供屏显 */
static uint8_t  s_lastRValid;              /* 最近一次 R 是否有效 */
static uint32_t s_lastPushMs;              /* 上一次推点的毫秒时基 */
```
**核心函数 `feature_r_tick()` 三步走**：
```c
/* 第一步：判当前是否处于「有效运行状态」 */
if ((vbat_valid == 0U) || (vbat_v < FEATURE_R_VBAT_MIN) ||
    (rpm < FEATURE_R_RPM_MIN) ||
    (duty_pct < FEATURE_R_DUTY_MIN))          /* 掉进启动死区 */
{
    if (s_fill != 0U) { feature_r_reset(); }   /* 关键：丢窗，不只是不推点 */
    s_lastRValid = 0U;
    s_lastPushMs = now_ms;                     /* 重新对齐节拍，避免恢复后补推 */
    return 0U;
}

/* 第二步：两步归一化，缺一不可 */
r = (rpm / vbat_v) * (FEATURE_R_DUTY_REF / duty_pct);
s_lastR = r;
s_lastRValid = 1U;

/* 第三步：按 100 ms 节拍推点；窗满后整体左移一位 */
if ((uint32_t)(now_ms - s_lastPushMs) < FEATURE_R_PUSH_MS) { return 0U; }
s_lastPushMs = now_ms;
if (s_fill < FEATURE_R_WINDOW) { s_win[s_fill++] = r; }
else {
    for (i = 0U; (i + 1U) < FEATURE_R_WINDOW; i++) { s_win[i] = s_win[i + 1U]; }
    s_win[FEATURE_R_WINDOW - 1U] = r;
}
return 1U;
```
**四个必须能讲清的设计决定（一定会被问）**：
1. **为什么失效时要把窗全丢掉，而不是「不推点」？** 因为窗口代表「最近 3.2 秒的连续工况」。如果停机 1 分钟后再起转，窗里还有 31 个停机前的旧点，模型算出的均值就是停机前和起转后的混合物，相似度会给出一个**物理上不存在**的值。丢掉窗是最保守也最正确的做法。
2. **为什么 `s_lastPushMs = now_ms` 而不是 `+= PUSH_MS`？** 因为主循环的 10 ms 节拍本身有抖动。如果累加，误差会一直积累（漂移）；直接对齐到当前时刻，每次最多晚 10 ms，但永远不会漂。**代价是不能补推，所以恢复后的第一个点是「从现在开始」的**，这正好符合「丢窗后重新攒」的语义。
3. **为什么窗口整体左移（O(n)）而不是用环形缓冲（O(1)）？** 因为 `feature_r_get()` 要交给库的必须是**时间上连续的线性数组**，库不会理解环形索引。32 个 float 的 `memmove` 等价操作在 168 MHz 上不到 1 µs，而每 100 ms 才做一次，**代价完全可以忽略**。用一个精确的接口换一个微秒级的开销，值得。
4. **为什么 `feature_r_get()` 在窗未满时返回 0 而不是返回半窗？** 因为库的 `signal_len = 32` 是固定的，喂 16 个点等于喂了 16 个垃圾（后面 16 个位置是 0）。**宁可等，不给半成品。**

### 9.7 `HARDWARE/ai_monitor.c/.h` —— 板上 AI（核心）

**状态变量**（都是 `static`，但通过 J-Link 按 `.map` 里的地址能读）：
```c
static float   g_neai_in[AI_MONITOR_IN_LEN];  /* 32 float：从 feature_r 拿来的窗 */
static uint32_t g_learned;                    /* 已经学了多少窗 */
static uint32_t g_detectCount;                /* 检测了多少次（用于周期重学习） */
static AiMonitorPhase g_phase;                /* OFF / LEARNING / DETECTING / ERROR */
static uint8_t g_similarity;                  /* 最近一次的相似度 0~100 */
static uint8_t g_result_valid;                /* 最近结果是否有效 */
static uint8_t g_initialized;                 /* 库是否初始化成功 */
static uint8_t g_alarm;                       /* 当前是否处于 ALARM */
static uint8_t g_lowRun, g_highRun;           /* 连续低/高于阈值的计数 */
static uint32_t g_stoppedTicks;               /* 连续停机节拍数 */
```
**编译期断言**（防止换库导致越界）：
```c
typedef char ai_monitor_input_len_check[
    ((AI_MONITOR_IN_LEN) == (NEAI_INPUT_SIGNAL_LENGTH * NEAI_INPUT_AXIS_NUMBER)) ? 1 : -1];
```
**主函数 `ai_monitor_tick()` 的流程**：
```c
if (!g_initialized) return;                       /* 库没起来就什么都不做 */
if (!feature_r_get(g_neai_in, AI_MONITOR_IN_LEN)) return;   /* 窗没满，等 */
/* 库内有预训练知识时 g_needLearn = 0，直接走检测分支；只有 init(true) 失败才现场学 */
if (g_needLearn != 0U && g_learned < AI_MONITOR_LEARN_MAX) {   /* 兜底：现场学习，上限 400 */
    st = neai_anomalydetection_learn(g_neai_in);
    if (st 是 OK / IN_PROGRESS / DONE) g_learned++;
    g_phase = AI_MONITOR_LEARNING;
    st = neai_anomalydetection_detect(g_neai_in, &g_similarity);
    /* 事件级报警：连续 2 窗低于 32 才报警，连续 2 窗高于 32 才解除 */
    if (g_similarity < AI_MONITOR_THRESHOLD) {
        g_highRun = 0;
        if (++g_lowRun >= AI_MONITOR_ALARM_WINDOWS) g_alarm = 1U;
    } else {
        g_lowRun = 0;
        if (++g_highRun >= AI_MONITOR_CLEAR_WINDOWS) g_alarm = 0U;
    }
    /* 周期重学习：只要不是硬故障（相似度 >= 20）就照常累计。
     * 这里不能再加 g_alarm == 0 的判断——报警与工况漂移会互相锁死，见 9.7 */
    if (g_similarity >= AI_MONITOR_RELEARN_MIN_SIM) {
        if (++g_detectCount >= AI_MONITOR_RELEARN_DETECTS) {   /* 6000 次 ≈ 10 min */
            g_detectCount = 0U;
            g_learned = 0U;
            g_phase = LEARNING;
        }
    }
}
```
**三个关键设计决定（一定会被问）**：
1. **为什么报警要「连续 2 窗」而不是单次低于阈值？** 这是实测倒逼的：正常运行时相似度会**偶发下探**（热机漂移时更明显），单点判定会产生孤立误报。而被捏住的转子会让相似度**连续好几秒**低于阈值——所以用「连续 N 窗」区分「持续异常」和「瞬时抖动」。
2. **为什么重学习要设 `RELEARN_MIN_SIM = 20` 这道门？** **这是整个模块里最重要的一个保护。** 如果系统正处在明显异常（相似度掉到 0~10）时触发重学习，它会把这批「异常数据」学成「正常基线」，然后**报警永久消失、故障被判成健康**。这是半监督自学习最经典的失效模式。设一道「相似度太低就不许学」的门，就把这条路径堵死了。
3. **为什么停机要通知 AI？** 因为我的模型容差只有 ±2% R，机械负载变化会让转速在 150↔216 rpm 之间自跳。停机 0.5 s 以上再起转，工况已经变了，必须重学基线。`ai_monitor_notify_stopped()` 就是干这个的（由 main.c 的 10 ms 块调用）。

### 9.8 `HARDWARE/telemetry.c` + `m2_protocol.c/.h` —— 遥测与 WiFi 数据源

**这一份是 WiFi 链路的 STM32 端**。
**硬件**：USART3，**PB10，AF7**，**57600 8N1**，**只发送不接收**（`USART_Mode_Tx`）——这是有意设计，避免 D1 mini 反过来驱动 STM32 的输入脚。
**帧格式（M2 二进制协议，`m2_protocol.h`）**：
```c
#define M2_SYNC0        0xA5U
#define M2_SYNC1        0x5AU
#define M2_VERSION      0x01U
#define M2_PAYLOAD_SIZE 36U     /* 6 个 int32 物理量 */
#define M2_FRAME_SIZE   42U     /* 2 同步 + 1 版本 + 1 长度 + 36 负载 + 2 CRC */
#define M2_TIMEOUT_MS   3000U   /* 超过 3 秒没新帧 = 链路失效 */
```
**有效性位定义**（加速度三位保留但不再置位）：
```c
#define M2_VALID_CURRENT (1U << 0)
#define M2_VALID_ACCEL_X (1U << 1)   /* 保留，MPU6050 摘除后不再置位 */
#define M2_VALID_ACCEL_Y (1U << 2)
#define M2_VALID_ACCEL_Z (1U << 3)
#define M2_VALID_SPEED   (1U << 4)
#define M2_VALID_BATTERY (1U << 5)
#define M2_VALID_ALL     0x3FU       /* 历史定义：6 路全有效（现只用 bit0/4/5） */
```
**发送机制（关键是「不阻塞」）**：
```c
void telemetry_poll(const UI_Data *data, uint32_t nowMs) {
    if (间隔 < 10 ms) return;                     /* 10 ms 一发 */
    if (g_txLength != 0U) { ++g_skipped; return; }/* 上一帧还没发完 → 跳过本帧，不等待 */
    duty = TIM9->CCR1 + TIM9->CCR2;               /* 从寄存器读真实占空比 */
    if (TIM9->ARR != 99 || duty > 88 || level > 4) { ++g_skipped; return; }  /* 参数自检 */
    ...按有效性逐路填充 frame.value[]...
    length = m2_encode(&frame, g_txBuffer, sizeof(g_txBuffer));
    __DMB(); g_txLength = length; __DMB();        /* 内存屏障后交给中断 */
    USART_ITConfig(USART3, USART_IT_TXE, ENABLE);
}
```
**中断服务**（`USART3_IRQHandler`）**只做一件事：从缓冲区取一个字节塞进数据寄存器**——不做格式化、不做延时、不读传感器。TXE 中断优先级设成**最低的 15**，不干扰 1 ms 的 TIM7 时基。
**物理量缩放**：所有浮点量都缩成整数传输（`m2_scale()`），电流 ×1000 得 mA、转速 ×10、电压 ×1000 得 mV——**避免浮点的字节序和精度问题**。
**还有一个很实用的设计**：`frame.uptimeMs` 和 `frame.seq` 让上位机能判断「有没有丢帧」。我训练数据的门禁就是靠这两个字段做的。

### 9.9 `HARDWARE/ui.c/.h` + `oled.c` —— OLED 显示层

**核心设计：数据与显示解耦**。`ui.h` 定义了 `UI_Data` 结构体，传感器代码只往里填数，`ui.c` 只负责画。所以后面加传感器、换特征（从振动换成 R）时**显示逻辑基本不用改**——`UI_Data` 里加一个 `r_ratio` 字段就行。
**`UI_Update()` 的分片刷新**（这是性能优化的核心）：
```c
static uint8_t refreshRegion = 0U;    /* 记住上次刷到第几个区域 */
switch (refreshRegion) {
    case 0: 画转速;                break;
    case 1: 画电流;                break;
    case 2: 画 R;                  break;
    default: 画母线电压 + 相似度 + 状态 + 底条; break;
}
refreshRegion = (refreshRegion + 1) % 4;   /* 轮流 */
```
**目的**：I2C 是同步阻塞的，一次重画全部数值会长时间占住主循环、让遥测帧出现空洞。拆成 4 个区域后，单次阻塞时间降到 1/4，而整屏仍然每 4 次调用（200 ms）就更新完一遍。
**无效值的显示**：每一路都有 `xxx_valid` 标志，无效时显示 `--`（转速）、`--.--`（电流）、`--.--`（R），并且**状态字强制变成 WARN**（不管其它数据多正常）。这是「宁可显示不知道，也不显示一个假的数」。
**残影处理**：状态字统一 5 个字符宽（`"STOP "` 带一个尾空格），电流在写正数之前先补一个空格——因为正数比负数/无效串**少一列**，不补空格会残留上一次的字符。`ALARM` 这个词正好用满 5 列（末像素落在第 121 列，右边余 6 像素），换坐标前要用脚本验证一遍不溢出。

### 9.10 `HARDWARE/key.c` —— 按键

**三个常数**：`KEY_SCAN_MS = 5`（每 5 ms 扫一次）、`KEY_STABLE_CNT = 4`（连续 4 次相同才认定，即 20 ms 消抖）、`KEY_LEARN_CNT = 40`（上电后 40 × 5 ms = 200 ms 学习静止电平）。
**自学习机制**：
```c
if (s_ready == 0U) {                 /* 阶段一：上电头 200 ms 学静止电平 */
    if (learn == 0U) { s_idle[i] = s_raw[i]; s_down[i] = 0; }
    learn++;
    if (learn >= 40) s_ready = 1U;
    return;
}
/* 阶段二：正常扫描 */
uint8_t down = (s_raw[i] != s_idle[i]) ? 1U : 0U;   /* 和静止电平不同就算按下 */
```
**为什么这么设计**：HIGH 有效和 LOW 有效两种按键接法都能自适应——**不用改代码**。本板实测是低电平有效（静止 1、按下 0）。
**事件只报一次**：只在「状态从松开变按下」的那一瞬间产生一个事件（`s_pending`），主循环取走就清空。这样**按住不放不会连续触发**，而且因为主循环只取事件、没有全局锁，也就没有「档位卡死」的可能（对比第八节问题 3）。
**顺带一个小设计**：`s_hits[3]` 累计每颗键按了多少次，**故意不设上限也不用于逻辑**，就是留给 J-Link 读，用来判断「按键到底有没有被识别到」。

### 9.11 `HARDWARE/fastcap.c/.h` —— 20 kHz 高速采样前端（并行取证路径）

**作用**：用 ADC2 + DMA2 循环采集 PA5，以 **20 kHz**（= PWM 载波频率）连续采样，每 10 ms 恰好一帧 200 点。
**为什么这么做**：一帧 200 点的均值，等效于长度 10 ms 的矩形窗，**零点精确落在 100 Hz 的整数倍上**——20 kHz 载波及其各次谐波被零点吃掉。这是「载波折叠到直流」的正解，比事后做滑动平均强（滑动平均只能压低混叠后的分量，压不掉混叠本身）。
**相位锁定**：`fastcap_align_to_pwm()` 把 ADC 触发相位锁到 PWM 的 **ON 窗口中部**（`FASTCAP_ON_SAMPLE_CNT = 29`，即 14.5 µs，离起沿和落沿各约 14 µs，避开开关振铃）。依据：ON 窗口内母线电流 = 绕组电流（连续量）。
**原始块抓取**：`fastcap_arm_raw()` 一次性抓 **2000 点（100 ms）** 连续原始数据存 RAM（`g_fastcap_raw`，4000 字节），供 J-Link 直接读出，上位机做 FFT 出频谱——这是「换向纹波真实存在」的现场硬证据。
**诊断量**（都是非 static 的全局，方便 J-Link 按符号名读）：`g_fastcap_frames`（累计帧数）、`g_fastcap_ovr`（溢出次数）、`g_fastcap_last`（最近一帧的统计）、`g_fastcap_status`、`g_fastcap_alignTim9/alignTim3`（相位对齐诊断）。
**【诚实边界】** 这个前端**只做取证，不参与 AI 特征**（`main.c` 里明确注释「不改 `d.current_a`」）。

### 9.12 上位机与 D1 mini 端（WiFi 连接代码）

#### （1）STM32 端 WiFi 相关代码

见 9.8：`telemetry.c`（USART3/PB10 @57600）+ `m2_protocol.c`（编码 + CRC16 + 帧校验）。**STM32 侧不需要任何 WiFi 或 AT 指令代码**——这是选 D1 mini 方案的最大好处。

#### （2）D1 mini（ESP8266）端

**接线**：D6/GPIO12 ↔ STM32 的 PB10；**只接收**（`g_uart.enableTx(false)`），另外一根共地线。

**软件串口配置**（`d1mini_telemetry.ino`）：
```c
g_uart.begin(STM32_UART_BAUD, SWSERIAL_8N1, 12, -1, false, 512, 2048);
// 参数：波特率, 格式8N1, RX=GPIO12, TX=-1（不给 TX 脚）, 非反相, RX缓冲512, TX缓冲2048
g_uart.enableTx(false);        /* 明确关掉发送 */
```
**`TX = -1` 这一手很关键**：D1 mini 的软件串口如果只给一个引脚，库会进入「单线半双工模式」——那样它可能会去驱动这根线。STM32 的 PB10 是**输出脚**，被对方驱动会造成电气冲突。所以我把 TX 设成 -1、显式禁用发送，**保证这条线永远只有 STM32 在驱动**。

**WiFi 配置（AP + STA 双模）**：
```c
WiFi.persistent(false);        /* 不写 Flash，避免反复擦写 */
WiFi.setAutoReconnect(true);   /* 断线自动重连；只有严格抓包那 60 秒临时关掉 */
snprintf(g_ssid, sizeof(g_ssid), "Motor-%06X", ESP.getChipId());   /* 热点名带芯片 ID */
snprintf(g_password, sizeof(g_password), "%s", D1_AP_PASSWORD);   /* 固定密码 motor12345 */
g_apReady = WiFi.mode(WIFI_AP) && WiFi.softAP(g_ssid, g_password, 1, false, 2);
```
**这里有四个刻意的设计**：
- **用 AP 模式（自己当热点）**：现场不需要路由器、不受场地网络限制，手机直接连 `Motor-<芯片ID>`，地址固定 `192.168.4.1`；
- **兜底密码是固定值**：原来是每次上电随机生成 14 位、只活在 RAM 里、只能插 USB 敲 `p` 才看得到——现场演示根本没法输，等于没有兜底。现在固定为 `motor12345`，手机输一次就能一直用（页面全是只读 GET，没有任何写操作）；
- **也能走 STA（连手机热点或带路由的场地）**：连上后地址由 DHCP 分配，**会变**，用前在 USB 敲 `p` 查（`p` 会打印 `STA_SSID / STA_IP / STA_GW / STA_URL`）。只有 STA 连不上（20 秒超时）才转 AP 兜底；
- **掉线自愈**：网络就绪之后状态机仍然每轮检查 `WiFi.status()`。掉线超过 6 秒就停掉服务器、主动重连，再给 20 秒，救不回来就转 AP 兜底。**没有这一条时，热点一消失模块就会永远停在「自以为还连着」的状态：网页打不开、不重连、不开兜底、串口也不报错**，从外面看等于板子死了。

**HTTP 服务**（两个路由）：
```c
g_server.on("/", HTTP_GET, [](){                      /* 只读网页 */
    g_server.send_P(200, "text/html; charset=utf-8", MONITOR_PAGE);  /* 页面存在 Flash 里(PROGMEM) */
});
g_server.on("/status", HTTP_GET, send_status);        /* JSON 接口 */
g_server.onNotFound([](){ g_server.send(404, "text/plain", "Not found"); });
```
**主循环（有界工作量的设计）**：
```c
void loop() {
    const int available = g_uart.available();
    if (g_uart.overflow()) {          /* 缓冲区溢出：丢掉残留数据重新同步 */
        m1_discard(&g_receiver);
        for (int i = 0; i < available; ++i) (void)g_uart.read();
    } else {
        for (int i = 0; i < available && i < 512; ++i) {   /* 每次最多处理 512 字节 */
            m1_feed(&g_receiver, (char)g_uart.read(), millis());
        }
    }
    if (g_apReady) g_server.handleClient();   /* 让 HTTP 也能得到执行时间 */
    delay(1);
}
```
**「每次最多处理 512 字节」+ `delay(1)`**：这是为了让 **HTTP 请求和 WiFi 调度不被串口接收饿死**。如果一次把串口缓冲全读完，网页会卡住。
**溢出处理**：`overflow()` 后不是接着读，而是**彻底丢弃并重新同步**——因为已经丢过字节的帧不可能靠继续读来修复，必须等下一个同步头 `A5 5A`。

#### （3）JSON 序列化（`status_json.cpp`）

**最重要的一条设计原则**：**「无效」和「为零」必须能区分**——无效的测量输出 JSON `null`，而不是 0。
```c
for (unsigned i = 0; i < 4; ++i) {
    if (live && (receiver->latest.validMask & (1U << i)) != 0U) {
        snprintf(values[i], sizeof(values[i]), "%ld", (long)receiver->latest.value[i]);
    } else {
        memcpy(values[i], "null", 5U);      /* 无效就是 null，不是 0 */
    }
}
```
输出的 JSON 字段：
```json
{"version":"2.1.9","link":"live","age_ms":12,"level":1,"duty":58,
 "valid_mask":53,"rpm_x10":1460,"current_mA":320,"battery_mV":11300,
 "frames":2971,"rejected":0,"duplicates":0,"resyncs":0}
```
**字段含义**：`link` 是链路状态（waiting / live / stale）；`age_ms` 是这一帧距今多少毫秒（**用来判断数据是不是过期的**）；`frames/rejected/duplicates/resyncs` 是接收统计（**用来判断链路有没有丢帧**）。
**链接超时**：超过 `M2_TIMEOUT_MS = 3000` 毫秒没有新帧，`link` 就变成 `stale`，网页上相关数值显示 `--`。
**网页端**：`monitor_page.h` 把整个 HTML 页面以 `PROGMEM` 常量存在 Flash 里（这样 RAM 只用来跑逻辑），页面每 1 秒重新请求一次 `/status`，请求超时 2.2 秒。

#### （4）实测验收结果

- **跨板通信实测通过**：手机/电脑连上 D1 的热点后，网页能显示有效帧数持续递增（290 → 481），异常帧始终为 0，数据年龄 0.3 s；
- **D1 固件正式部署**：版本 2.1.9，独立回读校验通过；
- **断线/恢复行为**：手机 WiFi 断开再连、STM32 按 RESET 停发，页面都能正确显示 waiting/stale 并在恢复后自动回到 live；
- **主机侧测试**：协议编解码 53360 项检查通过、遥测发送 369 项通过、浏览器模拟 320/390/1280 三种屏宽无横向溢出。

## 十、评委可能追问的问题（补充弹药）

### 关于技术选型

**Q：为什么用 NanoEdge AI 而不是自己训练一个神经网络？**
A：三个理由。① 它针对 MCU 做了极致的模型压缩和代码生成，导出的库 RAM 只占 **3668 B**、Flash **3108 B**——手写一个 TFLite Micro 模型光解释器就几十 KB；② 它自动搜索了 **29,060** 个候选模型（ICM / MML / ZSM / iPCA 四类算法 + 降维组合），这个搜索量手工做不出来；③ 它导出的库能直接用 Keil 的 AC5 编译器链进去，工具链打通了。
**代价**：它是**黑盒**，模型的内部结构和权重看不见。不过我把它的**预处理链与关键参数从库文件里解出来了**（`input_size = 3`、`clust_nbr = 35`、`norm1 = 1`、`sensitivity = 0.5`，以及 `absolute → extract_features(n95, peak_value, n25) → interleaved` 这条链），所以我能说清它的判据到底是什么——这一点比大多数「用了黑盒」的人讲得清楚。
**Q：为什么只用转速，不用电流/振动？**
A：这是**实测筛出来的，不是省事**。
- 转速的标准化效应量 **15.69**，电流只有 **2.18**，电流峰峰值只有 **0.15**（完全无判别力）；
- 电流信噪比 ≈ **1**（变化 0.03 A vs 噪声 ±0.03 A），转速（归一化后）信噪比 **65**；
- 振动效应量 7.71 确实不错，但要额外传感器、额外标定、对安装姿态敏感，而转速单独已经 100% 可分。
所以我把传感器从三路砍到两路（编码器 + 母线分压），把特征从 19 维砍到 1 维。**这不是能力不够，是筛选后的结论。**

**Q：为什么模型输入是「1 轴 × 32 采样」？**
A：32 个点 × 100 ms = **3.2 秒**的窗口。这个长度是权衡出来的：太短（比如 8 点 = 0.8 s）噪声压不住，相似度会来回跳；太长（比如 128 点 = 12.8 s）响应就慢了，捏住转子要等十几秒才报警。实测 32 点在「噪声压制」和「响应速度」之间最好——捏住后 3~3.5 秒就能报警。

**Q：为什么相似度阈值定 32？**
A：阈值定的是「相似度」，不是物理量。实测：正常稳定在 **100**，捏紧后 **3~3.5 秒**内掉到 **0**，中间 20~60 这段基本是过渡态。取 **32** 落在过渡态中间偏下，配合「连续 2 窗才动作」，既不漏掉真异常，也不会被正常态的小幅波动触发。**这个值不是算出来的，是实测标出来的——我如实说。**
**Q：如果评委问「你的模型判据到底是什么」，怎么答？**
A：直接给这句话：**「32 点窗里 (rpm / V_bat) 的峰峰值 dR 超过 1.0 rpm/V、并连续 2 窗确认，就判异常。」** 然后补一句：「正常人跑的时候 dR 的 99 分位只有 0.554，捏住轴中位数能到 3.555，门限 1.0 两边都留了足够余量；模型那边还有一道相似度阈值 32 并联着，实测两道同时触发。」——**这句话的杀伤力在于：判据是能手算复现的，不是把库当黑盒。**
### 关于数据与结论

**Q：你的 100% 准确率是不是过拟合？**
A：**准确说是「会话内」的准确率，不能当泛化能力**。我的正常样本和模型学习用的是同一次采集会话，只有「握持」那 3378 个窗是真正样本外的（半监督训练不用异常样本）。不过这一版另采了 **1126 窗**独立测试批，也过了。另外这个任务本身好分——正常 dR 的 p99 是 0.554、握持中位数 3.555，中间差了六倍多，所以 95.78% 不是我厉害的证据。真正的对比是同一份数据下 **ZSM 只有 58.9%、ICM 有 92.0%**（离线预估 87.0%）。
**Q：为什么轻捏不报警？**
A：因为判决带只有 **±0.96%**，而轻捏造成的 R 变化大约在 3%~8%，虽超出带子但相似度还没掉到 32 以下（属于过渡态）。**演示时要捏紧**。这个边界是真实的：模型的敏感度由 `std`（0.10655）决定，而 std 是训练数据的自然波动，想更敏感就得用更紧的 std——但那会带来热机误报。**这是一个必须做的取舍，不是 bug。**

**Q：你说「每 10 分钟重学一次」，那不就有盲区吗？**
A：**这一版已经没有这个盲区了**。上一版是「清零重学 64 窗」，重学期间确实有 6~7 秒不检测；这一版改成**增量 learn**——每 6000 次检测（约 10 分钟）把当前窗喂一次 `neai_anomalydetection_learn()`，它只是把聚类中心往当前工况挪一点，不清空知识、也不切换阶段，检测是连续的。
但要交代一个**诚实的边界**：这条增量学习在相似度 ≥ 20 时才允许。落在 20~31 的轻度偏离（已报警但未到硬故障）如果维持满 10 分钟，确实会在增量学习里被慢慢拉回正常。这是为了换掉「漂移死锁」而做的取舍——宁可放过一个持续 10 分钟的轻度偏离，也不能让系统在工况漂移后永久卡在报警里。实测这个带很窄，捏轴 3 秒内就掉到 0，不会停在这里。
**Q：电池电压掉下去会怎么样？**
A：这正是我做归一化要解决的问题。实测：母线从 11.3 V 掉到 9.85 V，裸转速掉约 17%（和「被握住」的 17% 完全重叠，裸转速必然误报）；而 R 只掉 **7%**（13.3 → 12.37），仍然和「握住」的 10.8~11.1 分得很开。所以**电量下降不会误报，这是 R 的核心价值**。
但要诚实补一句：**归一化不能把电量影响完全消掉**。9.85 V 时 R 从 13.3 掉到 12.37，如果电池再往下掉（比如 8.8 V），R 可能逼近 11.5，那时和「握住」就接近了。所以我的方案有**工作电压下限**，大致在 9.5 V 以上可靠。这也是为什么屏上一定要显示 `Bat`——**让人知道当前还在不在有效区内**。

补充一个这一版才有的性质：判决量是 **dR（窗内峰峰值）**，电量下降会把整条曲线一起压低，峰和谷同时降，**差值基本不变**。所以「电池掉压导致 R 逼近握持区」这个问题，在判决层已经被绕开了——上面这段说的是特征 R 本身的性质，不是判决量的性质。
### 关于局限

**Q：你这个方案有什么局限？**
A：五条，我都写在文档里了：
1. **特征只有幅值统计，没有波形频率特征**。所以对「平均负载不变、只是纹波结构变了」这类故障（不平衡、齿面损伤）分辨能力有限。我做了 20 kHz 高速采样前端能出 FFT 证据，但**还没接入模型**。
2. **模型覆盖 58% 与 64% 两个工况点，但都还是「同一负载下的不同转速」，不是宽工况**。换负载水平、换另一台电机都不保证有效（这是**有意的设计边界**，工程上叫「限定工况的专用监测器」）。技术上跨档已经打通——膝点归一化后残差 6.3%，dR 判据跨档只差 0.035 rpm/V，一套 1.0 的门限通用；但**更深一层的限制没有变**：单变量 R 在信息上无法区分「负载变化」与「机械故障」，要真正做宽工况必须加第二路独立信号。
3. **正常与异常之间靠一个量分开，判决带仍窄**：dR 门限 1.0，正常侧 p99 只有 0.554（余量 1.8 倍），异常侧中位数 3.555。所以窗内若出现较大的工况漂移仍可能被判异常——靠周期增量学习补偿，代价是有几秒盲区。（早先写的 ±0.96% 是 ZSM 时代 R 的模型带宽，现行判决量是 dR，口径不同，不要再引用那个数。）
4. **转速低于手册值，但成因已清楚，不是故障**：58% 档实测 140 rpm，而 MG310 手册标称是 500 rpm 级。原因是**这台电机的实际工作点被 50% 起动死区压低了**——`rpm ≈ 17.5 × (duty − 50)`，58% 只剩 8 个百分点的有效占空比。（早先我把这件事记成「低转速之谜」并怀疑驱动板退化；换全新 D153C 后仍是 140 rpm、与旧板 142 rpm 一致，**该怀疑已排除**。）已排除的：固件 PWM、编码器标定、电池带载能力（带载实测 11.87 V 不塌压）、机械堵转（跑 10 秒不烫）、驱动板。
5. **没有做长期稳定性测试**：所有验收都是分钟级的，最长的一次连续跑了 110 秒，没跑过几小时/几天。

**Q：如果让你重新做，你会怎么改？**
A：四件事，按优先级：
1. **先把硬件电压匹配做对**。注意**不是把电池降到 2S**——我算过，电机端可用窗口由「起动死区 + 额定上限」决定，换电池只是把它挪到占空比的另一段，宽度不变，还得另配 8.4 V 充电器，比现在更糟。正确做法是**把电机额定电压抬上去**：换 12 V 额定电机，3S 12.6 V 下死区占比从 50% 降到 40%，可用区间约 40%~95%，档位数立刻能加上去——这一条能一次解决「档位少」和「可用区间窄」两个问题，是投入产出比最高的改进。
2. **先做采样链路设计，再做特征和模型**。我这次是先把 100 Hz 的 AI 闭环做完了，才回头审计采样链路，发现带宽只有 5.6 Hz、载波折叠到直流——等于地基没打牢就盖了楼。
3. **训练数据要分成训练会话和验证会话**，从一开始就保证有干净的留出集，这样准确率才敢往论文里写。
4. **选噪声更低的电流传感方案**（比如 INA240 + 采样电阻，噪声比 ACS712 低一个数量级）。如果电流能测准，就可以做成「转速 + 电流」双变量，对「电源侧故障」和「机械侧故障」做区分——这是目前单变量做不到的。

**Q：这个项目你最大的收获是什么？**
A：**学会了怀疑自己的第一直觉。** 我最初的方案是「三路传感器 + 19 维特征 + 深度一点的模型」，听起来很唬人。但做完单变量分析我发现：**一个归一化过的转速，判别力就超过 19 维里的任何单个量，而且只用两路传感器。** 后来又发现模型的数学本质就是一个自适应阈值。这两次「把自己的方案往简单里砍」，比堆功能难得多——因为要承认「我原来想复杂了」。**能在答辩里说清「我的方案其实等价于什么」，我觉得这比说「我用了 AI」更有价值。**
