## 目标
把 10-22 定版固件（OLED 显示修正版）烧进 STM32F407ZGT6，板上此前是 10-21 旧固件。

## 工具
- J-Link Commander **V4.96d**（`E://Keil_v5//ARM//Segger//JLink.exe`），S/N 20090928
- 目标识别：`Found SWD-DP with ID 0x2BA01477` / `Cortex-M4 identified` / VTarget 3.300 V
- 脚本 `OBJ/burn_final_20261022.jlink`（LF 行尾，ASCII 路径）

脚本内容（注意 `device STM32F407ZG` 不能省，省了 erase 被拒但 loadbin 照样打印 O.K. → 静默失败）：
```
device STM32F407ZG
speed 4000
h
r
h
w4 0x40026440 0x00000000
w4 0x40012108 0x00000000
w4 0x40012304 0x00000000
erase
loadfile STM32F407_Template.hex 0x08000000
r
exit
```
> 烧前三条 `w4` 是关 ADC2 / DMA2_Stream2，否则 J-Link 的 RAMCode 会压在 ADC 缓冲上。

## 独立校验（不只信 O.K.）
J-Link 自报的 **Verify: 0.000s —— 它根本没做校验**，所以必须自己回读。
`output/_verify_burn_1022.py` 做两件事：
1. 解析 Intel HEX 得到期望映像（0x08000000~0x080071B3，29108 B，**0 空洞**）
2. J-Link 分 29 块 `mem32` 回读整个映像，按 ARM **小端**展开成字节表逐字节比对

结果：

## 版本确认（板上 flash 直接读特征串）
10-22 版比 10-21 版多了一个字符串常量 `"----"`（dR 无效态，4 字符），
旧版只有 `"--.--"`（电流行，5 字符）。板上实测：
```
08003790 = 2D 2D 2E 2D 2D 00 00 00 64 52 00 00 0A D7 1F 41
           ^^^^^^^^ = "--.--"  (电流行，新旧都有)
                    ^^^^ = "dR"
080037a0 = 2D 2D 2D 2D      = "----"   <- 10-22 版独有，确认板上跑的是新固件
```

## 运行态
`output/_read_state_1022.py` 一次 halt 读完 0x20000000~0x20000120（符号地址取自**当前固件的 map**，
不能用旧记忆里的地址），读完用 `g` 继续、**不用 `r` 复位**：
- `g_i_zero` = 0.00949 V（电流零点标定有效）
- `g_phase` = 2（AI 初始化完成）
- `g_guardTrip` = 0（无保护锁存）
- 烧录后 `s_rpm` = 0 —— 电机处于停机档，未转

## 实测验证（电机转起来后）

用 `output/_read_state_1022.py` 实测（一次 halt 读完 RAM，解出 `s_lastR` 就是 OLED 第 4~5 页显示的值）：

| 档位 | `s_winDuty` | `s_rpm` | `s_lastR`（= OLED R 行） | `g_similarity` | `g_rippleAbs` | 保护 |
| --- | --- | --- | --- | --- | --- | --- |
| 58% | 58.0 | ~124 rpm | **12.20 → 12.27** | 100 | 0.129 | 未触发 |
| 64% | 64.0 | **242.3 rpm** | **12.79** | 100 | 0.238 | 未触发 |

结论：
1. **R 是两位数**（12.2 / 12.8），OLED 会显示 `12.2` / `12.8`，
   旧固件的丢十位缺陷（显示 `1.7`）已修复 —— 本次 OLED 修正**实测生效**。
2. **膝点归一化在实板上得到验证**：58% 与 64% 两档的 R 只差 5%
   （12.2 vs 12.8），落在膝点归一化的预期残差 6.3% 以内 ——
   老式 `×(58/duty)` 在这两档会差 61%，必然误报。
3. 64% 档实测 242.3 rpm，与标定值 245 rpm 吻合。
4. `g_rippleAbs` 0.13~0.24 落在稳定区间 0.3~0.6 的下缘（刚起动不久），
   远低于 1.0 报警门限；相似度 100；`g_guardTrip` = 0。

## 过程中踩到的坑

1. **J-Link 自报的 O.K. 不能信**：`Verify: 0.000s` —— 它压根没做校验。
   必须自己 `mem32` 回读整个映像做逐字节比对。
2. **J-Link V4.96d 的 mem32 输出格式**：地址是 **8 位十六进制、不带 `0x` 前缀**
   （`08000000 = 20004750 0800019D ...`），每行 4 个 32-bit 字。
   正则若写成 `^(0x...)` 一个都匹配不上。
3. **回读的是 32-bit 字，比对要按 ARM 小端展开成 4 个字节**。
4. **符号地址必须取自当前固件的 map**：+8 字节只影响 code 段，RAM 段地址没变，
   但**换了固件就得重查**，别用记忆里的旧地址。
5. **`s_rpm` 是 `volatile float` 不是 int32**：按 int32 解读会得到 1124380986，
   实际是 0x42F7C2CA = float 123.88。
6. **J-Link 读某些外设寄存器会读到全 0**：TIM9（T=0x40024000）、ADC1 全 0，
   而 TIM4（0x40000800）正常。这是 J-Link 读外设的方式问题，**不代表固件没初始化**
   —— 别据此判断固件故障。
7. `g_learned = 0` 是正常的：68 号 ICM 库自带预训练知识，上电 init(true) 即检测，
   不需要 learn 调用。
