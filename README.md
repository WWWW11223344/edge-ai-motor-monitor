# 基于边缘 AI 的电机智能状态监控

**Edge-AI Motor Condition Monitoring** · 本科毕业设计项目

基于 STM32F407ZGT6 + NanoEdge AI 的电机异常状态在线监测系统。单片机端实时计算唯一特征量
**dR（转速电压比的滚动峰峰值）**，用 NanoEdge AI（ICM 库）在板上做异常检测，OLED 本地报警；
同时经 UART 把 42 字节遥测帧发给 ESP8266（D1 mini），在手机或电脑浏览器上实时查看
转速、电压、电流与 AI 状态。

> 全套新增器件 **¥244.50**（在用 ¥194.98 / 备件 ¥49.52，主控开发板由实验室提供不计），全程零焊接。

| 关键指标 | 数值 |
|---|---|
| 特征量 | **dR = 最近 8 点 (rpm/V) 的极差**，单变量 |
| 特征窗 | 32 点 × 100 ms = **3.2 s**（每点跨 0.8 s） |
| 模型 | NanoEdge AI **ICM**，result_id 68，RAM 3668 B / Flash 3108 B |
| 判定方式 | 库内预处理链 32 点 → 3 维特征 → 35 个聚类中心的距离 |
| 基线 | 库自带预训练知识，**上电即检测**（库要求学习时按 368 行兜底） |
| 报警判定 | 相似度 < **32** 连续 2 窗；并联 dR > **1.0 rpm/V** 连续 2 窗 |
| 检测时延 | 捏轴后约 **3~3.5 s** 报警，松开后自动解除 |
| 支持档位 | 58%（约 140 rpm）与 64%（约 245~260 rpm）两档通用 |
| 固件尺寸 | Code 22288 / RO 6548 / RW 264 / ZI 17992 B |

### 为什么是 dR，而不是直接把 R 喂给模型

R = rpm / V_bus 的**电平**确实能把正常（13.2~13.5）与捏轴（10.8~11.1）分开，但那只是
离线画图能看见。实际喂进 NanoEdge 库时会出事：

- 库对输入做池化/特征抽取，**电平的细微变化会被平均掉**；
- 同批数据实测：R 电平 + 均值池化只有 **58.9%**；换成滚动峰峰值后离线预估 **87.0%**、
  训成 ICM 后混淆矩阵实测 **92.0%**。作为对照，**直接用 dR 固定阈值 1.0 判决（不经模型）
  是 87.6%**——每行 32 个 dR 取最大值与 1.0 比，正常侧 0 / 2252 误报。

dR 的定义是「最近 8 个点的极差」，它不问水平高低，只问这段时间里**摆动了多少**。
捏一下轴 → 转速瞬时跌落 → 极差立刻顶上去，不会被任何平均抹平。物理依据是
`Δω = ΔT·Ra/Ke²`：捏力恒定则负载力矩恒定，所以转速跌幅是**绝对量**，
与工作点无关 —— 这就是它能跨档位通用的原因。

| 量 | 58% 档 | 64% 档 | 结论 |
|---|---|---|---|
| 稳定运行 dR | 0.13~0.21 | 同量级 | 两档一致 |
| 捏轴 dR | **2.0~3.2** | **2.0~3.2** | 两档一致，差 0.2% |
| 用「相对降幅」会怎样 | 21% | 10% | **差一倍，不能跨档** |

所以判决用 dR（绝对量），而 R 的电平仍然保留为观测量显示在 OLED 与网页上。

### 为什么用 ICM 而不是更小的 ZSM

ZSM 库本身只有 56 B，但它的内部把 32 点**均值池化成 1 个值**再做 Z-score，
等价于一行阈值 `if`——看不见时序形状，也看不见跳变。ICM 库大 3.7 KB，
但它的预处理链是 `absolute → extract_features(n95, peak_value, n25) → interleaved`，
把 32 点压成 **3 维**（95 分位、峰值、25 分位）再和 35 个聚类中心比距离，
**保留了峰的形状**。这 3.7 KB 换来的是检出率 58.9% → **92.0%**（离线预估 87.0%）。

完整推导见 [`docs/设计方案_最终版.md`](docs/设计方案_最终版.md) 与
[`docs/训练与选型记录_20261021.md`](docs/训练与选型记录_20261021.md)。

## 编译产物尺寸

Keil 全量重建，0 Error 0 Warning：

| 段 | 大小 |
|---|---|
| Code | 22288 B |
| RO-data | 6548 B |
| RW-data | 264 B |
| ZI-data | 17992 B |
| 合计 ROM | 29100 B（Code + RO + RW） |

共 27 个编译单元（26 个 `.c` + 1 个启动文件），FWLIB 只保留 misc / adc / dma / gpio / rcc / tim / usart。
`OBJ_firmware/` 里的 `.hex` 与 `.map` 是同一次构建产物，`.map` 的 Load Region 为 `0x71AC`（29100 B），
与上表一致。烧录后用 J-Link `mem32` 回读 `0x08000000` 起 256 字节，与 hex 逐字节相同。

NanoEdge AI 模型本身占 **RAM 3668 B / Flash 3108 B**。库端 `learning_min_lines = 368`
是「库如果要现场学习，至少要喂 368 行」的意思；本版用的是库内预训练知识
（`neai_anomalydetection_init(true)`），所以**上电即检测**，不必等 36.8 s。
两者不是同一个参数，别混。

## 实测效果

58% 档（140 rpm，母线 10.8 V）：

| 状态 | 相似度 | dR (rpm/V) | 电流 | 报警 |
|---|---|---|---|---|
| 空载正常 | **100** | 0.13~0.21 | +82 ~ +130 mA | 0 |
| 捏住输出轴 | **0** | **3.23** | **+196 mA** | **1** |
| 松开恢复 | **100** | 0.16 | +74 mA | 0 |

- 上电起转后立即进入检测（`learned = 0`、`needLearn = 0`）；
- 捏轴约 **3~3.5 s** 触发报警（PF9 低电平点亮），松开后自动解除，无需复位；
- 离线混淆矩阵：正常 2242/2252 判对（误报 10）、异常 3108/3378 判对（漏报 270），
  Balanced Accuracy **95.78%**、Quality Index **93.4**。

四种页面状态见 `docs/页面实拍_正常检测.png`、`页面实拍_异常报警.png`、
`页面实拍_学习中.png`、`页面实拍_停机.png`。

### 电流读数为什么曾经是负的

这是本项目最隐蔽的一个 bug，值得单独写一段：屏显电流一度稳定显示 **-0.37 A**，
而同一工况下 D1 采集的数据全是正的。真因不是传感器接反，而是**PWM 纹波与采样节拍相位混叠**：

- PWM 20 kHz → 周期 50 µs；采样节拍 10 ms = **200 个整周期**；`nowMs` 分辨率 1 ms = 20 个整周期；
- 三个数都是整数倍 → 每次采样永远落在纹波的**同一相位** → 8 点滑动平均采到 8 个几乎相同的值，
  **平均等于没平均**，直流分量被纹波偏置顶歪；
- 停机时没有纹波（`duty = 0`），所以零点永远是准的 —— 这也是「停机准、带载才偏」的原因。

修法是**采样相位抖动**：用 DWT 周期计数器在每次取 ADC 前延后 `g_i_dither × 1050` 个内核周期
（168 MHz 下 6.25 µs，8 步正好铺满 50 µs）。修复后 58% 档空载 **+82~+130 mA**、
捏轴 **+196 mA**，与独立通道采集的 `grip_58 ≈ +196 mA` 完全吻合。

### 使用边界（会踩到的坑）

1. **本装置定位是「固定负载下的专用监测器」**。设计内的负载变化与故障在物理上同向同形，
   单变量无法区分，所以电机必须固定（夹具或双面胶压住）。
2. **冷机与热机的基线略有差异**（热机转速高约 2%）。dR 判据对这点不敏感（它看的是波动量），
   但相似度会有几个点的差别，属正常。
3. **74% 以上的占空比会被 3S 保护板拉闸**，有效区间只有 50~70%，固件里已加编译期硬上限。

## 复现步骤

### 1. STM32 固件

1. Keil MDK 5 打开 `firmware_stm32/USER/STM32F407_Template.uvprojx`
2. Build（或直接用 `firmware_stm32/OBJ_firmware/STM32F407_Template.hex` 烧录）
3. 首次上电保持电机停转 → 自动完成电流零点校准（64 次平均）
4. 按 PE3 升档起转，转起来后等 OLED 第 6 页的相似度 `S:` 达到 100

**烧录注意**：J-Link 脚本必须带 `device STM32F407ZG`，不带时 erase 会被静默拒绝
却照样打印 O.K.。仓库里的 `burn_final_20261021.jlink` 已经写好，
并且烧录前会先关 ADC2/DMA2（否则它们会持续写 RAM 干扰）。

### 2. D1 mini 网页监视器

1. Arduino IDE 装 ESP8266 支持，打开 `firmware_d1mini/d1mini_telemetry.ino`
2. 把 `wifi_config.h` 里的 `D1_WIFI_SSID` / `D1_WIFI_PASSWORD` 改成你的热点（仓库里是占位符）
3. 烧录后打开串口（**115200**），等它打印 `STA_READY ip=...`
4. 手机或电脑连同一个热点，浏览器访问 `http://<那个 IP>`

**关于访问地址**：本机实测为 **http://192.168.157.79**，但这是 DHCP 分配的，换环境就会变。
往串口发一个字符 `p`，固件会打印当前 STA 地址 / AP 地址与访问 URL（`?` 打印自检信息）。
如果 20 s 内连不上热点，D1 会自动转为 **AP 兜底模式**，自开热点并把页面挂在固定地址
**http://192.168.4.1**。

### 3. 训练自己的 NanoEdge AI 模型（可选）

数据集在 `dataset/`，每行 32 个数（一个 3.2 s 特征窗的 dR 序列），空格分隔、无表头无标签。
在 NanoEdge AI Studio 新建工程：信号长度 32 点、**1 维**、传感器类型 Current、
资源上限 32 KB RAM / 512 KB Flash，然后按 nominal / anomaly 分别导入两份 CSV。
**务必手动关闭 Detrend**（开着会把 dR 的水平差异一起抹平）。

两个容易踩的坑：

- **`-fshort-wchar` 必须勾**。Studio 导出的库默认按 4 字节 `wchar_t` 编译，
  而 Keil ARMCC 是 2 字节，直接链接会报 `L6242E: Cannot link object ... wchar_t`。
  解决办法是在 Deployment 页勾上 `-fshort-wchar` 重新导出库（本次已勾）。
- **`float_abi` 实测是 hard**，与旧文档写的「软浮点」相反。工程里 `-mfloat-abi` 也必须是 hard，
  两边一致才能链接。

推荐算法 ICM，参数见 `docs/icm_model_params.json` 与 `docs/metadata.json`。
